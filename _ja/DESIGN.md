# Design

このプラグインの各部分がなぜこう配線されているのか、そしてそこから導かれる契約。スキルが**何のため**の
ものかは [`README.md`](README.md) にある。

## 三つの層

| 層 | どこ | それが走る文脈 |
|---|---|---|
| Instruction | `commands/` | 散らかったほう — 取得、質問、そもそも何が欲しいのかの割り出し |
| 原則とルーティング | `skills/dont-make-me-read` | メインスレッド |
| 成果物固有のルール | `skills/write-nice-*` | fork。上記を一切持ち込まない |

以下の境界はすべて、その下の層に何かが入り込むのを防ぐために存在する。

> 【訳注】この表は 8 スキルのうち 3 つ（`write-nice-*`）と入口 1 つしか載せていない。
> `avoid-*` 2つと `review-*` 2つは表に現れず、下の散文でのみ触れられている。

## `/` メニューにスキルは一つも出さない

ルールは、他の作業の途中で書かれるコードコメントにまで届かなければならない。そこで手を止めて書き物用
スキルを名指しする人間はいないので、名指しされたときだけ発火するスキルは、最も必要とされるその瞬間に
決して走らない。したがってすべてのスキルはモデル起動（`disable-model-invocation: false`）であり、
メニューからは隠される（`user-invocable: false`）。

そうすると明示的な経路は `commands/` に残る。これは、何かを書かせたい／チェックさせたいと自分で決めた
人間が打つもの。

## コマンドはスキルのエイリアスではない

同じ依頼はいくつかの形で到着する。issue の場合：内容がすでに書かれている。あるいは issue が既に存在し、
取得して改善する必要がある。あるいは何も決まっておらず、issue が何であるべきかがまだ会話の途中である。

これを仕分けるのは実際の作業であり、そのすべてが会話 — 中途半端な依頼、取得した資料、質疑応答、
持ち出されては捨てられた選択肢。コマンドがそれをやり、それから一つにまとめたブリーフを引き渡す。

もしスキルが入口だったら、その会話まるごとが**成果物が書かれる文脈**に居座り、成果物に表出する。
それこそ `avoid-unverifiable-context` が締め出すために存在する残滓である。

## writing スキルは fork する。他はしない

「この会話の参加者にしか再構成できないことを書くな」は、書き手が破りうるルール。`context: fork` は
会話履歴を一切持ち込まないので、会話を見たことのないスキルはそこから書くことができない。禁止が**性質**に
変わる — `structuring-skills.md` が二つのサブエージェントに互いの出力を見せないためにすでに打っているのと
同じ手。

他のスキルがメインスレッドに留まるのは、fork するとそれらが作用する対象から切り離されてしまうから：

- `dont-make-me-read` はルーティングする。ルーティングは目の前の作業についての判断である。
- `avoid-unverifiable-context` と `avoid-reference-detours` は、書くことが起きているその場で、起きている
  まさにその瞬間に制約をかける。
- 二つの `review-*` スキルは findings を返すが、findings は根拠が付いていて初めて価値を持つ。レビューを
  fork の向こうに置くのは `structuring-skills.md` が名指ししているケースそのもの — そうすると誰も
  レビューをレビューできなくなる。

## `review-nice-issues` はツールを一切持たない

その価値のすべては、そのテキストだけを手にしている実装者と同じやり方で issue 本文を判断することにある。
`allowed-tools: []` は、それを「覚えておくべき規律」ではなく**性質**として述べたもの。参照を解決できず、
リポジトリを確認できず、本物の読み手にも確認できない主張を裏取りできない。

したがって取得は呼び出し元の仕事 — `/review-issue` が issue を読んで本文を引き渡し、それ以外に知り得た
ことは何も一緒には行かない。

## スキルを追加する

どの層に属するかが frontmatter を決める。二つの問いで決まる。ブリーフから成果物を生み出すのか、それとも
すでにモデルの目の前にある作業に作用するのか。そして findings を報告するなら、その根拠は一緒に戻ってくるか。

ここのすべてのスキルは、例外なく：

```yaml
user-invocable: false           # / メニューにスキルは出さない。入口は commands/ にある
disable-model-invocation: false # スキルがいつ該当するかはモデルが決める
```

ブリーフから成果物を生み出すスキルは、これを足す：

```yaml
context: fork                   # 呼び出し元の会話を一切持たずに走る
background: false               # 呼び出し元が同じターンで結果を見せる
```

`agent` と `model` は未設定のままにする。どちらも fork を「情報収集の実行が必要とするもの」まで狭めて
しまう。読み取り専用のツールセットでは書けないし、ファイルを列挙できる最安のモデルは、人が行動する
ことになる文章を起草させるモデルではない。

ユーザーに面する入口はスキルではなく `commands/` 配下のファイルである。

> 【訳注】この「例外なく」の契約表に `allowed-tools` が入っていない。実際には全スキルが持ち、しかも
> `review-nice-issues` の `allowed-tools: []` は上の独立した節で設計上の性質として説明されている。

`SKILL.md` をコミットする前に：

```bash
bash skills/write-nice-skills/scripts/count-tokens.sh skills/*/SKILL.md
```

非ゼロなら本文が5000トークンを超えている。そのスキルの `references/` に枝固有の詳細を押し出して通るまで
繰り返す。references には深さのルールがあり、サイズのルールはない。

> 【訳注】「非ゼロなら5000トークン超過」は不正確。スクリプトの exit 1 は「ファイルが存在しない」でも
> 返り、exit 3 は「計測失敗」。
