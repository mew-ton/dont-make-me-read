# dont-make-me-read

[Claude Code](https://claude.com/claude-code) プラグイン。誰かが行動する前に読まねばならないもの
— GitHub issue、PRレビュー指摘、残り続けるドキュメント、`SKILL.md`、コメント、コードそのもの — を、
読み進めるのに難儀せずに行動できるように書くためのスキル群。

## 二つの命題

ここにあるすべてのスキルのすべてのルールは、この二つから導かれる。

1. **何をすればいいか把握するために、大量のものを頭に抱えたい人間はいない。** 美しいテキストのためでも、
   網羅的なテキストのためでも、丁寧なテキストのためでも同じ。測られているのは、目の前のものを理解する
   ために読み手が抱えねばならない範囲であって — そしてその読み手は人間かエージェントのどちらかである。
   どちらもそれを集めるコストを払い、どちらも最終的に手元に残ったものに基づいて行動するからだ。
2. **書き手にはその量が分からない。** 自分の下書きは、そこに欠けている文脈を自分で補いながら読むことに
   なる。だから範囲は自分にとっては小さく読める — 自分にとってだけ。

二つ目が、これが助言ではなくスキル群である理由。各スキルは、書いている最中に湧いてくる言い訳のための
Common Rationalizations（よくある自己正当化）の表を持っており、そのうちのいくつかは**すでに書かれた
テキストに対して走らせるためだけに**存在する。

## 一つのテスト

あらゆる粒度で — 単語、文、節、ファイル：

> **これは読み手が次に取る行動を変えるか？**

変えない：削る。変える、かつ欠けている：足す。短くすることも長くすることも、どちらも結果であって
目的ではない。使用箇所でルールを言い直すのは1行のコストで別ファイルへの往復を節約する。差分を引用して
返す代わりに `path:line` を指すのは、読み手がすでに開いているものの再読を節約する。同じ判断の、逆方向。

同じテストを単語レベルでかけると、内部フィールド名、でっち上げのラベル、"as appropriate"（適宜）が
揃って不合格になる理由が分かる。どれも、読み手が行動する前に解決しなければならないものを残している。

## Commands

コマンドがユーザーに面する唯一の表面。何かを書かせたい／チェックさせたいときにこれを打つ。

| Command | 何をするか |
|---|---|
| `/write-issue` | GitHub issue の本文を起草または改稿し、その結果を監査する。 |
| `/write-review-comment` | PRレビュー指摘を起草または改稿する。 |
| `/write-skill` | `SKILL.md` を書く、またはレビューする。 |
| `/write-architecture` | アーキテクチャドキュメントを書く、または改稿する。 |
| `/review-issue` | 既存の issue 本文を監査する。 |
| `/review-text` | PRの説明文と、そのPRが変更するコードコメントを監査し、求められればその指摘をPRに投稿する。 |

writing コマンドは instruction レイヤーであって、スキルのエイリアスではない。散らかった部分 — 既存の
issue の取得、まだ決まっていないことの質問、そもそも指摘が何なのかを突き止めること — をコマンドが担い、
成果物を所有するスキルに**一つにまとめたブリーフ**を渡す。そのスキルはこの会話を一切持たずに走るので
（`context: fork`）、ブリーフを生み出したものは何一つ、書かれる成果物に表出しない。これは
`avoid-unverifiable-context` のルールを、書き手の記憶に頼らせるのではなく構造で強制したもの。

## Skills

`/` メニューにはどのスキルも現れない。スキルはモデル自身の判断で、書いている最中にロードされ、上記の
コマンドが必要なものを呼ぶ。それが狙いで、これらのルールは**他の作業の途中で書かれるコードコメント**に
まで届かなければならない。そこで手を止めて書き物用スキルを名指しで呼ぶ人間はいない。

| Skill | 役割 |
|---|---|
| [`dont-make-me-read`](skills/dont-make-me-read/SKILL.md) | 常時の層。読み手が抱えねばならない範囲、それが壊れる三通り、上記のテスト、そしてそのために決して削ってはならないもの。 |
| [`write-nice-issue-description`](skills/write-nice-issue-description/SKILL.md) | 実装者が単独で行動できる GitHub issue 本文を書く。確定できる問題、チェック可能な受け入れ基準、スコープ外の境界。 |
| [`write-nice-instructions`](skills/write-nice-instructions/SKILL.md) | PRレビュー指摘の形を整える。一つの固定テンプレート（title / summary / details）と、対処をどれだけ強く言い切るか。 |
| [`avoid-unverifiable-context`](skills/avoid-unverifiable-context/SKILL.md) | 読み手が確認しに行けないものを、残り続けるテキストから締め出す。会話、レビュースレッド、コードにもう現れない過去の状態。 |
| [`avoid-reference-detours`](skills/avoid-reference-detours/SKILL.md) | 目の前の文を理解するために、到達可能などこかへ読み手を送るのをやめる。使用箇所で述べよ。原典はその場に残る。 |
| [`avoid-caller-knowledge`](skills/avoid-caller-knowledge/SKILL.md) | どの呼び出し元から呼ばれたかをモジュールに知らせない。コードにおける同じ範囲の失敗であり、そこでは言い直すことが依存を作るので、知識のほうを外へ出す。 |
| [`write-nice-skills`](skills/write-nice-skills/SKILL.md) | `SKILL.md` の description と本文を、確実に発火し、かつ軽く保たれるように書く／レビューする。 |
| [`write-nice-architecture-docs`](skills/write-nice-architecture-docs/SKILL.md) | 貢献者が判断に使う基準を担い、実装を閉じたまま判断できるようにする。 |
| [`review-nice-issues`](skills/review-nice-issues/SKILL.md) | `write-nice-issue-description` が書くときに満たす条件と同じもので、issue 本文をテキストだけから監査する。 |
| [`review-self-contained-docs`](skills/review-self-contained-docs/SKILL.md) | PRの説明文と、そのPRが変更するすべてのコメントを自己完結性（time-closure、referenceability、reference-scope closure）で監査する。 |
| [`find-document-dependencies`](skills/find-document-dependencies/SKILL.md) | そのドキュメントが何のために書き換えられねばならなくなるかを、何が何に固定されどちら側が動かねばならないかのグラフとして洗い出す — 固定先が場所なら弱、内容なら強 — 判定は呼び出し元に委ねる。 |

重みを担うのは二つである。**`dont-make-me-read` が常時の層**であり、二つの命題、範囲、テストを担う。
成果物を一つも名指しせず、どのスキルも指さない。それが、活動がいくつ増えてもこの層を固定サイズに保つ —
そしてテンプレートも予算も持たないので、これが効力を持っていることが、手元の成果物のルールをロードする
ことの代わりにはならない。**`write-*` スキルは一つの活動のベストプラクティスを保持する** — そのセクション、
予算、満たすべき条件。

残りは、その二つ目に**仕える**のであって、横に並ぶのではない。**`avoid-*`** スキルは、作業が何であろうと
成立する失敗モードを一つ名指しする — コードコメント、JSDocブロック、PR説明文、コミットメッセージ、
モジュールのインターフェース — だからあらゆる成果物の下地として効き、ここで最も広いトリガーを持ち、
たいていの書き物はこれ以上を必要としない。
**`review-*`** スキルは、同じ条件をすでに書かれたテキストに対して単位ごとに逆向きに走らせる。これが命題2を
実運用に落としたものである：authoring スキルが条件を述べ、書き手は自分の下書きを judge できない。これらは
どれも、読み手が確認できないことを確認できてしまうツールを持たない。その同じ足場に立っていること自体が
成果物である場合には、スキルはツールを一つも持たず、取得は呼び出し元の仕事になる。

**`find-*`** スキルは判定ではなく材料を返す。判定するパスが、judge する対象を持てるようにするためである —
findings は根拠の価値以上のものにはならないからだ。

動詞は、そのどれを見ているのか、そしてどちらの方向に引き算するのかを示す。三つの `avoid-*` スキルは一つの
問いを分け合っている — 読み手の範囲が、その成果物の外へどこまで伸びているか。`avoid-unverifiable-context`
は読み手がそもそも到達できないもので、直し方は削除。`avoid-reference-detours` は読み手が**到達できる**のに
行かされたもので、直し方はここで言い直し、原典はその場に残すこと。`avoid-caller-knowledge` はその二つ目の
ケースのコード版で、そこでは言い直すことが依存を作るので、代わりに知識のほうが外へ出る。

どの読み手が基準を決めるかは成果物ごとに違う — `write-nice-instructions` は最初の数行で行動するか流し読み
するかを決める人間に合わせ、`write-nice-skills` はファイルをロードするか判断するエージェントに合わせる —
が、ここにあるどの成果物も**両方**に読まれ、両者は同じノイズから別々の誤った結論に至る。

## Language

スキルは英語で書かれており、そのトリガーと実例も英語。公開されたスキルは、利用者がどの言語で
プロンプトを打つか知り得ないからだ。スキルが**何を書けと指示するか**は別の問題で、各 writing スキルは、
issue／指摘／ドキュメントを、その読者がすでに使っている言語で、かつ**一つの言語だけで**書けと言っている。
ルールが固定するのはテキストの形と、それが担う文脈であって、それを担う言語ではない。

## Architecture

このプラグイン自身の形についての判断を何が決めるか — 新しい入口をどこに置くか、スキルがどの文脈で走るか、
どのツールを持つか — は [`ARCHITECTURE.md`](ARCHITECTURE.md) にあり、そこから導かれる frontmatter の
契約もそこにある。
