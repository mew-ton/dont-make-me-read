# Design

このプラグイン自身の形についての判断を何が決めるか。8つのスキルを先に読まなくても判断できるように。
スキルが**何のため**のものかは [`README.md`](README.md)、各スキルが何を言うかはそれぞれの `SKILL.md`。

以下の見出しはすべて、貢献者が実際に直面する判断である。あなたの判断がここに無いなら、それはこのファイル
の穴であって、`skills/` にたまたま在るものから答えを帰納してよいという許可ではない。

## Where a new entry point goes（新しい入口をどこに置くか）

**人がそれを起動すると決める → `commands/`。すでに進行中の作業に届かねばならない → スキル。**

ルールは、他の作業の途中で書かれるコードコメントに着地しなければならない。そこで手を止めて書き物用スキル
を名指しする人間はいないので、名指しされたときだけ発火するものは、最も必要とされる瞬間を取り逃がす。それ
こそモデル起動が買うものであり、ここのすべてのスキルが `/` メニューから隠されている理由でもある。メニュー
にあるスキルは打たれることを誘うが、打たれるという場合はすでに `commands/` のほうがうまく扱う。

つまり二つの経路は同じものの代替ではない。コマンドは、何かを書かせたい／チェックさせたいと**自分で決めた**
人が打つもの。スキルは、何も決めていない人に**届く**もの。

## What a command owes the skill it calls（コマンドが呼ぶ先に負うもの）

**未決着のものはすべてコマンドで決着させる。渡るのは一つのブリーフ。**

同じ依頼はいくつかの形で到着する — issue なら、内容がすでに書かれている／issue が存在して取得が要る／
そもそも issue が何であるべきかがまだ会話の途中。これを仕分けるのは実際の作業であり、そのすべてが会話で
ある：中途半端な依頼、取得した資料、持ち出されては捨てられた選択肢。

生の会話をそのままスキルに渡すコマンドは、その会話を**成果物が書かれる文脈**に入れてしまい、それは成果物に
表出する。先に一つにまとめることがそれを締め出す — そして下記の `context: fork` が、それを「覚えておく」
ではなく構造にする。

## What context a skill runs in（スキルがどの文脈で走るか）

**ブリーフから成果物を生み出す → fork。すでにモデルの目の前にある作業に作用する → メインスレッド。**

fork は会話履歴を一切持ち込まないので、会話を見たことのないスキルはそこから書けない。「この会話の参加者に
しか再構成できないことを書くな」は、書き手が破りうるルールであることをやめ、破れない**性質**になる —
`structuring-skills.md` が二つのサブエージェントに互いの出力を見せないために打つのと同じ手である。

この基準は逆向きにも同じ強さで効く。すでに目の前にある作業に作用するスキルを fork すると、それが作用する
対象から切り離される。ルーティングは目の前の作業を要る。書くことへの制約は、書くことが起きる場所で起きね
ばならない。そしてレビューは findings を返すが、findings は根拠が付いていなければ何の価値もない — レビュー
を fork の向こうに置けば、誰もそのレビューをレビューできない。

その基準で9つすべて：

| 走る場所 | スキル |
|---|---|
| fork | `write-nice-issue-description`、`write-nice-instructions`、`write-nice-skills`、`write-nice-architecture-docs` |
| メインスレッド | `dont-make-me-read`、`avoid-unverifiable-context`、`avoid-reference-detours`、`review-nice-issues`、`review-self-contained-docs` |

これが frontmatter を決める。ここのすべてのスキル：

```yaml
user-invocable: false
disable-model-invocation: false
```

fork はこれを足す：

```yaml
context: fork
background: false
```

`background: false` は、呼び出し元が同じターンで結果を見せるから。`agent` と `model` は未設定のままに
する：どちらも fork を**情報収集**の実行が必要とするものまで狭めてしまい、読み取り専用のツールセットでは、
その fork が生み出すために存在する成果物を書けない。

## What tools a skill gets（スキルがどのツールを持つか）

**自分の仕事が必要とするもの — ただし、その読み手には確認できないことを確認できてしまうものを引いた残り。**

見落としやすいのは引き算のほうである。`review-nice-issues` は、そのテキストだけを手にしている実装者と同じ
やり方で issue 本文を判断する。だから `allowed-tools: []` は倹約ではない。その足場を構造にしたものである。
参照を解決できず、リポジトリを確認できない — それはまさにその読み手が置かれている位置だ。「便利だから」と
`gh` を与えれば、その判定を意味あるものにしている唯一の性質が消える。だから取得は、それを呼ぶ側に属する。

その引き算が当てはまらない場合、スキルは仕事が必要とするものを取る — `review-self-contained-docs` は、
判断する対象のプルリクエストを読む。

## Where an explanation goes（説明をどこに置くか）

**誰がそれを抱えねばならないか、そしてどれだけの頻度でか、で決まる。**

| その説明が | 置き場所 |
|---|---|
| 貢献者が判断に使うもの | ここ |
| スキルのすべての経路が必要とするもの | そのスキルの本文 |
| 一部の枝しか到達しないもの | そのスキルの `references/` |
| フィールドの意味 | frontmatter のどこでもない |

frontmatter は `SKILL.md` の中で唯一、読まれるのではなくパースされる部分であり、その全体が発火のたびに
ロードされる。そこに付けた末尾の `#` は、それで混乱したはずのない読み手に何も説明せず、すべての読み手が
永遠にそのコストを払う。枝固有の詳細を `references/` へ押し下げるのと同じ議論が、一段上に当てはまって
いるだけである。

## When an artifact earns rules of its own（成果物が固有ルールを持つのはいつか）

**その形が、一般則では供給できないほど固定されているとき：名前の付いたセクション、予算、テンプレート。**

たいていの書き物にはそんな形がない — コードコメント、コミットメッセージ、PR説明文。それらは
`dont-make-me-read` のテストと二つの `avoid-*` スキルで足りる。この二つがここで最も広いトリガーを持つのは
そのためである。

issue 本文、レビュー指摘、`SKILL.md`、アーキテクチャドキュメントの4つはその基準を超え、それぞれ一つの `write-*`
スキルを得た。新しい成果物の種類はそれを超えるか超えないかのどちらかであり、超えないものにスキルを足すと、
判断すべき description がもう一つ増えた重みを以後のすべてのターンが払う。

## What to do when a body is over budget（本文が予算を超えたとき何をするか）

**一部の枝しか到達しないものを、そのスキルの `references/` へ押し出す。通るまで。**

```bash
bash skills/write-nice-skills/scripts/count-tokens.sh skills/*/SKILL.md
```

非ゼロなら、まだコミットしない。どのコードが何を意味するかはスクリプト自身のヘッダにあり、そのうち予算に
ついてのものは一つだけである — 残りはチェックが走らなかったことを言っており、それは合格ではない。
references には深さのルールがありサイズのルールはないので、材料は削除されるのではなく、発火のたびに全員が
払う経路から外へ移されるだけである。
