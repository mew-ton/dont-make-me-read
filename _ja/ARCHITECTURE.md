# Architecture

## Bird's eye view（俯瞰）

誰かが行動する前に読まねばならないもの — issue、レビュー指摘、アーキテクチャドキュメント、`SKILL.md`、
コメント、コードそのもの — は、それを理解するために抱えねばならない範囲で支払われる。そして書き手にはその
範囲が感じられない — 自分の下書きは、欠けているものを自分で補いながら読むからだ。このプラグインはそこから
導かれるルールを、参照されるのを待つのではなく書いている現場に届くように配置したものである。

層は二つ。`dont-make-me-read` が常時の層 — テストと、範囲の壊れ方。成果物を一つも名指しせず、どこにも
引き渡さない。それが、活動がいくつ増えてもこの層を固定サイズに保つ。その上に、活動ごとに一つのスキルが乗り、
その活動の範囲がテストだけでは供給できない振る舞いをする部分を担う。複数が同時に立ち、その間を調停するものは
無い。だから積み上がりを支払い可能に保つのはサイズだけである。

ベストプラクティスはスキルが保持しているので、そのスキルは judge する対象から隔離される：成果物について
議論してきたセッションの中で走らせれば、標準はたった今言われたことのほうへ曲がる。成果物は外から生み出される
— 人はコマンドから、エージェントは fork から。

## Cross-cutting concerns and invariants（横断的関心事と不変条件）

### The golden rule（ゴールデンルール）

**覚えておかねばならないルールは破られる。それを性質にしてしまう仕掛けを作り、その仕掛けを、書くことがすでに
起きている場所に置け。**

このファイルが名指ししていない判断は、ここから導く：何が覚えておくべきことになるのか、そしてどんな配置なら
その必要が消えるのかを問う。

### The invariants it generates（そこから生まれる不変条件）

- **メニューから名指しされて到達できるものは無い。** ルールは作業の途中に着地せねばならず、作業の途中で手を
  止めて名指しする人間はいない。
- **常時の層は成果物を一つも名指しせず、どのスキルも指さない。** 在庫リストは更新箇所がもう一つ増えることで
  あり、しかも列挙する対象と共に増える — そしてここは、固定サイズを保たねばならない唯一のファイルである。
  スキルには自分の description で到達するか、さもなくば到達しない。
- **成果物を生み出すスキルは、そこに至った会話を決して見ない。** これが二つを同時に締め出す：読み手が確認
  できない残滓と、標準に対するセッションの引力。
- **スキルは、その読み手には確認できないことを確認できてしまうツールを決して持たない。** 足場そのものが成果物
  である場合、それを超えるものは、判定を「使わないでおくと誰かが覚えている限り」しか健全でなくする。

### Out of scope（スコープ外）

- スキルは自分の軸だけを judge する。リポジトリ接地性、依存の閉包、スコープは呼んだ側のもの。
- 汎用の「これをレビューして」の入口は無い。
- ツールチェーン、パッケージマネージャ、インストールパスを前提にしない。
- description に第二言語のキーワード列を置かない。

## Where a new entry point goes（新しい入口をどこに置くか）

**人がそれを起動すると決める → 打てるもの。すでに進行中の作業に届かねばならない → スキル。** ある活動の
あいだ効き続けねばならないルールも後者である：それを常時にしているものはスキルの内側にあり、その脇に置かれた
仕掛けではない。

## How a rule stays on（ルールはどうやって効き続けるか）

**description が中に入れ、body が中に留める。** ロードの前に読まれるテキストは description だけなので、
ある活動のあいだ効いていなければならないスキルは、その活動を `when` として述べる — 作業がたまたま含んでいる
語ではなく。そのルールを最も必要とする作業こそ、それを名指ししない作業だからである。ロードされたあとは、
まだ効力があると言わない body は、ロードされたのと同じターンのうちに効力から抜け落ちていく。

ゴールデンルールが求めるのは性質であり、これは性質ではない：毎ターン取り直される判断である。この仕掛けが
許すのは非対称なデフォルトのほうだ — 迷っているあいだは効力があり、解除は明示的な語によってのみ — そうすれば
安く済むほうの失敗が、ルールが効いたままになる側になる。

## What a command owes the skill it calls（コマンドが呼ぶ先に負うもの）

**未決着のものは引き渡しの前にすべて決着させる。渡るのは一つのブリーフ。** 代わりに会話をそのまま渡せば、
それは成果物が書かれる文脈に着地し、そこに表出する。

## What context a skill runs in（スキルがどの文脈で走るか）

**ブリーフから成果物を生み出す → セッションの外。すでにモデルの目の前にある作業に作用する → その場で。**

後者を隔離すると、作用する対象から切り離される：ルーティングは作業が目の前にあることを要し、制約は書くことが
起きる場所で効かねばならず、findings は根拠なしには価値がない。

すべてのスキル：

```yaml
user-invocable: false
disable-model-invocation: false
```

成果物を生み出すものはこれを足す：

```yaml
context: fork
background: false
```

`agent` と `model` を設定するのは、収集そのものが仕事のすべてである fork に限る。成果物を生み出す fork は
どちらも持たない。

## What tools a skill gets（スキルがどのツールを持つか）

**仕事が必要とするもの。ただし読み手には確認できないことを確認できてしまうものを引く。** この引き算が効くのは
その足場そのものが成果物である場合だけで、そのとき取得は呼び出し元に属する。

## Where an explanation goes（説明をどこに置くか）

**貢献者が判断に使うものはここに置く。ある成果物の読み手が必要とするものはその成果物と共に置き、その中の
どこに置くかはその成果物自身のルールが言う。**

## When an activity earns rules of its own（活動が固有ルールを持つのはいつか）

**活動ごとに一つ、そしてすべての活動が一つ持つ。** これが置き換える旧い基準 — 名前の付いたセクション、予算、
テンプレートを要するほど形が固定されているとき — は、常時の層がルーティングしていた頃に引かれたものである。
スキルは一度に一つだけロードされ、新しいものは自分が加わるメニューに対して秤にかけられていた。いま所属を
決めるのは、それをしている人が別のことをしているかどうかであって、生み出すものがテンプレートを持つかどうか
ではない。コードを書くことと issue を書くことは範囲を逆向きに壊すので、二つである。そしてテンプレートを
持たないほうが、落とされる側ではない。

## Before a skill is committed（スキルをコミットする前に）

**本文は予算に対して計測する。見積もらない。そして予算が属するのは、同時に立つ集合のほうであって、ファイル
ではない。** スキルはもう一度に一つずつ到着するわけではない：自分の上限の内側にあるファイルでも、その活動を
超過させうる。常時の層が最も厳しく抑えられる — 活動が何であれ常駐するからである。`SKILL.md` のベスト
プラクティスが、その数値とそれを計測するカウンタを担っている。非ゼロならまだコミットしてはならない。
