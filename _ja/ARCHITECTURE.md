# Architecture

## Bird's eye view（俯瞰）

誰かが読んで行動しなければならないテキストは、行動できるようになるまでに読み手にコストを払わせる。そして
書き手にはそのコストが感じられない — 自分の下書きは、そこに欠けている文脈を自分で補いながら読むからだ。
このプラグインはそこから導かれるルールを、参照されるのを待つのではなく**書いている現場に届く**形で梱包した
ものである：モデルが作業の途中に自分の判断でロードするスキルと、何かを書かせたい／チェックさせたいと自分で
決めた人が打つコマンド。

9つのスキルがルールを担い、6つのコマンドが人の打つ表面である。このファイルは、その形についての判断を何が
決めるか — 新しい部分をどこに置くか、それがどの文脈で走るか、何を持ってよいか — であり、9つを先に読まなく
ても判断できるようにするためのものである。

## Codemap（コードマップ）

| どこ | そこに属するもの |
|---|---|
| `commands/` | ユーザーに面する入口1つにつき1ファイル。instruction レイヤーの仕事：取得、質問、ブリーフの集約。人が起動すると決めるものすべて。 |
| `skills/<name>/` | スキル1つ。ロードされるのは `SKILL.md` であり、ディレクトリ内の他のすべては `SKILL.md` がそれを指しているから在る。他の経路では到達されない。 |
| `_ja/` | ツリーの一時的な日本語ミラー。著者がより速く読める言語で内容をレビューするためのもの。役目を終えたら削除する。ここから何もロードされない。 |

以下の見出しはすべて、貢献者が実際に直面する判断である。あなたの判断がここに無いなら、それはこのファイル
の穴であって、`skills/` にたまたま在るものから答えを帰納してよいという許可ではない。

## Cross-cutting concerns and invariants（横断的関心事と不変条件）

### The golden rule（ゴールデンルール）

**覚えておかねばならないルールは破られる。だから、それを性質にしてしまう仕掛けを作れ — そしてその仕掛けを、
誰かが取りに行かねばならない場所ではなく、書くことがすでに起きている場所に置け。**

以下のすべての判断はこれの一事例である。このファイルが名指ししていない新しい判断が現れたら、ここから導け：
何が覚えておくべきことになるのか、そしてどんな配置なら覚えておく必要がなくなるのかを問う。

### The invariants it generates（そこから生まれる不変条件）

**どのスキルも `/` メニューから到達できない。** ルールは、他の作業の途中で書かれるコードコメントに着地
しなければならない。名指しされたときだけ発火するものは、最も必要とされる瞬間を取り逃がす。だからメニューは
閉じられており、そこへ運ぶのはモデル起動である。

**成果物を書くスキルは、そこに至った会話を決して見ない。** `context: fork` は履歴を一切持ち込まない。それが
「この会話の参加者にしか再構成できないことを書くな」を、書き手が破りうるルールから、破れない性質へ変える。

**スキルは、その読み手には確認できないことを確認できてしまうツールを決して持たない。** 最も明快な例が
`review-nice-issues` で、その判定が意味を持つのは、実装者が手にするのと同じテキストだけから判断しているから
である。それ以上を与えれば、その判断は「使わないでおくことを誰かが覚えている限り」しか健全でなくなる。

**`_ja/` の外側の何ひとつ、その中身をロードも参照も依存もしない。** 何かが読むミラーは二つ目の信頼できる
情報源になり、そうなると正しくあり続けることが「覚えておくべきこと」になる。

### Out of scope（スコープ外）

意図的に存在しないもの。貢献者が一日かけて再発見せずに済むように：

- リポジトリ接地性、依存の閉包、スコープ、設計を判断するスキルは無い — それらはスキルを呼ぶ側に属する。
- 汎用の「このPRをレビューして」「この issue をレビューして」の入口になるスキルは無い。
- ツールチェーン、パッケージマネージャ、インストールパスを前提にしていない。コマンドを必要とするスキルは、
  走っているリポジトリからそれを読み出せと言う。
- 第二言語のキーワード列を持つ description は無い。公開されたスキルは利用者がどの言語で打つか知り得ない。
- child skill はここに同梱していない。`write-nice-skills` はその書き方を記述しているが、それはこのプラグイン
  が child skill を持っていることとは別である。

## Where a new entry point goes（新しい入口をどこに置くか）

**人がそれを起動すると決める → `commands/`。すでに進行中の作業に届かねばならない → スキル。**

上の不変条件を適用したものである。二つの経路は同じものの代替ではない。コマンドは、何かを書かせたい／
チェックさせたいと**自分で決めた**人が打つもの。スキルは、何も決めていない人に**届く**もの。

## What a command owes the skill it calls（コマンドが呼ぶ先に負うもの）

**未決着のものはすべてコマンドで決着させる。渡るのは一つのブリーフ。**

同じ依頼はいくつかの形で到着する — issue なら、内容がすでに書かれている／issue が存在して取得が要る／
そもそも issue が何であるべきかがまだ会話の途中。これを仕分けるのは実際の作業であり、そのすべてが会話で
ある：中途半端な依頼、取得した資料、持ち出されては捨てられた選択肢。

生の会話をそのままスキルに渡すコマンドは、その会話を**成果物が書かれる文脈**に入れてしまい、それは成果物に
表出する。先に一つにまとめることがそれを締め出す — そして `context: fork` が、それを「覚えておく」ではなく
構造にする。

## What context a skill runs in（スキルがどの文脈で走るか）

**ブリーフから成果物を生み出す → fork。すでにモデルの目の前にある作業に作用する → メインスレッド。**

この基準は逆向きにも効く。すでに目の前にある作業に作用するスキルを fork すると、それが作用する対象から
切り離される。ルーティングは目の前の作業を要る。書くことへの制約は、書くことが起きる場所で起きねばならない。
そしてレビューは findings を返すが、findings は根拠が付いていなければ何の価値もない — レビューを fork の
向こうに置けば、誰もそのレビューをレビューできない。

その基準で9つすべて：

| 走る場所 | スキル |
|---|---|
| fork | `write-nice-issue-description`、`write-nice-instructions`、`write-nice-skills`、`write-nice-architecture-docs` |
| メインスレッド | `dont-make-me-read`、`avoid-unverifiable-context`、`avoid-reference-detours`、`review-nice-issues`、`review-self-contained-docs` |

これが frontmatter を決める。ここのすべてのスキル：

```yaml
user-invocable: false
disable-model-invocation: false
```

fork はこれを足す：

```yaml
context: fork
background: false
```

`background: false` は、呼び出し元が同じターンで結果を見せるから。`agent` と `model` は未設定のままに
する：どちらも fork を**情報収集**の実行が必要とするものまで狭めてしまい、読み取り専用のツールセットでは、
その fork が生み出すために存在する成果物を書けない。

## What tools a skill gets（スキルがどのツールを持つか）

**自分の仕事が必要とするもの — ただし、その読み手には確認できないことを確認できてしまうものを引いた残り。**

見落としやすいのは引き算のほうである。`review-nice-issues` は、そのテキストだけを手にしている実装者と同じ
やり方で issue 本文を判断する。だから `allowed-tools: []` は倹約ではない。その足場を構造にしたものである。
「便利だから」と `gh` を与えれば、その判定を意味あるものにしている唯一の性質が消える。だから取得は、それを
呼ぶ側に属する。

その引き算が当てはまらない場合、スキルは仕事が必要とするものを取る — `review-self-contained-docs` は、
判断する対象のプルリクエストを読む。

## Where an explanation goes（説明をどこに置くか）

**誰がそれを抱えねばならないか、そしてどれだけの頻度でか、で決まる。**

| その説明が | 置き場所 |
|---|---|
| 貢献者が判断に使うもの | ここ |
| スキルのすべての経路が必要とするもの | そのスキルの本文 |
| 一部の枝しか到達しないもの | そのスキルの `SKILL.md` の隣にあり、そこから指されているファイル |
| フィールドの意味 | frontmatter のどこでもない |

frontmatter は `SKILL.md` の中で唯一、読まれるのではなくパースされる部分であり、その全体が発火のたびに
ロードされる。そこに付けた末尾の `#` は、それで混乱したはずのない読み手に何も説明せず、すべての読み手が
永遠にそのコストを払う — 枝固有の詳細を本文が指すファイルへ押し下げるのと同じ議論が、一段上に当てはまって
いるだけである。

## When an artifact earns rules of its own（成果物が固有ルールを持つのはいつか）

**その形が、一般則では供給できないほど固定されているとき：名前の付いたセクション、予算、テンプレート。**

たいていの書き物にはそんな形がない — コードコメント、コミットメッセージ、PR説明文。それらは
`dont-make-me-read` のテストと二つの `avoid-*` スキルで足りる。この二つがここで最も広いトリガーを持つのは
そのためである。

issue 本文、レビュー指摘、`SKILL.md`、アーキテクチャドキュメントの4つはその基準を超え、それぞれ一つの
`write-*` スキルを得た。その基準を超えていない成果物にスキルを足すと、判断すべき description がもう一つ
増えた重みを以後のすべてのターンが払う。

## What to do when a body is over budget（本文が予算を超えたとき何をするか）

**一部の枝しか到達しないものを、その `SKILL.md` の隣のファイルへ押し出す。通るまで。**

```bash
bash skills/write-nice-skills/scripts/count-tokens.sh skills/*/SKILL.md
```

非ゼロなら、まだコミットしない。どのコードが何を意味するかはスクリプト自身のヘッダにあり、そのうち予算に
ついてのものは一つだけである — 残りはチェックが走らなかったことを言っており、それは合格ではない。
本文が指すものには深さのルールがありサイズのルールはないので、材料は削除されるのではなく、発火のたびに
全員が払う経路から外へ移されるだけである。

それらのファイルが取る名前はここでは決めない。決めるものが何も無いからである：補助ファイルは `SKILL.md`
から参照されることで見つかり、プラットフォームはディレクトリも命名も要求しない。`references/`、`rules/`、
`scripts/`、`assets/` は、このツリーがたまたま使っているものである。合う隣人があればそれに合わせ、無ければ
読める名前を選べ — どちらの選択も、このファイルがあなたの代わりに決める筋合いのものではない。
