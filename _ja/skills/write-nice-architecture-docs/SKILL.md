## Overview（概要）

このスキルは、貢献者が実装を閉じたまま、そのドキュメントが見たことのない判断を決着させられるように、
アーキテクチャドキュメントを書き、改稿する。アーキテクチャドキュメントは「ここではこれをどう判断するのか」
に対する恒常的な答えであり、それを書いた者がもう捕まらなくなってから長く読まれ、案内される側ではなく
**足す側**の読み手に読まれる。

## How to work（どう進めるか）

- **一行書く前に、そのドキュメントがどの判断を置かねばならないかを決着させる。** 貢献者は一つの問いを持って
  到着する。誰の問いにも答えない節は、誰も読まない節である。
- **どの行も実装を閉じたまま判断する。** あなたはたった今コードを読んだが、読み手は読んでいない。その差が
  失敗の様式そのものである。
- **レビューのときは、落ちた条件を名前で呼ぶ。** 指摘が「長い」ではなく、どの条件かを言えるように。
- **依存は目視せず、引く。** 草稿に `find-document-dependencies` をかけること。このファイルへ刺さって
  くる矢印は、すべてここでの指摘である。

## The test（テスト）

`dont-make-me-read` のテストを、この成果物の粒度で：

> **読み手は、実装を閉じたまま、これだけで自分の判断を決着させられるか？**

コードはすでに、そこに何があるかを示している。git はすでに、それがいつ変わったかを示している。どちらも
示さないのは、**次の判断を何が決めるか**である。だから現状の形を語る節には読み手がいない — その中身はすべて、
別のどこかでもっと速く手に入る。

同じテストを保守の側から見たもの：**このファイルに修正を義務づけるものが一つもあってはならない。**
依存を矢印で書き — A → B は「A を直せば B も直さねばならない」を意味する — このファイルが乗っている矢印は
すべてこのファイルから出ていかねばならない：このファイルが動けばツリーが従い、その逆はない。矢印の出所が
コードであれ別のドキュメントであれ関係ない。刺さってくる矢印は、このファイルを、それが統べているはずの
ものの下流に置いたということであり、そこでは沈黙のうちに腐り、それを信じた貢献者は誰かが気づくより先に
置き場所を間違えている。

## What the doc owes its reader（ドキュメントが読み手に負うもの）

この順序で。セクションは matklad のものである（Alex Kladov, `ARCHITECTURE.md`, 2021）。

| セクション | そこに入るもの |
|---|---|
| **Bird's eye view（俯瞰）** | そのプロジェクトが解いている問題。構造の話より先に。数行。 |
| **Codemap（コードマップ）** | 粗い粒度のモジュールと、その関係 — 「一国の地図であって、各州の地図を集めた地図帳ではない」。**Xをやるものはどこか**、**今見ているものは何をするのか**に答える。 |
| **Cross-cutting concerns and invariants（横断的関心事と不変条件）** | モジュールをまたいで成立するもの、そして層とシステムのあいだの境界。他の二つに散らすのではなく、独立した節として。 |

コードマップを書くことは、コードの物理構造と論理アーキテクチャが乖離していることに気づく、最も安い機会でも
ある。

## The rules（規則）

それらのセクションを**どう書くか**についての条件。一つ一つが、指摘で名指しできるものである。

### 短く保ち、頻繁には変わらないものだけを書く

恒常的な貢献者は全員これを読む。コードと同期させ続けようとしないこと。年に数回見直す。

基準が理由を伴うのは、その理由が、基準だけでは置けない事例を置くときだけである。ルールを述べたうえで
それを説明するのが、この種のファイルが長くなる経路であり、長さそれ自体が失敗である：読み手は一つの判断の
ために来て、あなたを納得させた議論の代金を払わされる。残るすべての文が誰かの次の一手を変えるまで圧縮せよ。

### 役割を名指しし、ツリーへリンクせず、外へ預けない

重要なファイル・モジュール・型は名前で挙げ、その中へリンクを張らない。リンクは腐り、腐ったリンクは読み手が
検索できる名前より悪い。名前は、意味のあるどんな改名も生き延びる。

役割を名指しし、実体を名指ししない。アーキテクチャ上の役割 — 入口、標準を保持するもの — は安定しており
名指しする価値がある。今それを満たしている実体はそうではない。名指しすれば、ツリーでの改名のたびに矢印が
このファイルへ刺さって戻ってくる。

本体を別のドキュメントに預けない。「残りは `README.md` にある」は、読み手が取りに来たものの代わりに往復を
手渡すことである。別のファイルの存在を読み手に知らせるために名前を挙げるのは構わない。目の前の文を完結
させるためにそこへ行かせるのは駄目である。短く保つとは、書く量を減らすことであって、貢献者が必要とする
ものを移設することではない。

### すべての節が、誰かが直面する判断を決着させる

部品からではなく、判断から始める。「これはどの層に属するか」「これは fork するか」「この入口はどこに住むか」
は判断である。「層とは何か」は記述であり、判断がそれを必要とするときに節を得る。

コードマップがこれを最も失いやすい節である：ディレクトリ一覧に一文ずつ添えたものは記述であり、各項目が
**そこに何が属するか**を述べた瞬間にコードマップになる。それが、読み手に古いものを見つけさせるだけでなく、
新しいファイルを置けるようにするものである。

**員数はこの失敗の最も純粋な形である。**「9つのモジュールが X をやり、6つが Y をやる」は何も決着させず、次に
誰かが一つ足した時点で誤りになり、権威を担っていないのに権威として読まれる。**どんな種別があり、何がその
どれかに置くのか**を述べよ。読み手は自分で数えられるし、その数は正しい。

### 不変条件は、それを生むルールで始める

その節の冒頭に来るのは**ゴールデンルール** — プロジェクトの他のすべての判断がそこから従う思想である。それが
無ければ読み手が手にするのは「従うべき制約の一覧」でしかなく、それがあれば**誰も書き留めなかった制約を自分で
導ける**。ファイルの中で最もレバレッジの高い一文であり、不変条件は、それが何の一事例なのかを読み手が
見られるとき、はるかに価値が高い。

そのうえで不変条件そのものを書く。**不変条件はしばしば「不在」として表現される**のであり、それを述べることが
このファイルで最も価値の高い部分である — 不在こそ、コードをいくら読んでも明らかにならないものだからだ。それは Don'ts で組み立てられたドキュメントとは別物であり、違いはテストできる：

> **それは、このドキュメントが見たことのない事例を置けるか？**

- 「どの層も、その上の層からインポートしない」は不在であり、かつ基準である：まだ誰も書いていないモジュールも
  含めて、新しいものがどこへ行くかを決着させる。
- 「パーサは型チェッカを呼ばない」は不在であり、基準では**ない**：存在する二つのモジュールについての一つの
  事実であって、三つ目については何も決着させない。

二つ目は、それが事例であったところのルールへ引き上げれば一つ目になる。

### 慣習は不変条件ではない

それを不変条件として書き留めることは、誰も課していない制約を製造することである。ルールを述べる前に、それを破った人に何が起きるかを問え。答えが「何も起きない — みんなそうしているだけ、
例示がそうだったから」なら、それは習慣である。習慣だと言うか、何も言わないかにせよ。習慣をルールへ昇格させた
ドキュメントは、読み手が自由に決めてよかったことを代わりに決めるために読み手の信頼を使い、以後のすべての
貢献者が負う必要のなかった判断を払う。その下にある本当の要件はたいてい一文の距離にあり、そちらを述べる価値が
ある — プラットフォームが実際に強制していること、あるいはこのプロジェクトが実際にそれ無しでは壊れること。

### 拒否にはリストを与える。節は与えない

不在を引き上げられない場合、それが取ってよい水準は「リスト」であって「節」ではない。フラットな *out of scope*
のリストは行数の価値がある：そのプロジェクトが意図的に何をしないかを貢献者に伝え、それこそ彼らがさもなければ
一日かけて再発見する不在だからである。同じ内容を章に変えたときに失敗する。章は本来そこに基準があるべき場所
であり、目次を読んだ読み手は、拒否によって定義されたプロジェクトを見ることになる。

つまり：**単一の拒否に独立した節を与えない**。フラットなリスト一つに見出し一つ、それが許される水準であり、
残る見出しはゴールデンルールと不変条件のものである。否定形の見出しを数えるのが安いチェックである。

### 分類は、分類すると宣言した対象をすべて覆う

ドキュメントが存在するものを分割するとき — 層、種類、カテゴリ — 既存のすべてがちょうど一つのバケツに
着地し、読み手は同じ分割で新しいものを置ける。

8つのうち3つを挙げる表は、その分割が信頼できないことを読み手に教え、彼らはそれを判断に使うのをやめる。
全部になるまで広げるか、主張するものを狭めるかのどちらか：**3つの例**の表は誠実で有用である。**その層**
として提示された表は、全部を持たない限りそうではない。

### 判断が必要とするものを言い直す。他のファイルが所有する定義を導き直さない

終了コードは、それを返すスクリプトのものである。frontmatter のフィールドは、それをパースするプラット
フォームのものである。何が存在するかの一覧は、それを収めるディレクトリのものである。そして成果物が内部で
どう配置されるかは、その成果物自身のルールのものである — どの成果物がルールを持つかを述べたドキュメントは、
すでに十分述べ終えている。

繰り返してよいかは `avoid-reference-detours` がすでに決着させている：**この読み手が行動するために必要な
部分**を、その仕事を果たす最短の形で持ってくること。ここが狭めるのは**どの部分か**である：

| | 持ってくるもの |
|---|---|
| 読み手が今何かを決めねばならない | それを決着させる部分 —「非ゼロならまだコミットしない」 |
| 他のファイルがその物を定義している | 列挙ではなく実体の名前 — どのコードが何を意味するかはスクリプト自身のヘッダにある |

向きのテストを定義に絞ったもの：**そのファイルが変わったとき、このドキュメントは誤りになるか？**
なるなら、定義をコピーしている。
ならないなら、入力を言い直している。コピーした定義は、リンクとまったく同じように腐る。

### 部品ではなく判断で索引する

それらのセクションの内部では、貢献者が走査するのは見出しであり、彼らは一つの問いを持って到着する。

このファイルはリポジトリを変更する誰にとっても必須経路に座る。だから上限がかかるのは**彼らが来た判断までの
距離**であり、それこそ「短く保つ」が守っているものである。見出しが判断になっているファイルは育っても安い
ままだが、端から端まで読まねばならないファイルはそうならない。

## Common Rationalizations（よくある自己正当化）

| 自己正当化 | 実際のところ |
|---|---|
| 「ここは全部この配置なのだから、それが慣習だ。書き留めておこう。」 | 誰かが違うやり方をしたとき何が壊れるかを問え。正直な答えが「何も」なら、あなたは習慣をルールに変えようとしている。そして次の貢献者は、あなたが書き写しながら発明したものに従うために本物の思考を費やす。その下にある要件を述べるか、選択を元の場所に置いておけ。 |
| 「それは README に書いてあるから、そこを指しておく。」 | すると読み手はここに来て、追い返され、往復を払って戻ってくる。短さは書く量を減らして達成するものであって、貢献者が取りに来たものを移設して達成するものではない。判断が必要とする部分を持ってきて、他のファイルはその存在を知らせるためだけに名前で挙げよ。 |
| 「今どうしているかを説明することがアーキテクチャだ。」 | 今どうしているかはコードが示している。より速く、ドリフトもなく。コードが示せないのは不変条件と、次の判断を何が決めるかである — このファイルが足すものはそれだけだ。 |
| 「拒否するものごとに節を立てるのは、境界について誠実だ。」 | 拒否でできた目次は、そのプロジェクトが何をしないかを読み手に伝え、何をするかについては何も伝えない。拒否はフラットな out of scope のリストに与えよ — 安く、本当に有用である。見出しは、それらを生むルールのために取っておけ。 |
| 「禁止こそが本体で、基準は自明だ。」 | それが自明なのは**あなた**にとってである。あなたはそれを導いた基準をすでに持っている。読み手が受け取るのは、閉じられた一つの経路と地図のない空間である。それが事例であったところのルールへ引き上げ、そのルールが未見の事例を置けるか確認せよ。 |
| 「matklad は意図的な不在を明示せよと言っているのだから、不在の一覧がこのドキュメントだ。」 | 彼が言っているのは**不変条件はしばしば不在である**であって、不在は常に不変条件である、ではない。「どの層も上へインポートしない」はすべてを置く。「パーサは型チェッカを呼ばない」は何も置かない。両方残してよいが、節を担えるのは前者だけである。 |
| 「この表は面白いケースだけを挙げている。」 | ならそう表自身の言葉で言うこと。分類として提示された部分的な表は、何も置けないことを読み手に教える — 彼らが置きに来たものも含めて。 |
| 「モジュールにリンクを張るほうが親切だ。」 | それが移動するまでは。名前は改名を生き延び、検索が見つける。リンクは、一年誰も気づかない嘘になる。名前で挙げよ。 |
| 「代替案ではなくこちらを選んだ理由を記録するのは有用な経緯だ。」 | 根拠は残り、審議は落ちる（`avoid-unverifiable-context`）。代替案を排除する制約を、読み手がぶつかることになる壁として書け。二人でそれを天秤にかけた顛末ではなく。 |
| 「自分には問題なく読める。」 | あなたはすでに持っている基準を自分で補っている。このファイルを開き、実装を閉じている誰かとして判断せよ — それこそが失敗モードのすべてである。 |

## Red Flags（危険信号）

- 現在の形を語るだけの節 — コードのほうが速く示す。
- そのドキュメントが見たことのない事例を何も置けない invariant。
- 主題がプロジェクトの拒否であるような見出し。
- ツリーへのリンク — 名前であれば改名を生き延びたところで。
- それを所有するファイルから導き直された定義。
- 覆うと称する分類のどれにも当てはまらない事例がある分類。

## Verification（検証）

- [ ] どの節も、実装を閉じたまま、誰かが直面する判断を決着させている。
- [ ] どの invariant も、それを生成する規則を先頭に置いている。
- [ ] ここに書かれたものは、記述対象のファイルが言い換えられても誤りにならない。
