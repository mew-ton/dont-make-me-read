## Why this exists（なぜこれが存在するか）

二つの命題。このプラグインのすべてのルールはここから導かれる。

1. **何をすればいいか把握するために大量のテキストを読みたい人間はいない。** 美しいテキストでも、
   網羅的なテキストでも、丁寧なテキストでも同じ。
2. **書き手にはその量が分からない。** 自分の下書きは、そこに欠けている文脈を自分で補いながら読むことに
   なる。だから自分にとっては短く読める — 自分にとってだけ。

二つ目が、これらが助言ではなくスキルである理由であり、そのうち二つが**すでに書いたテキストに対して
走らせるためだけに**存在する理由である。

## Who the reader is（読み手は誰か）

人間かエージェント、常に両方。長く散らばった指示を集めて保持することは、どちらにもコストを課すし、
どちらも最終的に手元に残ったものに基づいて行動する。だからここにあるものは、片方だけのために書かれて
いない。

両者は同じようには失敗せず、それは下書きを判断するあいだ心に留めておく価値がある。**たまたまサンプル
したパスの一覧**は、人間には「少なくともこれら、おそらく似た他のものも」と読める。コーディング
エージェントはそれを**触るべき完全な集合**として受け取り、そこで止まる。同じテキスト、同じノイズ、
二つの異なる誤った判断。

このセットの中のスキルが片方を名指ししているとき — `write-nice-instructions` は人間の読み手で予算を
決め、`write-nice-skills` はファイルをロードするか判断するエージェントで決める — それは、その成果物に
とってどちらの読み手が**基準を決める**かを言っているのであって、どちらが読者かを言っているのではない。

## The test（テスト）

あらゆる粒度で — 単語、文、節、ファイル：

> **これは読み手が次に取る行動を変えるか？**

変えない：削る。変える、かつ欠けている：足す。短くすることも長くすることも、どちらも結果であって
目的ではない。

ノイズが払わせるのは読む時間ではない。**自信を持って下される誤った判断**である：

| ノイズ | 読み手が導く結論 |
|---|---|
| 自分で重みづけできたはずの修正のメニュー | 選択は自分のものだ — 書き手より少ない情報で決めることになる |
| たまたまサンプルしたパスを、修正として提示したもの | それらのファイルが触るべき完全な集合である |
| 「適切に処理すること」 | 仕様は完全である |
| issue に書かれた実装方法 | 書き手が見た形が、今日もまだその形である |

## What must never be cut（決して削ってはならないもの）

判断が依存していて、かつ読み手が再構成できないもの：

- 仕様や設計の背後にある根拠 — ビジネス要件、規制、ドメイン制約、プロダクト上の決定
- 明白な誤った動きを排除する制約。読み手に差し出される選択肢としてではなく、彼らがぶつかることに
  なる壁として述べたもの
- そもそもその依頼を擁護可能にする事実

これらのどれかを削ってもテキストは引き締まらない。判断材料の少ない誰かに判断を押し付けるだけであり、
それこそこのセット全体が防ごうとしている失敗である。読むのにコストがかかり、かつ判断がそれを必要と
する行は、残す。

## Where the length cap applies（長さの上限がどこに適用されるか）

**何をすべきか知るために読み手が必ず通る経路にだけ**適用される。裏付け資料は必要な者が取りに行くもので、
上限はない。

| | 上限 | 理由 |
|---|---|---|
| 必須経路 | あり | 全員が毎回それを払う |
| 裏付け資料 — 実例、証拠、ポインタの指す先の原典 | なし | それを必要とする読み手だけが払う |

だからレビュー指摘の details は 20 行に制限される一方、コードブロック内の証拠は制限されない。だから
スキルの `references/` には深さのルールがあり、サイズのルールはない。

## Which skill owns what（どのスキルが何を所有するか）

これが該当するもののほとんどはテンプレートを持たず、必要ともしない — 説明的なコードコメント、JSDoc
ブロック、PR説明文、コミットメッセージ。それらについては上記のテストと、二つの失敗モードで全部で
ある：

- `avoid-unverifiable-context` — 読み手が確認しに行けないものをテキストが担っている。
- `avoid-reference-detours` — 理解されるために、テキストが読み手を到達可能などこかへ送っている。

どちらもその成果物が何であれ成立するので、下記のすべての上にも重ねて適用される。

いくつかの成果物は、固有のルールを持つに足る固定された形を持っている。合致するものをロードすること。
このスキルはテストを持つのであって、それらのルールを持つのではない。

| 書くもの | Skill |
|---|---|
| GitHub issue 本文 | `write-nice-issue-description` |
| PRレビュー指摘、または人に何を変えるか伝えるあらゆるコメント | `write-nice-instructions` |
| `SKILL.md` | `write-nice-skills` |
| 設計ドキュメント — `DESIGN.md`、ADR、アーキテクチャノート | `write-nice-design-md` |

| すでに書かれたものをチェックする | Skill |
|---|---|
| issue 本文 | `review-nice-issues` |
| PRの説明文と、その差分が変更するすべてのコメント | `review-self-contained-docs` |

## Common Rationalizations（よくある自己正当化）

| 自己正当化 | 実際のところ |
|---|---|
| 「原則は分かったから、あのスキルをロードせずに issue を書ける。」 | 原則はセクション一覧も予算もゲートも運んでいない。何を狙うかは言うが、成果物が何を含まねばならないかは決して言わない。これをロードすることは、あれをロードすることの代わりにはならない。 |
| 「短いほうが良いのだから、削る。」 | 短さは結果であって目的ではない。判断がそれに依存する行は、読むのにどれだけコストがかかろうと残る。 |
| 「文脈は多いほうが安全だ。」 | 判断が使わない文脈こそが、読み手を誤ったことについて自信満々にさせる。安全は上の二つ目のリストであって、量ではない。 |
| 「自分には問題なく読める。」 | あなたは読みながら、テキストに欠けている意図を自分で補っている。テキストだけを手にしている人間として判断せよ — それこそが失敗モードのすべてである。 |
