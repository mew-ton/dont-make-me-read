# この規則がどこに座り、隣に何が座っているのか

このファイルを指すものは何も無く、指すべきでもない：これはスキルを保守する者に向けた近隣関係と設計上の論拠
であって、issue を書くエージェントがロードしなければならない材料ではない。ここに置くことで本文の外に出せる。
本文にあれば、issue を書きたいだけの読み手全員が代金を払うことになる。

## 近隣のスキルとの関係

本文はもうこれらのどれも名指ししない。近隣の一覧は著者が次にすることを何も変えず、どの名前も、何も検査され
ない他人のファイルへの依存だった。次にこのスキルを編集する者のために記録しておく。

- `review-nice-issues` — すでに起草された issue 本文を、同じゲートに照らして、読み手の目線から監査する。
  このスキルはあのスキルが始まるところで終わる。だから description の境界が監査のモードを取り戻しており、
  routing の表が「読み手の目を通す作業はこのスキルを呼んだ側に属する」と述べている。
- `write-nice-instructions-as-comment` — 一人の読み手が読んで答え返せるテキストのための、指摘／指示の
  テンプレートと remedy strength。あちらの description がすでに issue 本文を取り戻しているので、こちらは
  レビューコメントを除外するために文字を費やさない。
- `dont-make-me-read` の `rules/unverifiable-context.md` — あとから読まれるあらゆるテキストにまたがる、根拠 vs プロセスのルール。
  「実装者がすでに持っているもの」はそのルールを issue の粒度にしたものである：読み手はリポジトリを読める
  のでプロジェクトの文脈は落ち、読み手は参加者ではなかったのでセッションの残滓も落ちる。
- `dont-make-me-read` の `rules/reference-detours.md` — 文書をまたぐ場合の同じ引き算。Gate 2 が一つの文書の内部の繰り返しを覆う。
  読み手は issue を順に読むので二つ目の写しは再読であり、別ファイルに置かれた事実は往復の代金になる。
  Gate 1 の参照ルールが両者の交わる点である：次の行動がそれを解決せずに決まるなら、参照は残ってよい。
- `dont-make-me-read` — Gate 1 の下にあるテスト、issue 本文の粒度で：このテキストとリポジトリだけを持つ
  実装者が、着手でき、いつ終わったかを言える。

## description の他の二つの境界が落ちた理由

書き直した description は境界を一つ残し、二つ落としている。

- 「成果物が PR レビューの指摘であるとき」— GitHub issue の本文を名指しする機会がレビューコメントに届いた
  ことはない。だからこの節は、費やした文字を一つも取り戻していなかった。
- 「問題が永続ドキュメント一般の rationale と process の切り分けであるとき」— スキル名を抜いたルーティング
  表であり、機会が巻き込まない隣人を指していた。

生き残ったのは監査のモードである。「改稿する」はすでに書かれた issue に本当に届いており、その場合は別の
スキルの入口だからである。

## テンプレートが規則を持たない理由

テンプレートはかつて、HTML コメントの中で `SKILL.md` と `references/sections.md` のほぼすべての規則を言い
直していた — 三つ目の写しであり、著者が、それを所有するファイルを開く代わりに問いを決着させてしまうもので
ある。いまは骨組みである：見出し、空欄、そしてどの枠を落としてよいかを述べた注記。その注記が残るのは、この
スキル自身の原則が「存在するセクションは埋められる」なので、骨組みの側がどの見出しが任意かを言わねばならない
からである。
