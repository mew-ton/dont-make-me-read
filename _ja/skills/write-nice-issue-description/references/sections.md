# セクションを埋める

セクションを書く前に読むこと。`SKILL.md` は各セクションが何のためのものかを担う。ここはそれぞれを正しく
仕上げるためのルールと、失敗を示す対比を担う。ゲートの実例と通過する issue 本文の全体像は
[`examples.md`](examples.md) にある。

## Contents

- Background / Why
- Goal
- Acceptance criteria
- Affected areas
- Dependencies

## Background / Why

問題を構成する事実を書く。各文をテストせよ：それがなければ issue の必要性は成立しなくなるか？ その事実が
コードを読めば導けるかどうかはテストではない — **既存の振る舞いそのものが問題である**ときに書き、既存の
振る舞いが修正への手がかりにすぎないときは省く（所在は Affected areas の括弧書きで足りる）。

- 書く（問題）：「`GET /v1/foo/{id}` は、foo が削除されたのか、一度も公開されていないのか、クローズ
  されたのかにかかわらず同じ 404 を返し、理由を区別しない。」
- 省く（手がかり）：「メッセージング機能には、何かが非公開のときに代替ビューを出す構造がすでにある。」

制約が Acceptance criteria に置かれるときは、その根拠をここに、**問題として**書く。

- 「クローズされた求人を一時的な取得エラーと同じに扱うと、復旧時に再び見えるようになった後でも、読み手に
  その求人が『クローズ』したと伝えることになる。」

文の主語はドメインの実体に置く — issue 番号や「このタスク」ではない。issue がクローズした後も真であり
続ける文だけを書く。

- 書かない：「#1784 が記事本文の求人リンクを4状態のビューモデルにする。」
- 書く：「記事内に表示される求人カードは、クローズ／求人が存在しない／取得失敗、のいずれかの状態を
  取りうる。」

ある文が対象とするドメインの実体それ自体が文書やコードである場合、**そのパスがドメインの実体である** —
それを説明する散文ではなく、パスを主語として書く。説明は読み手にどのファイルのことかを解決させる。パスは
すでに解決済みである。

- 書かない：「バックエンドのレイヤー境界ルール文書は循環依存を禁止している。」
- 書く：「`.claude/rules/backend/` 配下のルールは循環依存を禁止している。」

これはその実体についての**既存の事実**を述べているのであって、見に行けという指示ではない。答えを見つける
ためにどのファイルを開けと読み手に伝えるのは別のことであり、それは実装ステップである
（[`SKILL.md`](../SKILL.md) の Decision vs. choice を参照）。そしてこれは issue の生存期間中その場に
留まる実体 — 恒常的なルール集、スキーマ、規約文書 — にのみ当てはまる。修正がコードのどこに着地するかの
推測ではない。その推測は Affected areas の仕事であり、そのパスは作業開始前に動くことが想定されている。

唯一の例外はスコープ文で、そこでは issue 自身が主語になってよい — この issue が何を所有し、後続が何を
所有するかを宣言する。

- 「このタスクはバックエンドの 410 経路と、ビューモデルの型・リゾルバを扱う。レンダリング
  コンポーネント側の追随は #1851 のもの。」

箇条書きが複数**種類**の問題にまたがるときは、フラットのままにしない。テストは箇条書きが何種類の問題に
仕分けられるかである。1種類ならフラットのまま（上のすべての例がそうである）。2種類以上なら、問題ごとに
1つの見出しに分け、それぞれの内部はフラットにする。

単一の箇条書きがそれ単体で問題として読めるかどうかは、そのテストではない。一つの問題に属する箇条書きは、
単体では成立しないことがよくある — それはその問題を共同で構成するいくつかの事実のうちの一つである。
分割を決めるのは、箇条書きが**いくつの別個の問題に属するか**であって、どれか一つが自足しているかでは
ない。

分割するときは、なぜ一つの issue がすべての問題を束ねているのかを述べる一文で始め、それから問題ごとに
1つの見出しを置く。その一文が書けないなら、それらの問題は一つの issue に属していない — 単一の Background
を章立てするのではなく、別々の issue に分割せよ。章立てが必要なことは、その issue が実は二つであるという
**症状**であって、構造を足して直すべきものではない。

冒頭の文は一文のままにする。例や正当化を付け足さない（Gate 2 の段落圧縮ルール、[`SKILL.md`](../SKILL.md)）。

**表組みは章立てとは別の軸**であり、二つは自由に組み合わさる。章立ては「この issue が何種類の問題を
抱えているか」を問い、表組みは「**一つの**種類の問題がいくつの要件を抱えているか」を問う。それぞれが
固有の現状と要求状態を持つ。そうした要件が複数あるとき、要件ごとに一文を書くのは Gate 2 の段落圧縮
ルールがそのまま箇条書きに広がっただけである — 表に置き換えよ（空の列、`Actual`、`Requirement`、要件ごと
に1行。[`examples.md`](examples.md) を参照）。要件が一つだけなら文のままにする。表は文以上のものを
何も買わない。章の内部の要件をさらに表組みしてもよい。

## Goal

**何に準拠するか**を指す：標準のセマンティクス、既存実装、スクリーンショット、コピー表。

Goal を自分の説明として書かない — 「〜に準拠する」が取りうる最も強い形である。

- 「メッセージング機能の求人カードの見た目に準拠する」（既存実装＋スクリーンショット＋コピー表）
- 「404 / 410 のセマンティクスは RFC 9110 に準拠する」（標準）

Goal は、最後の lint／型チェック／テストの項目を除く**すべての** Acceptance criteria 項目をカバーする —
その項目は作業がどう検証されるかであって、準拠する対象ではない。Goal が指していない何かに他の項目が
準拠しているなら、その issue は複数の問題を束ねている — 分割せよ。

Goal に検証手段を置かない。実行可能な検証コマンドは Acceptance criteria の最後の項目に属し、ここでは
ない。

- 書かない（Goal）：「アーキテクチャ lint が強制する `architecture.md` に準拠する。」
- 書く（Goal、準拠だけ）：「`architecture.md` が述べる構造に準拠する。」
- 書く（Acceptance criteria、検証）：「アーキテクチャ lint が通る」— このリポジトリが実際に走らせる
  コマンドを名指しして。

## Acceptance criteria

チェックボックスとして書く。

**実装の詳細を書かない** — 確認すべきファイル名や番号、内部フィールド名やスキーマの語彙。ドメイン自身の
語彙で書く。

- 書かない：「`published_version_id` は設定されているが、指す先のバージョンが非公開 → 410 を返す。」
- 書く：「過去に公開され、現在は非公開になっている場合に 410 を返す。」

ある基準が「すべての」を要求するとき、その集合は**主語のパスが名指しするもの**そのものである — あるいは
Background が要件の表を述べているときは、その表そのもの（各行を個別のチェックボックスに展開し直すのでは
なく「上の表のすべての行が成立する」）。パスにも表にも裏付けられていない「すべての」はチェックできない。
それがどの集合を range しているのか誰にも分からないからだ。

- 書かない：「すべてのバックエンドのアーキテクチャ文書が同じ依存方向を述べている。」
- 書く：「`.claude/rules/backend/` と `backend/docs/` 配下のすべてのアーキテクチャ文書が同じ依存方向を
  述べている。」

実装が制限されなければならないときは、ここに**満たすべき状態**として、理由を付けずに書く（理由は
Background へ）。その制限が、消費側がすでに依存している形 — レスポンスのフィールド、`ViewModel` — で
あるときは、それを指す短い基準を書き、形そのものはここに独自のブロックとして与える。「選択」として省いて
しまうのでもなく、複数フィールドのインタフェースを1つのチェックボックス行に押し込むのでもなく。

lint / 型チェック / テストは最後の項目に、対象ディレクトリを名指しして置く。コマンドは**このリポジトリが
実際に走らせるもの**である — ツールチェーンを仮定するのではなく、そのリポジトリ自身のスクリプトや
ドキュメントから読み出すこと。

## Affected areas

執筆時点で怪しく見えるファイルパスを列挙する — 当て推量であって、考え抜かれた範囲ではない。

**スコープの境界ではない** — 「この辺が怪しそう」以上には持ち上げない、どこから始めるかの手がかりである。
作業が始まる頃にはファイルは移動、改名、消滅しているかもしれない。抜けがあるのは織り込み済み。網羅を
目指さないこと。推測の裏取りに時間を使わないこと — 裏を取るのは実装者の最初のステップであって、書き手の
仕事ではない。

括弧書きは**そこに何があるか**だけを名指しし、**それに対して何をするか**は決して書かない — 何をするかを
名指しした時点で、実装方法が忍び込んでいる。

- 書かない：`` `createFooResolver.ts` (add a preview flag) ``
- 書く：`` `path/to/types.ts` (an existing discriminated-union example is
  `FooResolution` in `_internals/foo/fooResolution.ts`) ``

何かが将来どこへ移るかを述べる注記は、**あるもの**を装った**すべきこと**である — それは読み手を観察では
なく計画に縛り付ける。

- 書かない：`` `.claude/skills/` (where layer-specific implementation patterns get split out to) ``
- 書く：`` `.claude/skills/` (existing layer-specific implementation-pattern docs live here) ``

## Dependencies

**着手を妨げる**依存だけを書く。推測で置かない。

後続タスクは依存ではない — それは Background のスコープ文に属する。着手を妨げるものが何もなければ、
このセクションはまるごと落とす。
