# 既存の下書きを改稿する

issue がすでに存在するときに読むこと — 自分の下書きでも、締め直そうとしている他人の issue でも。改稿は
起草とは別のパスである。何を書くかを決めるのではなく、下書きが**すでに含んでいる、あってはならないもの**を
狩り出す作業であり、だから固有の順序を持つ。手順は順番に進めること。

1. Background の各文をテストする：それがなければ issue の必要性は成立しなくなるか？ 通ってしまうものを
   削除する。残ったものについて、主語がドメインの実体であることを確認する（主語としての `#\d+` や
   「このタスク」にフラグを立てる — スコープ文が唯一の例外。文書やコード自体を名指しするパスは可）
2. 残った箇条書きが何**種類**の問題に仕分けられるか確認する。2種類以上：問題ごとに1つの見出しに分割し、
   一文の冒頭理由を置く。その一文が書けない？ 別々の issue に分割する
3. Gate 1 を適用する：実装方法の記述を見つけ、コードベースの現在の構造に依存するものを落とす。issue の
   外側から来る制約だけを Acceptance criteria に移し、その根拠を Background に**問題として**書き込む
4. Acceptance criteria から内部フィールド名とスキーマの語彙を剥がし、ドメインの語彙に置き換える
5. Acceptance criteria の各項目について、それが解決する問題を Background が述べていることを確認する。
   対応する問題のない項目は、理由の述べられていない作業を実装者に求めている
6. Affected areas の括弧書きに「何をするか」の言い回しがないか確認する — 将来の配置に関する注記も含む —
   そして落とすか、「そこに何があるか」に置き換える
7. Gate 2 を適用する：内容にすでに行き先があるセクションをどこであれ落とす。後ろの文が最初の文を言い直して
   いるだけの段落を圧縮する
8. Goal が Acceptance criteria を言い直していないか確認する。していれば、何に準拠するかを指すポインタに
   置き換える
9. Goal が Acceptance criteria の全項目をカバーしているか確認する。Goal が届かない項目は、この issue に
   束ねられた二つ目の問題である — 切り出す
10. 下書きが一つの言語で書かれているか確認する — このリポジトリの issue がすでに使っている言語で —
    同じ内容の第二言語による言い直しがないこと（Gate 2）
