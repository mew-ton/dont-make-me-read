## Scope（範囲）

issue は設計文書ではない。**問題の記述＋完了条件**である。新規起草でも既存改稿でも、issue 本文
1つにつき1回適用する。

読み手は実装者であり、彼らはリポジトリを読める。だからこの issue は、`avoid-reference-detours` が
残り続けるテキスト一般に求めるようにプロジェクトの文脈を説明する必要はない — 散文で説明するくらいなら
場所を指すだけで十分であり、それを説明する散文は issue を膨らませ、かつ実装者自身の判断を侵食する。

`avoid-unverifiable-context` が防ぐものは全面的に適用され続ける：会話ログなし、捨てた代替案なし、この
セッションの参加者にしか再構成できない残滓なし。プロジェクト文脈の説明を落とすことは、セッション／
プロセスの文脈を呼び戻す許可ではない。むしろ issue こそがその文脈を最も許容しない場所である。読み手は
決して参加者ではないからだ。

以下の二つのゲートがすべてのセクションを統べる。

## Language（言語）

issue は、その実装者がすでに読んでいる言語で書く — リポジトリの言語、その既存 issue の言語、コード
レビューの言語。以下の二つのゲートはどちらも issue の**形**についてのものであり、セクション、二つの
ゲート、テンプレートは、どの言語で書こうと同じように適用される。ここの実例が英語なのはこのスキルが
英語だからであって、issue を英語で立てろという要求ではない。

**1つの issue、1つの言語。** 同じ内容の第二言語による言い直しは Gate 2 の重複であって、アクセシビリティ
ではない — Gate 2 の例外を参照。あれは**提示形式の違い**をカバーするものであって、言語の違いではない。

## Gate 1: determinacy（確定性）

目の前に書かれていること以上にファイルを読んだり `gh` を叩いたりできない読み手が、テキストだけから
以下を確定できなければならない：

- 解くべき問題
- 受け入れ基準
- スコープ外の境界

含まれないもの：**どのファイルを触るか**。Affected areas は執筆時点の当て推量にすぎない —
「この辺が怪しそう」以上に考え抜かれたものではない。作業が始まる頃にはファイルは移動、改名、消滅して
いるかもしれない。実際の範囲を確定できるのは、現在のリポジトリを読む実装者だけである。

**実装方法を書くな。**

### Decision vs. choice（決定 vs. 選択）

別の実装でも受け入れ基準を満たせるなら、それは**選択**である — 書くな。コードベースの現在の構造に依存
するものはすべて選択である。その構造は issue が書かれる時点では固定されていないからだ。

| 記述 | 分類 | 処理 |
|---|---|---|
| 既存コンポーネントを移動して再利用するか、新規に作るか | choice | 省く |
| 既存のi18nキーを再利用するか、新規に追加するか | choice | 省く |
| コンポーネントの props に何を渡すか | choice | 省く |
| 3値のunionで分岐するか、別フィールドの有無で分岐するか | choice | 省く |
| どのファイルの、どの行を確認するか | choice | 省く |

### When to write a constraint（制約を書くとき）

制約を書くのは、**実装が制限されなければならないとき**だけ。制約の根拠は issue そのものの外側にある —
標準のセマンティクス、既存のリポジトリ規約、性能要件、セキュリティ要件、他システムとの契約。

| 記述 | 分類 | 処理 |
|---|---|---|
| 410 の経路は既存の `GoneError` を再利用する | constraint（既存規約） | Acceptance criteria |
| バッチで解決できなかったIDだけが個別リトライを受ける | constraint（性能） | Acceptance criteria |
| 既存エンドポイントのエラーレスポンスは変わらない | constraint（既存契約） | Acceptance criteria |
| レスポンスの形（例：`ViewModel`）がこの issue より前の設計時点で確定していた | constraint（既存契約） | Acceptance criteria、形は独自ブロックに |

制約は**満たすべき状態**として、Acceptance criteria の中に書く。Affected areas には決して書かない —
Affected areas は当て推量であり、拘束力を持たない。

固定された形は、この issue の外側の何かがすでにそれに依存した瞬間に、選択ではなく制約になる — 消費側が
すでにそれに合わせて実装済み、あるいは先行する設計工程ですでに決着済み。それは基準として短く述べ
（「下記の形に準拠する」）、形そのものは Acceptance criteria の直下に独自のブロックとして与える。複数
フィールドのインタフェースを1つのチェックボックス行に畳み込んだり、それを収めるために
`Design / Approach` セクションに手を伸ばしたりしない。**その形は実装が生み出さねばならないもの** —
つまり Acceptance criteria 自身の内容 — であって、どう生み出すかではない。

制約の行に理由を付けてはならない。理由は問題であり、問題は Background に属する。制約の隣の理由はその行を
散文に戻し、散文こそ実装方法が忍び込む場所である。

判断を実装者に委ねたうえで、その理由づけだけ報告してほしいのなら、それは issue には属さない — 一般的な
レビュー規範であって、issue ごとの内容ではない。

### References（参照）

参照は、読み手がそれを解決してもしなくても次の行動が決まるように書く。

- 解決して初めて意味が通る参照：省く — `#1784 makes X return Y` は #1784 を開けない読み手を止めてしまう。
  その文の意味が #1784 に依存しているから。
- それ以上読むのを打ち切らせる参照：残す — `depends on #1784`。「ここから先はスコープ外」は開かずとも
  すでに決まっている。
- 裸の識別子：残す — `Refs #1558`。

## Gate 2: duplication（重複）

同じ内容を二箇所に書かない。削除ではなく**移動**で解決する — 内容にすでに行き先があるなら、セクションを
落とすだけで足りる。

| 重複 | 解決 |
|---|---|
| Out of scope が後続タスクの一覧を言い直している | Background のスコープ文に畳み込む |
| Out of scope が着手を妨げる依存を言い直している | Dependencies に畳み込む |
| Verification の内容が Acceptance criteria として表現可能 | Verification を落とす |
| Goal が Acceptance criteria を別の言葉で言い直している | 何に準拠するかを指すポインタに置き換える |
| Background の散文が、問題が何かではなく、どう解くかを説明している | その散文を落とす（所在は Affected areas の括弧書きに属する） |
| 同じ内容が二つの言語で書かれている | 一つの言語を残し、もう一方を落とす |

重複はセクション間だけでなく**一つの段落の中でも**起きる。最初の文が事実を述べ、続く文がその同じ事実を
説明・例示・言い換えているだけ、という形。段落を書いたら、それが一文に圧縮できないか確認する — 後ろの
文が最初の文にない事実を足していないなら、圧縮して消す。Background の冒頭の理由文
（[`references/sections.md`](references/sections.md)、Background が章に分かれる場合）が、これが最も強く
効く場所である。

### Exception: readers differ（例外：読み手が異なるとき）

**読み手が異なるとき**は同じ内容を二度述べてよい — 人間の読み手向けのスクリーンショットと、テキストしか
読めない読み手向けのコピー表。Goal が外部参照を指すときは、テキストによる代替も与える。

この例外は**提示形式の違い**についてのものであって、言語の違いではない。issue 全体を一つの言語で書き、
同じ内容を第二言語で言い直さない。

## Sections（セクション）

[`assets/issue-template.md`](assets/issue-template.md) を使う。

セクションは Refs / Background / Goal / Acceptance criteria / Affected areas / Dependencies だけ。
Design / Approach、Out of scope、Verification はここではセクションではない — 存在するセクションは埋め
られてしまうので、テンプレートからも外してある。

### Per section（セクションごと）

| Section | そこに入るもの |
|---|---|
| **Background / Why** | 問題を構成する事実。各文をテストせよ：それがなければ issue の必要性は成立しなくなるか？ 主語はドメインの実体。issue 番号や「このタスク」ではない。 |
| **Goal** | 何に準拠するか — 標準のセマンティクス、既存実装、スクリーンショット。自分による修正の説明は決して書かない。検証手段も書かない。 |
| **Acceptance criteria** | ドメイン自身の語彙によるチェックボックス。制約は満たすべき状態として書き、その理由は Background に置く。lint / 型チェック / テストは最後。 |
| **Affected areas** | 今この瞬間に怪しく見えるパス — 当て推量であって境界ではない。括弧書きはすでにそこに**あるもの**を名指しし、それに対して**何をするか**は決して書かない。 |
| **Dependencies** | 着手を妨げる依存だけ。妨げるものがなければセクションごと落とす。 |

セクションを埋める前に [`references/sections.md`](references/sections.md) を読むこと — セクションごとの
ルールと、それぞれ1つの実例対比を持っている：Background の主語、いつ章立て／表組みするか、Goal の
カバレッジテスト、"all" 基準が range する集合、括弧書きが何を言ってよいか。

## Revising an existing draft（既存の下書きを改稿する）

改稿は起草とは別のパスである。何を書くかを決めるのではなく、下書きが**すでに含んでいる、あってはならない
もの**を狩り出す作業である。[`references/revising.md`](references/revising.md) を読むこと — 順序付きの
チェックリストで、何を狩り出すかを述べる。監査の手前で意図的に止まっている：下書きは、問題をすでに頭の中に
入れた状態で書かれているので、`review-nice-issues` の実行は、どちらの経路であれ、このスキルを呼んだ側に
属する。

## Common Rationalizations（よくある自己正当化）

| 自己正当化 | 実際のところ |
|---|---|
| 「修正を説明しておけば実装者が早く着手できる。」 | 同時に彼らの判断を奪い、着手時にはもう動いているかもしれないコードベースの形に issue を縛り付ける。代わりに Affected areas を指せ — 指示ではなく当て推量として。 |
| 「この制約はその場に理由がないと恣意的に見える。」 | 理由は問題であり、問題は Background に属する。制約の隣の理由はその行を段落に戻し、その段落を通って実装方法が忍び込む。 |
| 「後続タスクを Out of scope に列挙するのは誠実な開示だ。」 | それは Background がいずれにせよ書かねばならないスコープ文（「このタスクはXを扱う。Yは #____ のもの」）の重複である。二つ目のリストを持つのではなく、そこに畳み込め。 |
| 「Verification セクションがあればチェックを走らせやすい。」 | その内容がチェックボックスとして表現可能なら、それは同じ内容が二度である。Acceptance criteria に畳み込んでセクションを落とせ。 |
| 「読み手の文脈のために実装案をいくつかスケッチしておくべきだ。」 | どちらでも受け入れ基準を満たすなら、両方とも表に出すべきでなかった選択である。あるいは本物の制約を持っているのなら、それは Acceptance criteria に、理由は Background に属する。本文のメニューとしてではない。 |
| 「これらの箇条書きは同じファイル／システムについてだから、一つの問題だ。」 | 主語を共有することは問題を共有することではない — テストは箇条書きが何**種類**の問題に仕分けられるかであって、何に触れるかではない。それらが一緒に属する理由を一文で書けないなら、共通の見出しを無理やり作らずに別々の issue に分割せよ。 |

## Related skills（関連スキル）

- `review-nice-issues` — すでに起草された issue 本文を、同じ二つのゲートに照らして、読み手の目線から
  監査する。
- `write-nice-instructions` — 指摘／指示のテンプレートと remedy strength。PRレビューコメントに適用され、
  issue 本文には適用されない。
- `avoid-unverifiable-context` — このスキルの Background 指針が「なぜを残す」半分を引いてきている、
  根拠 vs プロセスのルール。
- `avoid-reference-detours` — 文書をまたぐ場合の同じ引き算。Gate 2 が一つの文書の内部の繰り返しを
  カバーするのに対し、読み手は issue を順に読むので二つ目のコピーは再読であり、別ファイルに置かれた
  事実は往復のコストになる。
