## Overview（概要）

このスキルは、すでに書かれた issue 本文を、そのテキストだけを手にしている実装者として判定する — それについての
会話もなく、他所から持ち込まれた要求もなく、何かを引きに行けるリポジトリもない。そのテキストが、そういう
読み手にとって確定していなければならないものを確定しているか、そしてその内容のどれかが二度述べられていないかを
決着させる。

## The brief（ブリーフ）

issue 本文は **`$ARGUMENTS`** として届く — テキストそのものである。代わりに issue 番号やリポジトリを決して
求めないこと：取得は呼び出し元の仕事であり、取得が本文を超えて目の前に並べるものはすべて、このパスがそれなしで
済ませなければならないものである。

## Judging the body（本文を判定する）

- **手渡されたテキストを、そのまま、そこにあるとおりに判断する** — その背後にある要求ではなく、書いたときに
  自分が意図したことでもなく、それが着地するリポジトリについて知っていることでもない。自分がすでに知っている
  ことに乗った findings は、本文自身の読み手には決してできなかった findings である。
- **どのセクションも読むこと。代わりに言い回しを検索しないこと。** パターン検索が返すのは自分がすでに思いついた
  言い回しであり、欠陥は思いつかなかったほうにある。
- **参照されたファイルやシンボルが実際に存在するかどうかは、見に行くことを許された者に委ねること。** それは
  リポジトリへの接地であり、別のパスである。それに依る findings をここで出しても、テキストが示すものには何も
  乗っていない。

## Gate 1: determinacy（確定性）

本文自身のテキスト**だけ**を用いて — リポジトリの参照なし、たまたま知っていることの補完なし — テキストが
以下のそれぞれを確定しているか確認する：

- **問題。** `Background / Why` だけを読む。それが欠ければ issue の必要性が説明されないままになる、そういう
  事実を述べているか？ 要求をすでに知っている者にしか意味の通らない文（主語が issue 番号、ファイル名、
  「このタスク」で、許される唯一のスコープ文の外にあるもの）は、この読み手にとって問題を確定していない。
- **受け入れ基準。** `Acceptance criteria` だけを読む。各チェックボックスがドメインの語彙で述べられて
  いて、仕様の代わりに内部フィールド名、スキーマの語彙、ファイル名、行番号が立っていないか？ 実装ステップ
  として言い回された基準（「`published_version_id` を確認して…」）は、それがたまたま正しくても不合格。
- **境界。** `Goal`、`Dependencies`、（あれば）`Background` のスコープ文を読む。この読み手は自分の責任が
  どこで終わるか判別できるか — この issue が何を決めろと求めていないのか、そして何が着手そのものを妨げる
  のか？ `Affected areas` はこれも、`Background` に欠けた事実も決着させない：それは拘束力のない当て推量で
  あり、それを境界と取ることは、何が自分の決めることなのか読み手がなお判別できない本文を通してしまう。

別途、すべてのセクションを実装方法そのものについて走査する：

- **紛れ込んだ実装。** 別の実装が選ばれても処理が変わらない記述（どのコンポーネントを再利用するか、props に
  何を渡すか、どう分岐するか）は選択であって、基準でも affected-area の注記でもない — どこに現れようと
  フラグを立てる。
- **理由が付いた制約。** 制約だけを述べて正当化を `Background` に置く代わりに、正当化をインラインで担って
  いるチェックボックスや箇条書き。
- **この読み手を止める参照。** 開かないと文が完結しない参照（`#1784 makes X return Y`）は不合格。境界を
  示すだけの参照（`depends on #1784`、`Refs #1558`）はそうならない。

## Gate 2: duplication（重複）

同じ内容が二箇所以上で述べられていないか、そして存在すべきでないセクションが存在していないか確認する：

- `Design / Approach`、`Out of scope`、`Verification` の見出しが**存在すること自体**が findings である —
  これらは issue 本文のセクションではなく、その下にある内容は常に、issue 本文のセクションであるもののどれかに
  行き先を持つ。
- `Goal` が、何に準拠するかを指す代わりに `Acceptance criteria` を別の言葉で言い直している。
- `Background` の散文が、問題が何かではなく、どう解くかを説明している。

## From a failed gate to findings（落ちたゲートから findings へ）

各違反を、レンダリングに必要な一つまたは複数の事実として `write-nice-instructions-as-comment` に手渡す。
そのスキルが指摘の形と、対処をどれだけ強く述べるかを所有する。ここでどちらも発明しないこと。

- **確定性の失敗** — 問題、基準、境界がテキストだけで確定していないこと — は一つの事実である：何が欠けていて、
  それがどのセクションに属するか。
- **紛れ込んだ実装、理由を担った制約、読み手を止める参照** は修正が一意なので、それを述べる：外に出しておく
  選択、理由を `Background` に置いて単独で述べた制約、それが示す境界まで削り戻した参照。
- **重複** は、二箇所にある内容、あるいは存在すべきでないセクションである：その内容がどこに属するかを名指しし、
  修正はそれをそこに畳み込み、もう一方のセクションを落とすことである。

## Reporting（報告）

findings をテキストとして返す。それが出力のすべてであり、投稿は呼び出し元自身のツールによる呼び出し元の行為で
ある：このパスを起動した者 — 人間、あるいは `gh` アクセスを実際に持つスキル — が、それを見せるか、投稿するか、
より大きなレポートに畳み込むかを決める。

## The language the issue is written in is never a finding（issue が書かれている言語は決して findings にならない）

ゲートは本文の**形**についてのものなので、それが書かれている言語が何であれその言語で判断せよ。言語に関する
唯一の findings は Gate 2 のもの：同じ内容が第二言語で言い直されていること。

## Common Rationalizations（よくある自己正当化）

| 自己正当化 | 実際のところ |
|---|---|
| 「Affected areas のリストが詳しいので、境界は十分明確だ。」 | Affected areas は執筆時点の推測であり、拘束力を持たない — 読み手にどこを見ればよいかを伝えるのであって、何が彼らの決めることで何がそうでないかを伝えるのではない。境界は `Goal` / `Dependencies` / スコープ文から判断せよ。ファイル一覧の長さからではない。 |
| 「この issue のほとんどは実装可能に読めるので、一つの曖昧な基準は誰も止めないだろう。」 | 確定性に落ちる基準が一つあるということは、誰も自信をもってチェックを付けられない基準が一つあるということである。issue の残りがよく読めることは、その一つについての証拠ではない。全体の印象ではなく、すべての基準を判断せよ。 |
| 「この issue にはまだ Design / Approach セクションがあるが、有用な文脈として読める。」 | 「誰にとって有用な文脈か」こそ、このスキルが問うために存在する問いである。それが擁護可能な制約なら、理由を Background に置いて Acceptance criteria に属する。そうでないなら、そのセクションは、外に出しておくべきだった選択を紛れ込ませている。どちらにせよ、セクションそのものが findings である。 |
| 「この issue は1時間前に自分で書いた、意味は分かっている。」 | あなたは読みながら、テキストに欠けている意図を自分で補っている。その場にいなかった読み手にはそれができず、その隙間こそが失敗モードのすべてである。 |
| 「このスキルに `gh` アクセスを与えれば一手間省ける。」 | それは同時に、本文自身の読み手にはできない参照の解決や事実の確認を、こっそりやることを許してしまう — そして読み手にそれができないことこそ、Gate 1 が確認していることである。省かれる一手間こそ、このスキルが存在する理由そのものである。 |

## Red Flags（危険信号）

- その要件について自分がすでに知っていることに、テキストではなく寄りかかった所見。
- `Affected areas` をスコープ外の境界として数えている。
- リポジトリへの接地、スコープ、あるいは issue が書かれている言語についての所見。
- 所見を書くべきところで issue を書き直している。

## Verification（検証）

- [ ] どの所見も、それが出てきた本文の節か文を名指ししている。
- [ ] どの所見も Gate 1 か Gate 2 の不合格であり、どちらかを述べている。
