# review-nice-issues

## Purpose（目的）

`write-nice-issue-description` は issue の書き方を述べる。このスキルは**実際に書かれたもの**を、同じ二つの
ゲート — 確定性と重複（下で定義） — に照らして、読み手の側からチェックする。

このスキルは**設計上、外を見るツールを取り上げられた状態で走る**：`disallowed-tools` がそれらをプールから
除去するので、判断している間は `gh` を走らせられず、リポジトリを読めず、調べ物をサブエージェントに委譲でき
ず、何も投稿し返せない。それは判断の最中に覚えておくべき規律ではない — この除去こそが、下記の判断に
**実際に手渡されたテキストだけ**を使わせるものである（Gate 1 が記述する読み手と同じ足場）。空の
`allowed-tools` はこれを一切供給しない。あのフィールドはすでに手の届くものを事前承認するだけで、手の届く
範囲から何かを取り除くことは決してない。

この除去が解かれるのは、このスキル自身が返ったときではなく、利用者の次のメッセージが来たときである。つまり
除去は、呼び出したターンの残りにも及ぶ。したがって取得は引き渡しの**前**に済ませるか、さもなくば行われない
— このスキルの Inputs がすでに要求している順序が、仕掛けとして到着したものである。

このスキルは二つの状況で走る：

- **GitHub にすでに存在する issue をレビューする**：本文テキストは、このスキルが走る**前に**、取得を担う
  誰かによって取得されていなければならない — `/review-issue` コマンド、あるいは `gh` を持つ別のスキル。
  このスキルには、その結果のテキストだけを渡す。
- **書き上げたばかりの下書きを自己チェックする**：起草したテキストを直接渡す。自分の最初の一読を信用する
  のではなく — あなたは問題と実装をすでに頭の中に入れた状態でそれを書いており、まさにそれこそがこの
  チェックが迂回しなければならないものである。

## Inputs（入力）

issue 本文のテキスト — それだけ。このスキルは issue 番号やリポジトリを決して求めない。どちらにも作用する
手段を持たないからである。取得は呼び出し元の仕事。

## Workflow（手順）

### 1. 本文を所与として受け取る

手渡されたテキストを、そのまま、そこにあるとおりに判断する — その背後にある要求ではなく、書いたときに自分が
意図したことでもなく、それが着地するリポジトリについて知っていることでもない。

### 2. 本文を Gate 1（確定性）に照らして判断する

本文自身のテキスト**だけ**を用いて — リポジトリの参照なし、たまたま知っていることの補完なし — 以下の三つが
確定しているか確認する：

- **問題。** `Background / Why` だけを読む。それが欠ければ issue の必要性が説明されないままになる、そういう
  事実を述べているか？ 要求をすでに知っている者にしか意味の通らない文（主語が issue 番号、ファイル名、
  「このタスク」で、許される唯一のスコープ文の外にあるもの）は、この読み手にとって問題を確定していない。
- **受け入れ基準。** `Acceptance criteria` だけを読む。各チェックボックスがドメインの語彙で述べられて
  いて、仕様の代わりに内部フィールド名、スキーマの語彙、ファイル名、行番号が立っていないか？ 実装ステップ
  として言い回された基準（「`published_version_id` を確認して…」）は、それがたまたま正しくても不合格。
- **境界。** `Goal`、`Dependencies`、（あれば）`Background` のスコープ文を読む。この読み手は自分の責任が
  どこで終わるか判別できるか — この issue が何を決めろと求めていないのか、そして何が着手そのものを妨げる
  のか？ `Affected areas` はここで何も確定しない — 境界ではなく当て推量である。これがこの項目を満たすと
  数えてはならない。

別途、すべてのセクションを実装方法そのものについて走査する：

- **紛れ込んだ実装。** 別の実装が選ばれても処理が変わらない記述（どのコンポーネントを再利用するか、props に
  何を渡すか、どう分岐するか）は選択であって、基準でも affected-area の注記でもない — どこに現れようと
  フラグを立てる。
- **理由が付いた制約。** 制約だけを述べて正当化を `Background` に置く代わりに、正当化をインラインで担って
  いるチェックボックスや箇条書き。
- **この読み手を止める参照。** 開かないと文が完結しない参照（`#1784 makes X return Y`）は不合格。境界を
  示すだけの参照（`depends on #1784`、`Refs #1558`）はそうならない。

### 3. 本文を Gate 2（重複）に照らして判断する

同じ内容が二箇所以上で述べられていないか、そして存在すべきでないセクションが存在していないか確認する：

- `Design / Approach`、`Out of scope`、`Verification` のセクションが**存在すること自体**が findings で
  ある — `write-nice-issue-description` はこれらのセクションを使わず、その内容は常に、残るセクションの
  どれかに行き先を持つ（そのスキルの `SKILL.md` の表を参照）。
- `Goal` が、何に準拠するかを指す代わりに `Acceptance criteria` を別の言葉で言い直している。
- `Background` の散文が、問題が何かではなく、どう解くかを説明している。

### 4. findings を組み立てる

各違反を、レンダリングに必要な事実として `write-nice-instructions` に手渡す — そのスキルが指摘の形と、
対処をどれだけ強く述べるかを所有する。ここでどちらも発明しないこと。

- 確定性の失敗（問題・基準・境界がテキストだけで確定しない）→ 何が欠けていてどこに属するかを、
  `write-nice-issue-description` のセクション指針を用いて述べる。
- 紛れ込んだ実装、置き場所を誤った制約の理由、読み手を止める参照 → 修正はたいてい一意である：その
  選択／制約／参照を、あのスキルの Gate 1 が記述するとおりに述べる。
- 重複 → 行き先を持つほうのセクションを指す。修正は内容をそこに畳み込み、もう一方のセクションを落とすこと
  であり、それはあのスキルの Gate 2 の表に従う。

### 5. 報告する

findings をテキストとして返す。それが出力のすべてである — このスキルはコメントを投稿したり issue を編集
したりする手段を持たず、試みもしない。これを起動した者（人間、あるいは `gh` を持つ別のスキル）が、findings を
どうするかを決める：見せる、投稿する、より大きなレポートに畳み込む。

## Guardrails（ガードレール）

- 手順2・3に外部の知識を決して持ち込まない — 本文自身のテキストだけから、Gate 1 が記述する読み手がそれに
  出会うのとまったく同じように判断せよ。要求について自分がすでに知っていることに手を伸ばすのが、このスキル
  全体が**自分自身の中に**捕まえるために存在する唯一の失敗モードである。
- `disallowed-tools` のリストを丸ごと保つこと。このスキルの価値のすべては、判断している間 issue トラッカー
  やコードベースを見ることが**できない**点にある — 「便利だから」とリストから一つ取り戻せば、その判断を
  信頼に足るものにしている唯一の性質が失われる。`allowed-tools` へ移すのも、取り除くことに変わりはない。
- `Affected areas` は手順2の境界の項目に決して数えない。また `Background` に欠けた事実を決して免除しない —
  `write-nice-issue-description` 自身の定義により、それは拘束力のない当て推量である。
- 参照されたファイルやシンボルが実際に存在するかどうかはここでは範囲外である — それはリポジトリ接地性で
  あり、実際に見に行くことを許されたスキルの仕事である。
- issue が書かれている言語は決して findings にならない。両方のゲートは本文の**形**についてのものなので、
  それが書かれている言語が何であれその言語で判断せよ — `write-nice-issue-description` の実例が英語なのは、
  あのスキルが英語だからにすぎない。言語に関する唯一の findings は Gate 2 のもの：同じ内容が第二言語で
  言い直されていること。
- このスキルの内側から決して何も投稿しない。投稿は、望まれるなら、呼び出し元自身のツールによる呼び出し元の
  行為である。

## Common Rationalizations（よくある自己正当化）

| 自己正当化 | 実際のところ |
|---|---|
| 「Affected areas のリストが詳しいので、境界は十分明確だ。」 | Affected areas は執筆時点の推測であり、拘束力を持たない — 読み手にどこを見ればよいかを伝えるのであって、何が彼らの決めることで何がそうでないかを伝えるのではない。境界は `Goal` / `Dependencies` / スコープ文から判断せよ。ファイル一覧の長さからではない。 |
| 「この issue のほとんどは実装可能に読めるので、一つの曖昧な基準は誰も止めないだろう。」 | 確定性に落ちる基準が一つあるということは、誰も自信をもってチェックを付けられない基準が一つあるということである。issue の残りがよく読めることは、その一つについての証拠ではない。全体の印象ではなく、すべての基準を判断せよ。 |
| 「この issue にはまだ Design / Approach セクションがあるが、有用な文脈として読める。」 | 「誰にとって有用な文脈か」こそ、このスキルが問うために存在する問いである。それが擁護可能な制約なら、理由を Background に置いて Acceptance criteria に属する。そうでないなら、そのセクションは、外に出しておくべきだった選択を紛れ込ませている。どちらにせよ、セクションそのものが findings である。 |
| 「この issue は1時間前に自分で書いた、意味は分かっている。」 | あなたは読みながら、テキストに欠けている意図を自分で補っている。テキストだけを手にしている人間として判断せよ — それこそが失敗モードのすべてである。 |
| 「このスキルに `gh` アクセスを与えれば一手間省ける。」 | それは同時に、本物のテキストを前にした読み手にはできない参照の解決や事実の確認を、こっそりやることを許してしまう — そして読み手にそれができないことこそ、手順2が確認していることである。省かれる一手間こそ、このスキルが存在する理由そのものである。 |

## Related skills（関連スキル）

- `write-nice-issue-description` — このスキルが準拠をチェックする、執筆時の指針。ここでの findings が
  分かりにくければ読むこと。同じ二つのゲートを書き手の側から、より多くの実例とともに説明している。
- `write-nice-instructions` — 指摘のテンプレートと対処の強さを所有する。このスキルはそれに事実を手渡す
  （手順4）のであって、レンダリング済みの形を渡すのではない。
