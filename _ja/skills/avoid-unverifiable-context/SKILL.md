## Overview（概要）

残り続けるテキストは、それが書かれたときそこにいなかった誰かに読まれる。そしてプロセスは参加者にしか再生
されない：「レビューで指摘されたとおり」「もともとXでいくつもりだった」は、その人には再構成できない時系列に
依存している。到達できない参照も同じ失敗である — 対象が最初から存在しなかったのか、ここからは取りに行けない
だけなのか、読み手にとっては等しく行き止まりである。

## The rule（ルール）

テキストについての一つの問い：**読み手はそれが言っていることを確認しに行けるか？**

- 行ける：ビジネス要件、規制、ドメイン制約、プロダクト上の決定、そして現在のコード・型・スキーマに
  今も存在するもの。書け。
- 行けない：会話、レビュースレッド、試行錯誤、以前の方針、削除された議論。落とせ。

対象が到達**できる**のに、それでも読み手を送るべきでなかった場合は、何も削除されない — その事実は使用地点で
言い直される。それは別の所見である。

## Guidance（指針）

1. **根拠は残し、プロセスは落とす。** 仕様や設計がなぜ存在するのかは読み手にとっての判断材料である。
   「レビューのフィードバックにより」「方針が変わった」「もともとXにしていた」は、参加者にしか追えない
   タイムラインに依存する
2. **対比的な言い回しに注意。** 「AではなくB」「Aは非推奨」「Aは削除された」はいずれも読み手がAを
   知っていることを前提にする。知らないなら、Bをそれ単体で記述せよ
3. **issue 横断の参照は短い `TODO(#123): ...` の形に限定する。** それが何をどこで読めばよいかを正確に
   名指しし、この形を唯一到達可能なものにしている。「別 issue で対応」はそうではない
4. **非推奨の注記は実装が存在するあいだは問題ない** — それはまだ読み手の観測できる形の一部である。実装が
   消えたら、その注記は何も指さなくなるので一緒に消す
5. **どうしてもプロセスを残すなら、プロセスの居場所に置く。** PR説明文の Background セクション、または
   ADR。ソースコードでも、ユーザー向けドキュメントでも、APIリファレンスでもない
6. **読み手の言語で書く** — コードコメントやPR説明文ならリポジトリの言語、issue ならトラッカーの言語。
   同じ内容を第二言語で言い直してはならない。翻訳は独立に古びていき、どちらのコピーが最新なのか誰にも
   判別できなくなる

## Persistence（効力の持続）

ロードされたあとは、それをロードしたレスポンスだけでなく、すべてのレスポンスで効力を持つ。これから
書くものが後で読まれるかどうか迷っているあいだも、効力は残る。解除されるのは、作業が誰も行動のために
読まないものへ移ったとき、または止めるよう言われたときである。

## Common Rationalizations（よくある自己正当化）

最もよくある失敗は、その成果物が「ドキュメント」に感じられなかったせいで、これをまったく適用しないこと
である。まずそれを塞ぎ、それからプロセス漏れの言い訳へ：

| 自己正当化 | 実際のところ |
|---|---|
| 「これはコードコメント／コミットメッセージ／issue／Notion ページであって、本当の意味での『ドキュメント』ではないから該当しない。」 | 該当する。対象は**残り続けるあらゆる成果物**であり、それがどこにあろうと関係ない — コードコメント、コミットメッセージ、PRとissueの説明、APIと設計ドキュメント、Notion / docx ページ、すべて含む。これが繰り返される失敗である。「doc」とラベルが付いたときだけでなく、書く**前に**このスキルに照らして成果物を確認せよ。 |
| 「自分には問題なく読める。」 | あなたは読みながら、テキストに欠けている意図を自分で補っている。テキストだけを手にしている人間として判断せよ — それこそが失敗モードのすべてである。 |
| 「会話の履歴を入れておけば読み手に有益な文脈になる。」 | 読み手はその会話にいなかったので、ログは彼らにとってノイズである。**なぜ**は残し、**どうしてそうなったか**は落とせ。 |
| 「レビューでこの変更を求められたので、それを記録しておく。」 | レビューのフィードバックはプロセスである。結果としての決定を述べよ。レビューが要求したことではなく。 |
| 「却下した代替案を列挙しておけば透明性が高い。」 | 捨てられた選択肢は書き手だけの文脈である。読み手が本当になぜダメだったかを知る必要がある場合を除き、省け。 |
| 「このPR説明文は、読み手がスレッドを見ている前提でよい。」 | 残り続けるドキュメントはスレッドより長生きする。何ヶ月も後に初めて開く人間のために書け。 |

## Red Flags（危険信号）

- 「議論したとおり」「当初は X でいくつもりだった」「レビュー指摘を受けて」 — 参加者にしか辿れない時系列。
- 対比される側を読み手が知っている前提の文 — 「A ではなく B」「A は削除された」。
- 裸の `issue: 1234`、あるいはこの読み手が持っていないかもしれないワークスペースへのリンク。

## Verification（検証）

- [ ] どの主張も、現在のコード・型・スキーマ、あるいは明示された外部の規則から確かめられる。
- [ ] いつ書かれたか、誰がその場にいたかに依存する文が一つもない。
- [ ] issue をまたぐ参照は `TODO(#123): …` の形で、何を読むかを名指ししている。
- [ ] 文脈をまったく持たない読み手が、紹介なしに現れる固有名詞や前提に出会わない。
