## Overview（概要）

このスキルは、何も決めていない読み手が「これは自分のものか」を決着させて最初の一歩を踏み出せるように、
README を書き、改稿する。README は**「これは自分のものか、そして最初に何をするのか」**への常置の答えで
ある。リポジトリの他のどのドキュメントも、すでに決めた者に読まれる。これだけが、決めている最中に読まれる。

## When it applies（いつ適用するか）

*どこまで*決まっているかが場合によって違い、そしてそれがこのファイルの形を決める。以下の条件は公開される
README に向けて書かれており、他の場合は何が緩むかを述べる。

**公開。** 読み手は何にも同意していない。インストールしておらず、自分の問題がこれで解けるかどうかも知らず、
ファイルがその問いに答えるのをやめた瞬間に立ち去る。プロジェクトについて何一つ前提にできず、以下の条件が
すべて完全に適用される。

**チーム内部。** 読み手はすでに同意している — ここで働いているし、あなたに訊ける。到着する前に採用は
決着しているので、彼らが来た理由は入口と表面であり、これが何であるかはそのチーム自身の語彙で述べてよい。
緩まないもの：入口は実行可能なままであること。歩いて行って訊くことこそ、このファイルが取り除くために
存在する費用だからである。そして、このプロジェクトが意図的にしないことは前のほうに残すこと。見知らぬ者なら
ダウンロードの時点で立ち去るところを、同僚は誤った前提のうえで一日動いてから気づくからである。

**私的、著者以外の誰にも読まれない。** 範囲外である。文脈を推し測るべき読み手が存在せず、それがこのスキルの
前提だからである。

貢献者が**ここでどう作るか**を決めるのは別のドキュメントによってである。こちらは見知らぬ者がそれ**から**
判断するファイルである。読み手が存在するかぎり、順序を決めるのはその読み手である：フラグを調べに来た
メンテナはスクロールできるが、読み続けるかを決めている者にはそれができない。

## How to work（どう進めるか）

- **一行書く前に読み手が誰かを決着させる** — 公開か、チーム内部か。どの条件が緩み、どれが完全に効くかを
  決めるのがそれだからである。
- **草稿を上から、下のテストに照らして読み**、読み手が判断できる地点で止める。その地点より上のすべてが、
  このファイルの費用である。
- **レビューのときは、落ちた条件を名前で呼ぶ。** 指摘が「読みにくい」ではなく、どの条件かを言えるように。
- **書いたコマンドを、書いた順に実際に走らせる。** 入口についての散文は入口ではない。

## The test（テスト）

> **これを使うとまだ決めていない読み手が、それを決着させ、最初の一歩を踏み出せるか。それ以上読まずに。**

「それ以上読まずに」が条件のすべてである。判断の前に抱えねばならないものは、到着した全員が支払う —
立ち去る全員も含めて。

これは `dont-make-me-read` のテストを README の粒度にしたものであり、あのスキルの前提を引き継いでいる：
自分が要求している範囲を感じ取れない唯一の人間が書き手である。自分の草稿を、プロジェクトが何であるかを
すでに知った状態で読むからである。

## What a README owes its reader（README が読み手に負うもの）

この順で。それぞれが何かを決着させることで場所を得る。何も決着させない節は、どんな慣習が
そこに置いたものであれ、落ちる。

| | 何を決着させるか |
|---|---|
| **What this is** | 読み手の問題が、これが解く問題かどうか — カテゴリではなく、問題として述べる |
| **The way in** | 何もない状態から最初に動くものまで連れて行くコマンド |
| **The surface** | 読み手が打つ／呼ぶ／import するもの — そこから選ぶ集合 |
| **Where the rest lives** | 他のドキュメントが存在することを、名前で。誰もここで探さずに済むように |

プロジェクトが意図的にやらないことは、一つ目と一緒に置く：採用の前に読まれる境界は読み手に往復を丸ごと
節約させ、採用の後に読まれる境界は弁解に読める。

## The rules（規則）

上のものを**どう書くか**についての条件。レビューのときは名前で呼ぶこと。どれが落ちたかを指摘が
言えるように。

### 判断は説明より先に来る

読み手の最初の判断は、採用するか立ち去るかである。それを下せる地点より上のすべての行は、留まらない
人々も支払っている。哲学、経緯、バッジ、目次、あなたを納得させた理屈 — どれも、自分が気にかけるか
どうかを知る前に誰かが読んだ節である。

これは順序のルールであって長さのルールではない：その材料は、もっと下に、すでに欲しいと決めた者に
読まれる場所に置いてよい。

### 形はそれを生むルールで述べる。在庫を歩いて述べない

種類ごとに一段落あれば、段落は種類とともに増える。新しい種類が一つ増えれば一段落増え、名前が変われば
一段落直り、そのどれも読み手の関心があった場所ではない。

何がその種類に属するかを決めるルールを一度述べれば、読み手は次のものを自分で分類する — このファイルが
最後に触られたあとに足されたものも含めて。

**員数は同じ失敗の縮小版である。** 「三つの補助」「八つのモジュール」「そのうち二つが重みを担う」：
どれも次に誰かが足した時点で誤りになり、権威があるように読めて、権威を何も担っていない。種類が何かと、
何がそこに入るかを述べよ。読み手は数えられるし、その数は最新である。

### 読み手が選ぶものだけがリストになる

リストとは差し出された選択である。読み手が一つ選んで行動するなら、そのリストは仕事をしている：打てる
コマンド、import できる入口、インストールできるプラットフォーム。

存在はするが読み手が決して選ばないもの — 内部の構成要素、ツリーの全ファイル、プロジェクトが含むものの
すべて — は選択ではない。並べても読み手には何も入らず、項目ごとに保守の編集が一つ増える。そのリストは
ディレクトリがすでに持っていて、しかも正しく持っている。

リストが本当に選択であるときは、各項目を**読み手がそれを選ぶ条件**として書く。それが何であるかの要約
としてではない。要約はそれが定義されている場所にすでにある。条件のほうが、この読み手が来た理由であり、
他のどこも述べていないものである。

### ここにあるどれも、他のファイルが所有するものの二つ目の写しではない

README は自分が所有しないものを記述する。だからこそ、それは音もなく古びる：所有者側が編集され、README は
編集されず、何も壊れないので誰も気づかない。

向きのテスト：**所有者側が言い換えられたら、このファイルは誤りになるか。** なるなら、所有物を写している。
名前を出し、それが何のためにあるかを述べよ — 名前は意味のある言い換えをすべて生き延びるし、リネームも
生き延びる。検索が見つけるからである。

これはプロジェクト自身の原則にも当てはまる。あるドキュメント、スキル、仕様がそのルールの在り処なら、
README は**読み手が何を得るか**を、README 自身の言葉で述べる。ルールをそのまま言い直せば、このファイルは
原典が研がれるたびに更新を要する鏡になる。

### 入り口は実行可能で、しかも本物である

試すと決めた読み手に残っている問いは一つで、それは散文では答えられない。貼り付けられるコマンドを、走る
順に与えること。そして今日それが実際に動くかを確かめること：願望のインストール手順や、プロジェクトが
変わる前には正しかった手順は、すでに「はい」と言った読み手をちょうど無駄にする。

楽な経路がまだ存在しないなら、存在するほうを与えよ。動く不格好な経路は、動かない優雅な経路に勝つ。

### 読み手がすでに使っている言語で書く

利用者が一つの言語を読むプロジェクトが別の言語で読まれる理由はなく、
利用者が混在するプロジェクトは両方を出すのではなく選ばねばならない — 同じ内容の二言語は重複であり、
歩調を合わせるファイルが二つになり、両方を必要とする読み手はいない。

## Common Rationalizations（よくある自己正当化）

| 自己正当化 | 実際 |
|---|---|
| 「なぜこれが重要かを理解するには、読み手に哲学が要る。」 | 読み手に要るのは、これが自分のものかどうかである。留まると決めた者は哲学を読む。決めている最中の者はそれを支払って、それでも立ち去る。判断の前ではなく後に置け。 |
| 「プロジェクトが含むものを全部並べれば、これだけあると示せる。」 | 示せるのは、一月で誤りになるリストであり、しかも読み手が下す選択ではない。量は価値の提案ではないし、ディレクトリの一覧は最新かつ無料である。 |
| 「種類ごとに一文あると設計が読み取れる。」 | それを一文でやり、種類が増えても正しいままなのは、種類を生むルールのほうである。種類ごとの注釈は同じ内容を、増えるサイズで持っただけである。 |
| 「員数があると具体的になる。」 | 次のコミットで誤りになる。八つか九つかで誰かの判断が変わったことはない。 |
| 「原則を、それを所有するドキュメントから写せば読み手の往復が減る。」 | 使用箇所で言い直すのは正しい。その言い回しを写すことが、このファイルを下流にする。読み手が何を得るかを自分の言葉で述べ、ルールを所有するファイルは名前で挙げよ。 |
| 「命名規則があると、部品同士がどう噛み合うか分かる。だから前のほうに置く。」 | それは設計上の判断であり、設計上の判断が決着する場所が所有している。しかも読み手の次の行動を何も変えない。あちらで研げばこのファイルは黙って誤りになる — 読み手がすでに信じたあとまで誰も気づかない、内向きの矢印である。 |
| 「みんな README を見るのだから、そこから全部に到達できるべきだ。」 | 到達はそのとおり — 名前で。複製は違う。リポジトリの索引はリポジトリの二つ目の写しであり、最新に保たれるのはそのうち一方だけである。 |
| 「インストール手順は、パッケージングが片付いてから書く。」 | それでは、いま試そうとしていた読み手に走らせるものが何もない。今日動く経路を出し、より良いものができたら差し替えよ。 |
| 「内部向けだし、ここの全員がこれが何をするか知っている。」 | それを必要とする読み手は、知らないほうである — 新しく入った人、隣のチーム、一年後のあなた。内部の読み手が飛ばせるのは売り込みであって、入口ではない。 |
| 「自分には十分読める。」 | あなたはファイルを開く前からこのプロジェクトが何かを知っていた。それこそが読み手の持たない唯一のものであり、このファイルがそれを与えるためだけに存在するものである。 |

## Red Flags（危険信号）

- 読み手が決断できる地点より上に、哲学、経緯、バッジ、目次がある。
- 種類ごとに一段落、あるいはその個数。
- 読み手が決して選ばないもの、すなわちプロジェクトが含むものすべての一覧。
- プロジェクトが変わる前には正しかったインストール手順。

## Verification（検証）

- [ ] まだ決めていない読み手が、それ以上読まずに決断し、最初のコマンドを走らせられる。
- [ ] どのリストも読み手の選択であり、各項目はそれを選ぶ条件として書かれている。
- [ ] ここに書かれたものは、それを所有するファイルが言い換えられても誤りにならない。
- [ ] 並んでいる順にコマンドを実際に走らせた。
