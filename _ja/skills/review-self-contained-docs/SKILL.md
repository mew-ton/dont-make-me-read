# review-self-contained-docs

## Purpose（目的）

`avoid-unverifiable-context` と `avoid-reference-detours` は**何を書くか**を述べる。このスキルは実際に
書かれたものを、同じ三つの条件に照らして読み手の側からチェックする：time-closure と referenceability
（この対は `avoid-unverifiable-context` のもの）、そして reference-scope closure（`avoid-reference-detours`
のもの）。二つの状況で走る：

- **PRをレビューする**：その説明文と、差分が追加または変更するすべてのコメントを確認する。
- **書き上げたばかりのテキストを自己チェックする**：PR説明文、issue 本文、コードコメントが出荷される前に、
  自分の最初の一読を信用するのではなく、この同じ判断を明示的に通す — あなたはすべての文脈をすでに頭の中に
  入れた状態でそれを書いており、まさにそれこそがこのチェックが迂回しなければならないものである。二つの
  authoring スキルの自己チェックが記述する、まさにその読み手 — 文脈ゼロでこれを開く誰か — を想像し、その
  読み手の目の前にあるものだけを判断せよ：その単位自身のテキストと、コードコメントならそれが注釈している
  コード。PR、issue、この会話についてあなたが知っている他の何も、証拠として数えない。

## Inputs（入力）

これらは呼び出し元が供給する。

| 引数 | 意味 | 必須 |
|---|---|---|
| `<pr-url-or-number>` | レビュー対象のPR。既定は現在のブランチのPR。 | 任意 |
| `--repo <owner/repo>` | cwd から推測できないときの対象リポジトリ。 | 任意 |
| `--worktree <path>` | APIでコンテンツを取得する代わりに、すでにチェックアウト済みの worktree からファイルを読む。すでに worktree を持っている別のレビューフローから呼ばれるときに設定する。 | 任意 |
| `--comment` | findings をPRのインラインレビューコメントとして投稿する。既定は findings を出力して何も投稿しない。 | 任意 |

書き上げたばかりのテキストを自己チェックする場合、PR引数は存在しない：起草したテキスト（とコードコメント
ならそれが注釈しているコードブロック）を持って、下の「各単位を判断する」に直行する — 単位は一つだけで、
抽出は適用されない。

## Workflow（手順）

### 1. 差分だけでなく、現在のファイル内容を取得する

time-closure（下記の条件1）はコメント単体からは判断できない — 今コードが実際にどう見えるかに照らして確認
されねばならない。差分のハンクだけではこれを隠しうる：追加されたコメントが、同じPRの**より後の**ハンクが
再度変更するコードを記述しているかもしれないし、ハンク周辺の文脈行がファイルの head に対して古びている
かもしれない。

- `--worktree <path>` が与えられていれば、そこからファイルを読み、差分はその worktree の中から引数なしで
  `gh pr diff` を走らせて取得する — チェックアウトされたブランチからPRを自動検出するので、`git diff` の
  別途の権限は不要。
- そうでなければ、差分には `gh pr diff <pr>` を走らせ、各ファイルの内容はPRの head SHA で
  `gh api repos/<owner>/<repo>/contents/<path>?ref=<head-sha>` から取得する（レスポンスを base64 デコード
  する）。`gh pr diff` のハンクだけから判断しないこと：ハンクの文脈行は、その変更の周辺でファイルがどう
  見えたかであって、この条件が照合されるべき head ではない。

### 2. 候補となる単位を抽出する

**追加または変更された行だけ**に注意を限定する — PRレビューが、誰も触っていないコメントをレビューする筋合い
はない。これは単一の正規表現ではなく、二段のフィルタである：

1. **機械的パス**：変更された各ファイルについて、その拡張子に合致するコメント構文（`//`、`#`、
   `/* ... */`、docstring、`<!-- -->` など）を選び、`Grep` でそれを始める追加／変更行をすべて引き出す。
   そうした行の連続した並びを一つのブロックとして扱う。
2. **判断パス**：候補が散文ではなくコメントアウトされたコードである場合、あるいは変更が意味の違いを伴わない
   純粋な整形／誤字修正である場合は落とす — どちらもこのスキルが判断する単位ではない。生き残ったものに
   ついて、付随するコードを決める：既定ではコメントがその上または横に座る、それを囲む最小の文・ブロック・
   関数とし、コメント自体が明らかにより広い／狭い範囲についてであればそれに合わせる。内容をその選択に
   照らして確認する：docstring は、それが物理的に座っている宣言について真でありながら、なお別の宣言 —
   その契約を実際に必要とするのは呼び出し元であるほうの宣言 — を無記述のまま残しうる。その隙間は、それ自体
   が一つの findings であり、三つの条件がその docstring の内容に適用される**前**に来る。

変更された行は、**変更されていない**隣接行の意味を、その行自身の文字を変えることなくずらすこともある —
同じ段落の末尾の文が「なぜかは上のコメントを見よ」と言っているとき、それは同じ語句を指し続けているが、
その直前の文がたった今変わったのなら、読み手が読みに行かされる先も一緒に変わっている。変更されていない行が
変更された行と文法的に連続している（一つの文、あるいは一つの思考の流れとして読める）ときは常に、差分が
印を付けた行だけでなく、段落やコメントブロック全体を単位に引き込むこと。変わった半分だけを判断するのは、
まさにこのスキルが捕まえるために存在する種類の**誤誘導された参照**を見逃すことになる。

PR説明文それ自体をもう一つの単位として加える（`gh pr view --json body` で取得）。自己チェックされる issue
本文も同じように扱う — 単位一つ、付随するコードなし。

### 3. 各単位を判断する

生き残ったすべての単位について、**その単位のテキストだけ**と（コードコメントなら）その付随するコード
ブロックを用いて、下記の三つの条件に照らして判断する。目の前にないものは、本物の読み手にとっても存在しない
ものとして扱う — 周囲のファイルやPRが「たぶんこう言っているだろう」を補わないこと。これは二つの authoring
スキルが書き手に自分自身へ走らせるよう求めているのと同じ自己チェックだが、ここでは通し読みに委ねるのではなく
明示的に、単位ごとに走らせる。

順に判断する。後の条件は先の条件が通っていることを前提にするので、最初の失敗で止めること。各単位がどの条件で
落ちたか、あるいは三つすべてを通ったかを記録する — 候補リストや全体の流し読みをこの単位ごとの記録の代用と
する前に、[Common Rationalizations](#common-rationalizations) を読むこと。

#### 条件1: time-closure（時間の閉包）

問われているのは、そのテキストが**どの時点**を記述しているかであって、どの文法上の時制を使っているかでは
ない。過去形のテキストが現在を記述していることはありうる：「レガシーAPI由来の制約がまだ有効なので、この
呼び出しは同期である」は過去を参照しているが、目の前のコードの今この瞬間の性質を記述している — 付随する
コードに照らして確認し、コードがそれを裏づけるなら、時制にかかわらずこの条件は通る。テキストがこの条件で
落ちるのは、記述しているものが付随するコードにまったく対応物を持たないときである：「移行前はレガシーAPIを
呼んでいた」は過去の状態を記述しており、付随するコードがそれらしきものを何も示さないなら、読み手が検証
できるものは何も残っていない。

#### 条件2: referenceability（参照可能性）

問われているのは、読み手がそのテキストの指すものを確認しに行けるかどうかである。参照を到達不能にするものは
二つあり、どちらも同じ判定を受ける。読み手が等しく手詰まりになるからだ：

- **識別不能** — その参照がそもそもどのシステムに属するのかを語句が語っていない（システム名のない
  「issue: 1234」：Notion のページID？ GitHub issue？ Jira チケット？）。これは到達可能性が読み手にとって
  問いになる前に落ちる。
- **原理的に到達不能** — 会話、試行錯誤の連鎖、このセッションで下された決定。読みに行く成果物が存在しない。
- **この読み手の環境で到達不能** — Notion ページ、Slack スレッド、ミーティング。存在はするが、そのテキスト
  自身の語句が読み手を連れて行ける場所ではない。

短い `TODO(#123): ...` 形式の相互参照が唯一の例外である。何をどこで読めばよいかを正確に名指ししているので、
この条件を通ったものとして扱う。

#### 条件3: reference-scope closure（参照スコープの閉包）

条件2とは別の軸であり、すでにそれを通ったテキストにのみ適用される。問われているのは参照が到達可能かどうか
ではなく、**そもそもそれを理解するために、読み手がこの単位の外へ送られているかどうか**である — ファイル内の
別の場所にあるクラスレベルのコメント、「config を見よ」、「`coupon.rb` と同じ」、同じPR説明文の別セクション。
その対象は完璧に読めるものかもしれない。問題は、それを読むことが選択肢ではなかったことであり、そのコメントの
**位置**こそが誤りの起きた場所である。「読み手はそれに到達できるか？」は条件2の問い。「読み手はそれを理解
するために、この単位を離れなければならないのか？」がこちらの問いである。

条件ごとの Bad/Good の対、（条件1には、それ以外は妥当なコメントの中に埋もれた違反のための二組目がある）、
コメントがまったくない best case、そして差分を要する二つの抽出のエッジケース — 変更された行が変更されていない
隣接行の意味を変えるケースと、docstring がそれが座っているのとは別の宣言を記述しているケース — は
[`references/examples.md`](references/examples.md) を参照。

### 4. findings を組み立てる

各違反を、レンダリングに必要な事実として `write-instructions-as-comment` に手渡す — そのスキルが指摘の形と、
対処をどれだけ強く述べるかを所有する。ここでどちらも発明しないこと。

- 条件1または2の違反 → **一つの事実**：その単位は落ちており、修正は一意である — 削除せよ。
- 条件3の違反 → **たいてい二つの別個の事実**。擁護できる修正（その単位を削除する）と、未解決の隙間
  （それが担っていた情報に居場所がない）は、異なる種類の主張だからである：
  - (a) その単位は読み手を自身のスコープの外へ送っている — 削除せよ。
  - (b) それが担っていた情報が、その使用地点のどこにも表現されていない — 何が欠けていて、それがどこに
    住む必要があるかを名指しし、修正は名指ししない。(a) と純粋に冗長になる場合は (b) を省く — 条件3の
    違反の中には「置き場所を誤っている」以上の情報を担っていないものがあり、そこから無理に二つ目の事実を
    捻り出すのは、存在しない設計上の隙間をでっち上げることになる。

> 【訳注】この手順4も `write-instructions-as-comment` の起動を求めているが、`allowed-tools` に `Skill` は
> 含まれていない。`review-nice-issues` の手順4と同じ構造上の疑い。

### 5. 報告する

- 既定：findings を出力する。何も投稿しない。
- `--comment`（単体利用時のみ）：各 findings を
  `gh api repos/<owner>/<repo>/pulls/<pr>/comments` 経由でPRのインラインレビューコメントとして投稿する。
  その単位の `commit_id`（PRの head SHA）、`path`、`line`、レンダリング済みの findings を `body` として
  渡す。素の `gh pr comment` は行ではなく conversation タブに着地する — それは `--comment` を満たさない。
- **別のスキルの内部の一工程として起動されたとき**（より広いPRレビューが、そのテキスト自己完結性の軸として
  これを呼ぶ場合）、決して投稿しない — findings を返し、呼び出し元が自身のコメントに畳み込むに任せる。
  両方から投稿すると、同じ findings が二度重複することになる。

## Guardrails（ガードレール）

- 条件1を差分のハンクだけから決して判断しない。まずファイルの現在の内容を取得すること（手順1）。
- 手順3に外部の知識を決して持ち込まない — 各単位を、その単位自身のテキストと直接付随するコードだけから、
  読み手がそれに出会うのとまったく同じように判断せよ。PRについて自分がすでに知っていることに手を伸ばすのが、
  このスキル全体が**自分自身の中に**捕まえるために存在する唯一の失敗モードである。
- `--comment` が明示的に与えられていない限り findings を決して投稿せず、別のスキルのサブルーチンとして
  走っているときは一切投稿しない。
- 単位が書かれている言語は決して findings にならない。三つの条件はすべてテキストが**どんな文脈**を担うかに
  ついてのものなので、各単位が書かれている言語が何であれその言語で判断せよ — このスキルの実例が英語なのは、
  このスキルが英語だからにすぎない。同じ内容を第二言語で言い直している単位は findings になるが、言語選択
  としてではなく重複としてである。
- 条件1または2で落ちた単位は、条件3に照らして重ねて確認しない — 最初の失敗で止めること。すでに先の条件で
  落ちた単位について、条件3の判定をでっち上げないこと。

## Common Rationalizations（よくある自己正当化）

手順2は候補リストを生む。実際にそれを判断するのは手順3である。この表を始める前に読み、その言い訳が頭に
浮かんだときにはすでに答えが用意されているようにすること。

| 手順 | 自己正当化 | 実際のところ |
|---|---|---|
| 3 | 「コメント候補が何十件（何百件）もある。grep してリストを報告すればそれがレビューだ。」 | grep はコメントのように**見える**行を抽出するだけで、手順2の判断パスはそのリストをさらに絞るだけである。どちらも time-closure、referenceability、reference-scope closure を判断していない — それらはパターンマッチでは解決しない意味の問いである。候補リストは、その大小にかかわらず手順2の出力であって、決して手順3の出力ではない。 |
| 3 | 「生き残った単位が多すぎて、一度に一つずつ判断できない。」 | 生き残りが5件でも500件でも、同じ作業の繰り返しである — 量はサンプリング、バッチ処理、流し読みのシグナルには決してならない。手順4に移る前に、生き残ったすべての単位について判定を記録せよ。 |
| 3 | 「このコメントのほとんどは正当でチェック可能な理由づけとして読めるので、単位全体は通る。」 | 一つの節が条件に落ちれば単位全体が落ちる。同じコメントの残りが現在形でチェック可能であっても同じ。周囲の良い説明は、そうでない一つの節の恩赦にはならない — 単位の全体的な印象ではなく、すべての節を判断せよ（`references/examples.md` の二つ目の条件1の例を参照）。 |

## Related skills（関連スキル）

- `avoid-unverifiable-context` — 条件1と2の背後にある執筆時の指針。どちらかの findings が分かりにくければ
  読むこと。書き手の側から、より多くの実例とともに説明している。
- `avoid-reference-detours` — 条件3の背後にある執筆時の指針。その修正がなぜ削除ではなく言い直しなのかも
  含む。
- `write-instructions-as-comment` — 指摘のテンプレートと対処の強さを所有する。このスキルはそれに事実を手渡す
  （手順4）のであって、レンダリング済みの形を渡すのではない。
