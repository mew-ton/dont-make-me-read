## Overview（概要）

このスキルは、すでに書かれたテキスト — PR の説明と、その差分が触れるすべてのコードコメント — を、書き手の
文脈を何も持たない読み手として判定する：会話もなく、issue もなく、周囲の差分もない読み手として。各単位は、
それ自身のテキストと、コードコメントならそれが注釈しているコードから判定する。それ以外に自分が知っている
ことは証拠にならず、そこに手を伸ばすことが、このスキルが自分自身の中に捕まえるために存在する唯一の失敗で
ある。

## How to work（どう進めるか）

- **各単位を、それ自身のテキストと付随するコードから判定し、それ以外はすべて存在しないものとして扱う。**
  周囲のファイルやPRが「たぶんこう言っているだろう」を補わないこと — 本物の読み手にはそれができない。
- **何かを判定する前に、PRの head 時点のままのファイルを取得する。** ハンクの文脈行は、その変更の周辺で
  ファイルがどう見えたかであって、最初の条件が照合されるべきコードではない。
- **追加または変更された行だけから抽出し、生き残ったものをすべて判定する。** PRレビューが、誰も触っていない
  コメントをレビューする筋合いはなく、量はサンプリングの理由に決してならない。
- **どの単位も読むこと。代わりに言い回しを検索しないこと。** パターン検索が返すのは自分がすでに思いついた
  言い回しであり、欠陥は思いつかなかったほうにある。
- **単位ごとに判定を記録する** — どの条件で落ちたか、あるいはどの条件も通ったか — findings を一つでも
  組み立てる前に。候補リストは判定ではない。
- **事実は、それをレンダリングするスキルに手渡す。頼まれていないものは何も投稿しない。**

## The brief（ブリーフ）

呼び出し元のブリーフは **`$ARGUMENTS`** として届き、次のものを運びうる。

| ブリーフにあるもの | それが決着させること | 既定 |
|---|---|---|
| `<pr-url-or-number>` | レビュー対象のPR | 現在のブランチのPR |
| `--repo <owner/repo>` | cwd が決着させないときの対象リポジトリ | cwd から推測する |
| `--worktree <path>` | APIでコンテンツを取得する代わりに、すでに存在するチェックアウトからファイルを読む — すでに worktree を持っているレビューフローが設定する | APIで取得する |
| `--comment` | findings をPRのインラインレビューコメントとして投稿する | findings を出力し、何も投稿しない |

PR を含まないブリーフは、書き上げたばかりのテキストの自己チェックである：単位は一つ — そのテキストと、それが
注釈しているコードブロック — であり、抽出するものは何もないので、そのまま条件へ進む。

## The conditions（条件）

各単位を、以下のどの条件にも照らして順に判断する。後の条件は先の条件が通っていることを前提にするので、最初の失敗で
止めて、それを記録すること：条件1か2で落ちた単位は、条件3の判定を決して受けない。

### 条件1: time-closure（時間の閉包）

問われているのは、そのテキストが**どの時点**を記述しているかであって、どの文法上の時制を使っているかでは
ない。過去形のテキストが現在を記述していることはありうる：「レガシーAPI由来の制約がまだ有効なので、この
呼び出しは同期である」は過去を参照しているが、目の前のコードの今この瞬間の性質を述べている — 付随する
コードに照らして確認し、コードがそれを裏づけるなら、時制にかかわらずこの条件は通る。テキストが落ちるのは、
記述しているものが付随するコードにまったく対応物を持たないときである：「移行前はレガシーAPIを呼んでいた」は
過去の状態を記述しており、コードがそれらしきものを何も示さないなら、読み手が検証できるものは何も残って
いない。

すべての節を判断すること。一つの節が落ちれば、残りがどれほどチェック可能であっても単位全体が落ちる。

### 条件2: referenceability（参照可能性）

問われているのは、読み手がそのテキストの指すものを確認しに行けるかどうかである。次のものが参照を到達不能に
し、どれも同じ判定を受ける。読み手が等しく手詰まりになるからだ：

- **識別不能** — その参照がそもそもどのシステムに属するのかを語句が語っていない（システム名のない
  「issue: 1234」：Notion のページID？ GitHub issue？ Jira チケット？）。これは到達可能性が読み手にとって
  問いになる前に落ちる。
- **原理的に到達不能** — 会話、試行錯誤の連鎖、このセッションで下された決定。読みに行く成果物が存在しない。
- **この読み手の環境で到達不能** — Notion ページ、Slack スレッド、ミーティング。存在はするが、そのテキスト
  自身の語句が読み手を連れて行ける場所ではない。

短い `TODO(#123): ...` の相互参照が唯一の例外である。何をどこで読めばよいかを正確に名指ししているので、
通ったものとして扱う。

### 条件3: reference-scope closure（参照スコープの閉包）

条件2とは別の軸であり、すでにそれを通ったテキストにのみ適用される。問われているのは参照が到達可能かどうか
ではなく、**そもそもそれを理解するために、読み手がこの単位の外へ送られているかどうか**である — ファイル内の
別の場所にあるクラスレベルのコメント、「config を見よ」、「`coupon.rb` と同じ」、同じPR説明文の別セクション。
その対象は完璧に読めるものかもしれない。問題は、それを読むことが選択肢ではなかったことであり、そのコメントの
**位置**こそが誤りの起きた場所である。「読み手はそれに到達できるか？」は条件2の問い。「読み手はそれを理解
するために、この単位を離れなければならないのか？」がこちらの問いである。

## From a failed unit to findings（落ちた単位から findings へ）

各違反を、レンダリングに必要な一つまたは複数の事実として `write-nice-instructions-as-comment` に手渡す。
そのスキルが指摘の形と、対処をどれだけ強く述べるかを所有する。ここでどちらも発明しないこと。

- **条件1または2** — **一つの事実**：その単位は落ちており、修正は一意なので、それを述べる。その単位を
  削除せよ。
- **条件3** — **たいてい二つの事実**。擁護できる修正と未解決の隙間は、異なる種類の主張だからである：
  - (a) その単位は読み手を自身のスコープの外へ送っている — 削除せよ。
  - (b) それが担っていた情報が、その使用地点のどこにも表現されていない — 何が欠けていて、それがどこに
    住む必要があるかを名指しし、修正は名指ししない。
  - (a) を言い直すだけになる場合は (b) を省く。条件3の単位の中には「置き場所を誤っている」以上の何も担って
    いないものがあり、そこから無理に二つ目の事実を捻り出すのは、存在しない設計上の隙間をでっち上げることに
    なる。

> 【訳注】この節も `write-nice-instructions-as-comment` の起動を求めているが、`allowed-tools` に `Skill` は
> 含まれていない。`review-nice-issues` の手順4と同じ構造上の疑い。

## Reporting（報告）

- **既定：findings を出力する。** 何も投稿しない。
- **`--comment`（単体利用時のみ）**：各 findings を `gh api repos/<owner>/<repo>/pulls/<pr>/comments` 経由で
  インラインレビューコメントとして投稿する。その単位の `commit_id`（PRの head SHA）、`path`、`line`、
  レンダリング済みの findings を `body` として渡す。素の `gh pr comment` は行ではなく conversation タブに
  着地し、`--comment` を満たさない。
- **別のスキルの内部の一工程として走っているときは、一切投稿しない** — findings を返し、呼び出し元が自身の
  コメントに畳み込むに任せる。両方から投稿すると、同じ findings を二度提出することになる。

## The language a unit is written in is never a finding（単位が書かれている言語は決して findings にならない）

条件はどれもテキストが**どんな文脈**を担うかについてのものなので、各単位が書かれている言語が何であれその
言語で判断し、findings はそのリポジトリのレビューがすでに使っている言語で書くこと。自分の内容を第二言語で
言い直している単位は findings になる — 言語選択としてではなく、重複としてである。

## Common Rationalizations（よくある自己正当化）

| 自己正当化 | 実際のところ |
|---|---|
| 「コメント候補が何十件もある。grep してリストを報告すればそれがレビューだ。」 | grep はコメントのように**見える**行を抽出するだけで、判断パスはそのリストをさらに絞るだけである。どちらも time-closure、referenceability、reference-scope closure に答えていない — それらはパターンマッチでは解決しない意味の問いである。候補リストは、その大小にかかわらず抽出の出力であって、決して判定ではない。 |
| 「生き残った単位が多すぎて、一度に一つずつ判断できない。」 | 生き残りが5件でも500件でも、同じ作業の繰り返しである — 量はサンプリング、バッチ処理、流し読みのシグナルには決してならない。findings を一つでも組み立てる前に、生き残ったすべての単位について判定を記録せよ。 |
| 「このコメントのほとんどは正当でチェック可能な理由づけとして読めるので、単位全体は通る。」 | 一つの節が条件に落ちれば単位全体が落ちる。残りが現在形でチェック可能であっても同じ。周囲の良い説明は、そうでない一つの節の恩赦にはならない — 単位の全体的な印象ではなく、すべての節を判断せよ（`references/examples.md` の条件1の二つ目の Bad）。 |
| 「このコメントが何を意味するかはPRから分かっているので、これで問題ない。」 | ならばその指摘は、読み手が持っていない文脈に乗っている。差分から、issue から、この会話から自分が抱えているものこそ、その単位が自分自身で担わねばならないものである。 |

## Red Flags（危険信号）

- ファイルの現在の内容を取らずに、差分のハンクだけで条件1を判定している。
- すでに条件1か2で落ちた単位に、条件3の判定まで付いている。
- たまたま自分が持っているPRの文脈を根拠にした findings。
- 言語の選択が findings として報告されている。
- 差分が一度も触っていないコメントが、findings の中に現れている。

## Verification（検証）

- [ ] どの単位も、それ自身のテキストとそれに付随するコードから判定されている。
- [ ] 生き残ったすべての単位に判定が記録されており、落ちた単位はどれも最初に落ちた条件で止まっている。
- [ ] `--comment` が与えられない限り何も投稿しておらず、別のスキルの一工程として走っているときは一切投稿して
      いない。
