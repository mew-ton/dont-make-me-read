# Extracting the units（単位を抽出する）

ブリーフがPRを名指ししており、その差分を、条件が照らされる単位にしなければならないときに読むこと。
書き上げたばかりのテキストの自己チェックは単位が一つで、ここのすべてを飛ばす。

## 1. Get the current file content, not just the diff（差分だけでなく、現在のファイル内容を取得する）

time-closure はコメント単体からは判断できない — 今コードがどう見えるかに照らして確認される。差分のハンク
だけではそれを隠してしまう：追加されたコメントが、同じPRの**より後の**ハンクが再度変更するコードを記述して
いるかもしれず、ハンク周辺の文脈行は、その変更の周辺でファイルがどう見えたかであって、この条件が照合される
べき head ではない。

- **`--worktree <path>` があるとき** — そこからファイルを読み、差分はその worktree の中から引数なしで
  `gh pr diff` を走らせて取得する。チェックアウトされたブランチからPRを検出するので、`git diff` の別途の
  権限は不要。
- **そうでないとき** — 差分には `gh pr diff <pr>` を走らせ、各ファイルの内容はPRの head SHA で
  `gh api repos/<owner>/<repo>/contents/<path>?ref=<head-sha>` から取得し、レスポンスを base64 デコードする。

## 2. Pick the candidates, in two passes（候補を二段のパスで選ぶ）

**追加または変更された行だけ**に注意を限定する — PRレビューが、誰も触っていないコメントをレビューする筋合い
はない。これは単一の正規表現ではなく、二段のフィルタである。

1. **機械的パス**：変更された各ファイルについて、その拡張子が使うコメント構文（`//`、`#`、`/* ... */`、
   docstring、`<!-- -->` など）を取り、`Grep` でそれを始める追加／変更行をすべて引き出す。そうした行の
   連続した並びが一つのブロックである。
2. **判断パス**：候補が散文ではなくコメントアウトされたコードである場合、あるいは変更が意味の違いを伴わない
   純粋な整形／誤字修正である場合は落とす。どちらもこのスキルが判断する単位ではない。

PR説明文それ自体をもう一つの単位として加える（`gh pr view --json body` で取得）。自己チェックされる issue
本文も同じように働く：単位一つ、付随するコードなし。

## 3. Decide the code each unit is judged against（各単位が照らされるコードを決める）

既定では、コメントがその上または横に座る、それを囲む最小の文・ブロック・関数とし、コメントが明らかに別の
範囲についてであればそれを広げるか狭める。

そのうえで、単位の内容をその選択に照らして確認する。docstring は、それが物理的に座っている宣言について真で
ありながら、なお**別の**宣言 — その契約を実際に必要とするのは呼び出し元であるほうの宣言 — を無記述のまま
残しうる。その隙間はそれ自体が一つの findings であり、その docstring が述べていることにどの条件かが適用
される**前**に来る。

## 4. Pull in the unchanged lines whose meaning changed（意味が変わった、変更されていない行を引き込む）

変更された行は、**変更されていない**隣接行の意味を、その行自身の文字を変えることなくずらすことがある。
同じ段落の末尾の文が「なぜかは上のコメントを見よ」と言っているとき、それは同じ語句を指し続けているが、
その直前の文がたった今変わったのなら、読み手が読みに行かされる先も一緒に変わっている。

だから、変更されていない行が変更された行と文法的に連続している（一つの文、あるいは一つの思考の流れとして
読める）ときは常に、差分が印を付けた行だけでなく、段落やコメントブロック全体を単位に引き込むこと。変わった
半分だけを判断するのは、まさにこのスキルが捕まえるために存在する種類の誤誘導された参照を見逃すことになる。

## Worked case: a changed line redirects an unchanged one（変更された行が、変更されていない行を誤誘導する）

条件は素のコードとして示せるが、こちらは本質的に差分についてのもの — 何が変わったか、そしてそのせいで
変更されていない隣接行が今や何を意味するのか。

**Diff (`src/analytics/types.ts`)**

```diff
 /**
- * The resolved path. **Query string is not included** (`resolvePath` drops it).
+ * The resolved path and its query string. **Hash is not included.**
+ *
+ * The query is passed through `resolvePath` unchanged; only key order is stabilized.
  * See the comment in this file for why.
  */
 path: string;
```
（訳：削除行＝「解決済みのパス。**クエリ文字列は含まれない**（`resolvePath` が落とす）。」／追加行＝
「解決済みのパスとそのクエリ文字列。**ハッシュは含まれない。**」「クエリは `resolvePath` を無変更で
通過する。キー順序のみが安定化される。」／変更なしの行＝「理由についてはこのファイル内のコメントを見よ。」）

**抽出される単位**：4行すべてを一つの段落として。「See the comment in this file for why.」は `+`/`-` の印を
持たないので、差分だけを見るパスは飛ばしてしまう — しかしそれは、変更された行が開く段落の文法的な結びの文で
あり、それが指し示すものも一緒に変わっている。

条件1と2は通る — 段落は現在のフィールドを記述しており、「このファイル内のコメント」は到達可能に聞こえる。
条件3は落ちる。しかも通常より悪い：このドキュメントが直接述べられる事実のために読み手を他所へ送ることが
すでにスコープ違反であるうえに、ここではそのポインタ自体が誤っている — 実際の理由づけは
`src/analytics/resolvePath.ts` という別のファイルにある。書かれたとおり字義どおりにポインタをたどった読み手は、
そこで何も見つけられない。

**二つの事実**（条件3のいつもの形。場所の誤りは (a) の問題の一部であって、別個の事実ではない）：

(a) `types.ts` の `path` に対するドキュメントは、理由づけが「このファイル内」にあると述べているが、実際には
`resolvePath.ts` にある — ポインタをたどった読み手は何も見つけられない。正しいファイルを名指しするよう
ポインタを直すか、削除して理由（クエリは保持、ハッシュは削除）をここで直接述べよ。

(b) `path` が何を含むかの契約が、その使用地点で表現されていない。修正は名指ししない。このフィールドの
ドキュメントは、別のファイルをまったく開くことなく単体で読めるべきである — それが開いたままの隙間である。

## Worked case: a docstring describing a different declaration than the one it sits on（docstring が、それが座っているのとは別の宣言を記述している）

これは条件3の違反ではない — 下のテキストのどこにも、読み手をどこかへ送るものはない。docstring は正確で、
完全で、まさにそれがある場所で到達可能である。誤りはもっと早く、抽出で起きている：書いた者は
`validateDiscountCode` を記述するつもりだったが、それが物理的に座っている行は別の宣言である。

```typescript
/** Discount codes are 5-8 uppercase alphanumeric characters, optional campaign-tag prefix. */
const VALIDATE_CODE_REGEX = /^[A-Z0-9]{5,8}$/;

export function validateDiscountCode(code: string): boolean {
  return VALIDATE_CODE_REGEX.test(code);
}
```
（訳：docstring＝「割引コードは5〜8文字の大文字英数字、任意でキャンペーンタグの接頭辞。」）

**抽出される単位**：上の既定ルール（物理的に座っている宣言）により、docstring ＋ `VALIDATE_CODE_REGEX`。
その単位だけで判断すると、どの条件の違反もない — テキストは `VALIDATE_CODE_REGEX` のフォーマットについて
真であり、それがある場所でローカルかつ到達可能である。findings は条件からではなく、内容チェックから来る：
この契約を必要とするのは `validateDiscountCode` の呼び出し元であり（エクスポートされているのはこちらの関数で、
正規表現はその実装にすぎない）、その関数は固有のドキュメントを持たない — 関数の読み手は、上にある別名の宣言に
気づいて、そちらを読まねばならなくなる。

**Finding**：`validateDiscountCode` は固有のドキュメントを持たない。その契約はその上の宣言
`VALIDATE_CODE_REGEX` にしか現れていない — docstring を `validateDiscountCode` へ移せ。
