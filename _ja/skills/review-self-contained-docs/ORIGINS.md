# この規則がどこに座り、何がその隣に座っているのか

このファイルを指すものは何も無く、指すべきでもない：これはスキルを保守する者に向けた近隣の見取り図と設計上の
理由であって、このパスを走らせるエージェントがロードしなければならない材料ではない。ここに置くことで
`SKILL.md` の外に出せる。そこにあれば、単位を判断したいだけの読み手全員が代金を払うことになる。

## 条件がどこから来たのか

本文はもう、かつてそれで始まっていた二つの authoring スキルを名指ししない。本文にある名前は、何も検査しない
他人のファイルへの依存であり、レビューの途中にいる読み手は、ある条件がどこで最初に書き下されたかを知っても
何も違うことをしない。

- `dont-make-me-read` の `rules/unverifiable-context.md` — 条件1と2の背後にある執筆時の規則。書き手の側から、より多くの実例とともに
  述べている。どちらかの条件の findings が分かりにくければ読むこと。
- `dont-make-me-read` の `rules/reference-detours.md` — 条件3の背後にある執筆時の規則。その修正がなぜ削除ではなく言い直しなのかも
  含む。その非対称性こそ、ここで条件3が二つの事実を生み、他方が一つを生む理由である。

`write-nice-instructions-as-comment` は例外で、本文に名指しされたまま残る：このスキルはすべての findings を
レンダリングするためにそれを起動するのであり、何かを呼ぶ工程は、自分が何を呼ぶのかを言わねばならない。

## なぜこのスキルは fork ではないのか

この一揃いの中で親から起動される他のスキルはすべて `context: fork` / `background: false` を持つ。これは
意図的に持たない：その唯一の産物は判定の集まりであり、自分自身の実行環境から返される判定は、それぞれが
乗っている単位のテキストと付随するコードを伴わずに届くので、そのレビューを誰もレビューできない。このパスは
呼び出し元の文脈で走り、そこでは証拠が見えたまま残る。

## 何がどこへ移り、なぜか

- 抽出の手順 — head の内容を取得する、二段の候補フィルタ、付随するコードを決める、連続した変更されていない
  行を引き込む — に到達するのは、ブリーフがPRを名指ししているときだけである。書き上げたばかりのテキストの
  自己チェックは単位が一つでそれを飛ばすので、本文ではなく同梱ファイルにしてある。
- 抽出のエッジケースもそれと一緒に移り、抽出は一箇所で決着する。`examples.md` は今では条件ごとの対と、
  コメントがない best case だけである。
- 古い `Guardrails` の節は四つ目のガードだった：その一行一行が、二度述べられた規則か、すでに存在する
  Red Flag のどちらかだった。その内容は、それが属する規則の中か、Red Flags か、Verification に座っている。
