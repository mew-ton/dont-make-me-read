## Scope（範囲）

設計ドキュメントは、それが記述するコードベースに何かを足そう／変えようとしている者に読まれる。
**既存の実装を先に読まなくても**正しく判断できるようにすることで、その存在価値を得る。仕事はそれが
すべてである。

コードはすでに、そこに何があるかを示している。git はすでに、それがいつ変わったかを示している。どちらも
示さないのは、**次の判断を何が決めるか**である。だから現状の形を語る設計ドキュメントには読み手がいない —
その中身はすべて、別のどこかでもっと速く手に入る。

issue は問題＋完了条件である（`write-nice-issue-description`）。`SKILL.md` はエージェントへの指示である
（`write-nice-skills`）。設計ドキュメントはそのどちらでもない。「ここではこれをどう判断するのか」に対する
恒常的な答えであり、それを書いた者がもう捕まらなくなってから長く読まれる。

## The test（テスト）

`dont-make-me-read` のテストを、この成果物の粒度で：

> **読み手は、実装を閉じたまま、これだけで自分の判断を決着させられるか？**

節に適用すると、貢献者が結論に至るのか、それとも何が起きたかを知るだけなのかを問う。ファイル全体に適用
すると、貢献者が実際に直面する判断がすべてここに入っているかを問う。

## The four conditions（四つの条件）

レビューのときはこれを名指しすること。findings がどれに落ちたかを言えるように。

### 1. すべての節が、誰かが直面する判断を決着させる

部品からではなく、判断から始める。「これはどの層に属するか」「これは fork するか」「この入口はどこに
住むか」は判断である。「四つの層とは何か」は記述であり、判断がそれを必要とするときに初めて節になる。

現在の配置を記述しているだけの節が、その兆候である。修正は、その節が何の判断のために書かれたのかを見つけ、
それを決めるもので始めること — あるいは、そんな判断が存在しないなら、節を落として記述はコードに担わせる
こと。

### 2. 基準を述べる。禁止は、基準が尽きる場所にだけ置く

基準は何でも置ける — このドキュメントがまだ見たことのないものも含めて。禁止は一つの経路を閉じ、空間の
残りを地図のないまま残すので、読み手は依然として判断できない。一つの答えが誤りだと知るだけである。

- **基準**：**何がそれを決めるか**を、このドキュメントが見たことのない事例にも読み手が適用できる形で述べる。
  「スキルは、ブリーフから成果物を生み出すなら fork する。すでにモデルの目の前にある作業に作用するなら
  メインスレッドに留まる。」
- **禁止**：閉じられているもの。**基準に従った読み手がそれでもぶつかることになる場所にのみ**、その壁として
  ドキュメントに置く — これは `dont-make-me-read` の制約についてのルールを、ここに適用したものである。

見出しがこれを最初に露呈する。「X は Y ではない」「X は Z をしない」という形の見出しは Don'ts の節を予告
する。同じ節をその判断で題すれば（「入口がどこに住むか」）、基準が本文に出てくるほかなくなる。

数えるのが安いチェックである：ドキュメントの見出しの大半が否定形なら、下の散文が何を言っていようと、それは
Don'ts の一覧である。

### 3. 分類は、分類すると宣言した対象をすべて覆う

ドキュメントが存在するものを分割するとき — 層、種類、カテゴリ — 既存のすべてがちょうど一つのバケツに
着地し、読み手は同じ分割で新しいものを置ける。

8つのうち3つを挙げる表は、その分割が信頼できないことを読み手に教え、彼らはそれを判断に使うのをやめる。
全部になるまで広げるか、主張するものを狭めるかのどちらか：**3つの例**の表は誠実で有用である。**その層**
として提示された表は、全部を持たない限りそうではない。

### 4. 判断が必要とするものを言い直す。他のファイルが所有する定義を導き直さない

終了コードは、それを返すスクリプトのものである。frontmatter のフィールドは、それをパースするプラット
フォームのものである。何が存在するかの一覧は、それを収めるディレクトリのものである。

区別は「繰り返してよいか」ではない — `avoid-reference-detours` がすでにそれに答えている：**この読み手が
行動するために必要な部分**を、その仕事を果たす最短の形で持ってくること。区別は、あなたが持ってきたのが
**判断の入力**なのか、**二つ目の定義**なのかである：

| | 持ってくるもの |
|---|---|
| 読み手が今何かを決めねばならない | それを決着させる部分 —「非ゼロならまだコミットしない」 |
| 他のファイルがその物を定義している | 列挙ではなくポインタ — どのコードが何を意味するかはスクリプト自身のヘッダにある |

テスト：**そのファイルが変わったとき、このドキュメントは誤りになるか？** なるなら、定義をコピーしている。
ならないなら、入力を言い直している。

## Organising the file（ファイルの組み立て）

**判断で索引する。部品でではない。** 貢献者は一つの問いを持って到着し、それを見つけるために走査するのは
見出しである。だから判断を名指しする見出しは到達可能で、部品を名指しする見出しは到達可能でない。

設計ドキュメントは、リポジトリを変更する誰にとっても必須経路に座る。だから上限がかかるのは**彼らが来た
判断までの距離**であって、ファイルの総量ではない。見出しが判断になっている長いファイルは、端から端まで
読まねばならない短いファイルより安い。

## Language（言語）

その貢献者がすでに使っている言語 — リポジトリの言語 — で書く。上の条件は、そのドキュメントが**何を決着
させるか**についてのものであって、どの言語が決着させるかではない。ここの実例が英語なのは、このスキルが
英語だからにすぎない。

## Common Rationalizations（よくある自己正当化）

| 自己正当化 | 実際のところ |
|---|---|
| 「今どうしているかを説明することが設計だ。」 | 今どうしているかはコードが示している。より速く、ドリフトもなく。コードが示せないのは、次の判断を何が決めるかである — このファイルが足すものはそれだけだ。 |
| 「禁止こそが本体で、基準は自明だ。」 | それが自明なのは**あなた**にとってである。あなたはそれを導いた基準をすでに持っている。読み手が受け取るのは、閉じられた一つの経路と地図のない空間であり、残りは推測するしかない。 |
| 「この表は面白いケースだけを挙げている。」 | ならそう表自身の言葉で言うこと。分類として提示された部分的な表は、何も置けないことを読み手に教える — 彼らが置きに来たものも含めて。 |
| 「代替案ではなくこちらを選んだ理由を記録するのは有用な経緯だ。」 | 根拠は残り、審議は落ちる（`avoid-unverifiable-context`）。代替案を排除する制約を、読み手がぶつかることになる壁として書け。二人でそれを天秤にかけた顛末ではなく。 |
| 「フィールド一覧をここに写せば読み手の往復が減る。」 | 往復は一つ減り、独立に古びる二つ目の定義が一つ増える。判断が必要とするものを持ってきて、それを定義しているものを指せ。 |
| 「自分には問題なく読める。」 | あなたはすでに持っている基準を自分で補っている。このファイルを開き、実装を閉じている誰かとして判断せよ — それこそが失敗モードのすべてである。 |

## Related skills（関連スキル）

- `dont-make-me-read` — このスキルが鋭くしているテストと、制約を「読み手がぶつかることになる壁として」
  述べるルール。
- `avoid-unverifiable-context` — 根拠を残しつつ審議を締め出すもの。
- `avoid-reference-detours` — 使用地点で何を言い直すか。条件4はそれを、他のファイルが所有する定義について
  狭めたものである。
- `write-nice-skills` — `SKILL.md` はエージェントへの指示であって設計ドキュメントではない。このスキルは
  あのスキルが始まる場所で終わる。
