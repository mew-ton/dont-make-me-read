## Overview（概要）

コメントとして書かれる指示 — PR レビューの指摘、変更を提案する返信、修正を依頼する所見 — の読み手は返答
できる。それが規則との違いである。読み手は最初の数行で、行動するか、流し読むか、反論するかを決める。そして
基準は読み手のものである：以下の予算が存在するのは、人がそれだけ速く決めるからだ。

## Language（言語）

指摘は、その読者がすでに使っている言語で書く — リポジトリの言語、レビュースレッドの言語、周囲のコメントの
言語。以下のすべてのルールは指摘の**形**についてのものである。Title / Summary / Details、予算、強さの行は、
どの言語で投稿しようと同じように適用される。

翻訳された指摘がたいていつまずく場所：

- **予算は投稿する言語で数える。** ある言語では20行に収まり別の言語では収まらない Details は、後者では
  予算超過であり、対処はいつもと同じ — たいていは折り返しの問題ではなく、一つに二つの指示が入っている。
- **同じ指摘を二つの言語で二度投稿しない。** 一つの指摘、一つの言語。バイリンガルのコメントは読むコストを
  倍にし、実際にはいくつの別々の論点が述べられたのかを隠す。

## One instruction, one application（一つの指示に一つの適用）

テンプレートは**指示1つにつき1回**適用する — 複数を含む文書1つにつき1回では決してない。

| 成果物 | 適用回数 | Title | Summary | Details |
|---|---|---|---|---|
| PRレビュー | **指摘ごとに1回** | その指摘の先頭行（`**<severity>** — <fact>`） | その指摘の書き出し | summary が how / why を担っていないときだけ |

Details を書く前に [`rules/one-instruction-one-application.md`](rules/one-instruction-one-application.md)
を読むこと — 下書きがすでに一つの Title の下に二つの適用を抱えているという兆候、同じものを後から
捕まえる溢れのシグナル、そして実例を担っている。どれか一つでも当てはまれば、Details を書く前に分割する。

## The template（テンプレート）

| 部分 | そこに入るもの | 予算 |
|---|---|---|
| **Title** | 観測された**事実**、それだけ — **それが破っているルールの水準**で述べる。それを証明する証拠の水準ではない。パス、引用された識別子、その事例に固有の比較は、たいてい証拠であって Summary に属する（例外は下記のルールファイル）。依頼ではなく、評価でもなく、それがどう感じさせたかでもない。 | **一文** — 二文目が要るなら、残りは Summary |
| **Summary** | 事実と、それについて何をすべきか。読み手はこれだけから行動できる。 | **短い記述を最大3つのリスト** — 1つにつき1事実か1指示 |
| **Details** | その修正の背後にある how と why。summary がすでにそれらを担っているなら省く。 | **20行**、コードブロックを除く |

Title を書く前に下記のルールを読むこと — それぞれが実例を一つ持っている：

- [`rules/avoid-negating-the-request-as-the-fact.md`](rules/avoid-negating-the-request-as-the-fact.md)
  — 否定された依頼は観測ではない。
- [`rules/avoid-fusing-the-instance-into-the-title.md`](rules/avoid-fusing-the-instance-into-the-title.md)
  — ルールと、それを破った一つの事例を見分けるための swap test、そしてパスが本当に事実である例外。
- [`rules/avoid-naming-sampled-paths-as-the-fix.md`](rules/avoid-naming-sampled-paths-as-the-fix.md)
  — 指摘の背後にある性質が機械的にチェック可能なとき、そのチェック自体を述べる。

**Summary は段落ではなくリストである。** 各記述をそれ自身の箇条書きとして書き、それぞれを短い一文に保つ。
3行の段落は指示を従属節の中に隠してしまい — 「呼び出し側はどのフィールドが失敗したか分からないので、
〜のほうがよいかもしれない」 — 実際にいくつの別々の論点を述べたのかも隠す。箇条書きは両方を表に引きずり
出す：修飾が、それが修飾する文に収まらないなら、それは独立した記述であるか Details に属するかのどちらか
である。3つは目標ではなく上限であり、1つが普通で、そのほうが良い。**箇条書きであることと Summary である
ことは同じではない**：証拠のリスト — 何を確認したか、表の中身 — は、形を変えただけの Details である。

Details について、**行**とは、あなたが書いている幅での1行の書かれた行を指す — GitHubのコメントは100文字
付近で折り返す — なので20行はおよそ2000文字である。数を合わせるために折り返し直すのは修正ではない。1行
200文字にして初めて収まるなら、それは収まっていない。**フェンス付きコードブロックだけ**が除外される —
Details 内の表、リスト、小見出しは書かれた行として数えるので、表にしても何も買い戻せない。Title は文数で
数える。タイトルは自分の意思で折り返すものではないからだ — 長い Title はたいてい二つの事実であり、二つ目は
Summary に属する。記述3つに収まらない Summary は、たいてい**二つ目の適用**である
（[`rules/one-instruction-one-application.md`](rules/one-instruction-one-application.md)）。

## How firmly to state the remedy（対処をどれだけ強く言い切るか）

実際に擁護できるものによって、一つを選ぶ：

| 手持ちのもの | どう書くか |
|---|---|
| **擁護できる修正が一つ** | 取るべき唯一の修正として言い切る。却下した選択肢は、それを排除する制約としてのみ現れてよい — 読み手に差し出される選択肢としては決して現れない。 |
| **複数の修正があり、どれでも本当に構わない** | 重みづけなしで、フラットに並べる。 |
| **名指しできる修正がない** | 目標を**問題を登録すること**に切り替える：issue を立て、そのコードのコメントからリンクする。 |

強さは**重大度と直交する**：`critical` / `major` / `minor` / `nit` はその指摘がマージを止めるかどうかを
言い、強さは対処をどれだけ強く述べるかを言う。`major` に既知の修正がない（行3）こともあれば、`nit` に
ちょうど一つある（行1）こともある。

Summary の修正を書く前に [`rules/remedy-strength.md`](rules/remedy-strength.md) を読むこと — 三つの行の
選び方、コメントとコードの矛盾に対する注意（自動的に行1にはならない）、各行の実例を担っている。

## Fitting the budget（予算に収める）

下書きを削る前に [`rules/fitting-the-budget.md`](rules/fitting-the-budget.md) を読むこと — 何を、なぜ削る
のか、そして唯一の例外（コードブロック内のかさばる証拠は予算の外に座る）を担っている。

## Common Rationalizations（よくある自己正当化）

| 自己正当化 | 実際のところ |
|---|---|
| 「すべての選択肢を挙げるのが誠実だ。」 | 却下した選択肢はあなたの文脈であって、読み手の文脈ではない。メニューは彼らに情報を与えず、判断をあなたより情報の少ない者に移すだけである。擁護できる修正を言い切れ。フラットなリストは本当に互換な選択肢のために取っておけ。 |
| 「修正を一つ言い切るのは押しつけがましい。」 | 強さは判断がどこに座るかについてのものであって、口調についてではない。擁護できる修正をヘッジすると、読み手はあなたの判断を代わりに背負うことになり、彼らのほうが下手にそれを背負う。丁寧さは言葉遣いに宿るのであって、曖昧さに宿るのではない。 |
| 「修正がないので、提案として軟化させておく。」 | 裏付けのない柔らかな提案は、あなたが一度も持っていなかった修正を読み手に探させに行かせる。登録せよ：issue を立て、コードからリンクする。 |
| 「20行では説明を担えない。」 | ほぼ常に一つに二つの指示が入っている — 分割せよ（兆候がもっと早く捕まえる）。本当に一つなら、超過分はリンク先の issue に属するのであって、Details ではない。 |
| 「箇条書きの summary より段落のほうが自然に読める。」 | それが自然に読めるのは**あなた**にとってである。どの節が指示なのかをすでに知っているから。読み手にとって散文は、依頼を従属節に隠させ、いくつの論点が述べられたのかを隠させる。箇条書きは両方を数えられるようにする — 書くときに窮屈に感じるのは、まさにそのためである。 |
| 「先に背景を置くほうが読み手に親切だ。」 | Title と Summary が事実と修正であり、なぜは Details に行く。summary の3つの記述の後で行動できない読み手は読むのをやめ、背景には決して到達しない。 |
| 「同じファイル／同じPRの話だから、一つの指摘だ。」 | 単位は**対処**であって、主題ではない。異なる編集 — あるいは片方を受け入れつつもう片方に異議を唱えうるもの — なら二つの適用である。束ねると、あなたがすでにできたはずの分割を読み手にやり直させることになる。 |
| 「自分には問題なく読める。」 | あなたは読みながら、テキストに欠けている意図を自分で補っている。テキストだけを手にしている人間として判断せよ — それこそが失敗モードのすべてである。 |
| 「どんな依頼も否定すれば事実にできる。」 | 依頼を否定しても文法が変わるだけで、内容は変わらない — 「ライブラリ `A` が導入されていない」は「ライブラリ `A` を導入せよ」と同じ情報しか担っていない。事実は上流になければならない：その依頼が応答しているところの、コード内の振る舞いである。 |
| 「Title にファイル名を入れるほうが正確だ。」 | 誤った水準での正確さは、ルールではなく証拠として読まれる。読み手は問題の住所を必要とする前に、問題の形を認識する必要がある — ファイルは Summary の最初の箇条書きに置き、Title は他所を指してもまだ真として読めるかで swap test にかけよ。 |
| 「コメント／仕様は意図された振る舞いを記述しているのだから、コードをそれに合わせるのが修正だ。」 | より自信ありげに、より完全に読めることは、それが現在のほうだという証拠ではない — コメントのほうが古びた半分でありうる。PR や issue がその差を意図的なスコープ分割として開示しているなら、コードを追いつかせるのは、レビュアーではなく著者に属するスコープの問題を決めてしまうことになる。どちらか一方を実際に支持する独立した証拠 — grep、片方が古いという明示 — がない限り、それは行2である。 |
| 「このスキルの実例が英語なので、指摘も英語にすべきだ。」 | 実例が英語なのはスキルが英語だからである。リポジトリのレビューがすでに使っている言語で投稿せよ — このスキルが固定するのは形であって、言語ではない。 |

## Red Flags（危険信号）

- Title が、破られた規則ではなく、その証拠であるパスや識別子を担っている。
- Title が依頼、評価、あるいはどう感じたかになっている。
- Summary が段落になっていて、指示が従属節の中に隠れている。
- 擁護できる修正があるのに、選択肢が並べられている。

## Verification（検証）

- [ ] Title は一文で事実を担っており、依頼・判断・心情が混ざっていない。
- [ ] Title は同じ規則の別の事例に向けてもなお真である。あるいはその場所が本当に唯一の事例である。
- [ ] Summary は短い記述が最大3つ、それぞれ事実か指示のどちらか一つである。
- [ ] Details はコードブロックを除き、投稿する言語で数えて20行以内、あるいは存在しない。
- [ ] 対処は、ヘッジなしで言い切られているか、重みづけなしで並べられているか、問題として登録されているか
      のいずれかであり、実際に擁護できる範囲と一致している。
- [ ] 一つの編集で指摘全体に答えられ、そのすべての部分が一つの強さの行に収まっている。
- [ ] 機械的にチェック可能な性質は、サンプルしたパスとしてではなくチェックそのものとして述べられている。
- [ ] 残っているどの行も読み手の行動を変え、全体が一つの言語で書かれている。

## Related skills（関連スキル）

- `dont-make-me-read` — このスキルが研ぎ上げるテスト：指摘は、読み手が行動する前に抱えねばならない量で
  判定される。
- `avoid-unverifiable-context` — 読み手が、その指摘の主張を確認できるか：根拠は残り、それが出てきた
  プロセスは落ちる。
- `avoid-reference-detours` — 読み手がそれを理解するためにどこかへ送られたか、そして代わりに使用地点で
  何を言い直してよいか。
- `write-nice-issue-description` — 問題の記述＋完了条件であり、リポジトリを読める実装者に読まれるもの。
  このスキルはあちらが始まるところで終わる。
- `write-nice-instructions-as-rule` — その指示が効力を持ち続ける場合の、同じ要求：ガイドライン、規約、あるいはスキル本文の
  中の規則。それらは、その規則が捕まえた者によって順番どおりでなく読まれる。
