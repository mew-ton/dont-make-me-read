## Overview（概要）

このスキルは、コメントとして書かれる指示を、その読み手が最初の数行から行動できるように起草し、改稿する。
コメントには返答できる読み手がいる。それが規則との違いである。そしてその数行の内側で、読み手は行動するか、
流し読むか、反論するかを決める。指摘は、その読み手が行動する前に抱えねばならないもので判定される。以下の
予算が厳しいのは、人がそれだけ速く決めるからだ。

## How to work（どう進めるか）

- **一行を書く前に、その一つの指示が何かを決着させる。** 単位は対処であって主題ではない：一つの編集で
  指摘全体に答えられ、二つ目の編集を要する部分は二つ目の指摘である。
- **Title、次に Summary、次に Details の順で書き、読み手が行動できるようになった時点で止める。**
- **修正を言葉にする前に、実際に擁護できるものから強さの行を選ぶ。**
- **予算には、読み手の行動を変えないものを取り除いて収める** — 散文を圧縮したり行を折り返し直したりして
  収めるのでは決してない。
- **下書きを、テキストだけを手にしている人間として判断する。** あなたは読みながら、テキストに欠けている
  意図を自分で補っている。それこそが失敗モードのすべてである。

## One instruction, one application（一つの指示に一つの適用）

テンプレートは**指示1つにつき1回**適用する — 複数を含む文書1つにつき1回では決してない。PRレビューでは
それは**指摘ごとに1回**である：Title はその指摘の先頭行（`**<severity>** — <fact>`）であり、Summary は
その書き出しである。

**下書きがすでに一つの Title の下に二つの適用を抱えているという兆候：**

- Title が一つを述べる代わりに二つの事実を接続している（「…かつ…も」）。
- Title が事例を数えている（「4箇所」）が、それらが同じ編集で閉じない。
- 部分が異なる強さの行に座っている — 一方には修正があり、他方にはない。
- Details が小見出しを欲しがっている。その見出しこそが二つ目の指示の名前である。

どれか一つでも当てはまれば、Details を書く前に分割する。

**溢れは同じシグナルを、後から捕まえたもの。** 20行に収まらない Details は、たいてい一つの適用を共有して
いる二つの指示である — キャッシュキーが乖離していること**と**、同じURL復元パターンをさらに3つの一覧画面へ
展開すること。これらは異なる担当者、異なる受け入れ基準、異なるレビュー結果を持つ：指摘は一方に留め、もう
一方は別途起票せよ。3つの記述に収まらない Summary は、同じシグナルを一段早く捕まえたものである — 4つ目の
箇条書きが別の事実ならそれは Details であり、別の指示ならそれは別の適用である。

二つを一緒に起票すると、弱いほうの半分が強いほうの下に隠れる：言い切られた修正を適用した読み手は指摘全体が
解決したとみなし、誰も対処しなかった部分もそれと一緒に消える。

## The template（テンプレート）

| 部分 | そこに入るもの | 予算 |
|---|---|---|
| **Title** | 観測された**事実**、それだけ。下記のルールが定める水準で述べる。依頼ではなく、評価でもなく、それがどう感じさせたかでもない。 | **一文** — 二文目が要るなら、残りは Summary |
| **Summary** | 事実と、それについて何をすべきか。読み手はこれだけから行動できる。 | **短い記述を最大3つ** — 1つにつき1事実か1指示 |
| **Details** | その修正の背後にある how と why。summary がすでにそれらを担っているなら省く。 | **20行**、コードブロックを除く |

**Summary は段落ではなくリストである。** 箇条書き1つにつき短い一文。3行の段落は指示を従属節の中に隠して
しまい — 「呼び出し側はどのフィールドが失敗したか分からないので、〜のほうがよいかもしれない」 — 実際に
いくつの別々の論点を述べたのかも隠す。箇条書きは両方を表に引きずり出す。修飾が、それが修飾する文に収まら
ないなら、それは独立した記述であるか Details に属するかのどちらかである。3つは目標ではなく上限であり、
1つが普通で、そのほうが良い。**箇条書きであることと Summary であることは同じではない**：証拠のリスト —
何を確認したか、表の中身 — は、形を変えただけの Details である。

Details について、**行**とは、あなたが書いている幅での1行の書かれた行を指す — GitHubのコメントは100文字
付近で折り返す — なので20行はおよそ2000文字である。数を合わせるために折り返し直すのは修正ではない。1行
200文字にして初めて収まるなら、それは収まっていない。**フェンス付きコードブロックだけ**が除外されるので、
Details 内の表、リスト、小見出しは書かれた行として数え、何も買い戻せない。Title は文数で数える。タイトルは
自分の意思で折り返すものではないからだ。

## The rules（規則）

どれも、上の各部分をどう書くかについての条件であり、下書きに対する指摘は、そのどれが破られたのかを
名指しする。

### Title は、それを破った一つの事例ではなく、ルールを述べる

Title は一つの誠実な事実でありながら、なお誤った水準に座りうる：それを破った一つの事例と融合している、と
いう誤りである。**swap test** — 同じ Title は、別のファイルを指してもまだ真として読めるか？ 読めないなら、
そのファイル、その比較、その理由づけは事実ではなく証拠であり、Summary に個別の箇条書きとして — どこで、
次になぜ、次に修正、の順で — 属する。1ファイルを名指しした Title の下で、Summary がすでにその傾向は他所
にも現れると述べているなら、それは自らの申告によってこのテストに落ちている。

**これはあらゆるパスを Title から剥がせという意味ではない。** `` `validate.ts:14` returns no field name
on a validation failure ``（訳：「`validate.ts:14` はバリデーション失敗時にフィールド名を返さない」）は
パスを保つ。その場所**こそ**が事実だからである：同じ振る舞いを示すものが他になく、事例の上に抽象化すべき
ルールが存在しない。決める前に swap test を走らせよ — 指摘が再発しうるパターンについてのものなら、証拠は
Summary に行く。

### 依頼を否定したものを事実と呼ばない

「これを名前付きの computed に抽出せよ」を「名前付きの computed に抽出されていない」と書き換えたものは
チェック可能ではあるが、それでも Title の形をまとった依頼である：求められたものの不在を名指ししており、
その依頼以上の情報を担っていない。事実は依頼の上流に座っている — その依頼が応答しているところの、今日
コードがやっていることである。「複合条件がテンプレートに直接書かれている」が事実であり、「computed に
抽出されていない」は依頼の反転である。

これは、指摘が壊れているものを報告するのではなく、より良い案を提案する場合にも当てはまる。上流の事実は、
なぜコードが壊れているかである必要はなく、なぜコードが今日この形をしているかでもよい。決して、提案自身の
否定ではない。

### 対処は、擁護できる限りの強さで言い切り、それ以上には言い切らない

行を一つ選ぶ。ここは生成されたテキストが誤る軸である：どの行にいてもフラットな選択肢のメニューに手を伸ばして
しまい、それはバランスが取れているように読めて、判断を読み手に丸投げする。

| 手持ちのもの | どう書くか | やってはいけないこと |
|---|---|---|
| **擁護できる修正が一つ** | 取るべき唯一の修正として言い切る：「`path/to/validate.ts:22` がやっているように `ValidationError` で直す」。却下した選択肢は、**それを排除する制約としてのみ**現れてよい — 読み手がそうしなければぶつかっていた壁として — 決して差し出される選択肢としてではない。 | 却下した代替案を選択肢として提示しない。選んだものをヘッジしない（「〜を検討する価値があるかもしれない」）。どちらもあなたの判断を読み手に返してしまう。 |
| **複数の修正があり、どれでも本当に構わない** | 重みづけなしで、フラットに並べる。 | 順序、長さ、言葉遣いを通じて選好を忍び込ませない。選好があるなら、それは行1である — そう言え。 |
| **名指しできる修正がない** | 目標を**問題を登録すること**に切り替える：issue を立て、そのコードのコメントからリンクする。 | 枠を埋めるために曖昧な提案をでっち上げない。解けないからといって指摘を落とさない。 |

**フラットなリストは最後の手段であって、既定値ではない。** 3つの選択肢を挙げようとしているときは、まず行1を
確認せよ：少しでも重みづけできるなら、それは行1であり、一つの言い切られた修正である。行2は、その選択を本当に
レビューしないであろう選択肢のためにある。

**修正を「採用するかは任意」と示すことは、それをヘッジすることではない。** nit は、今日何も壊れていないと
明言したうえで、もし対処するならこれが取るべき修正だと具体的に言い切ってよい — 修正は自信をもって述べられて
おり、読み手に委ねられているのは今それに手をかける価値があるかどうかだけである。それは「〜を検討する価値が
あるかもしれない」とは異なる。後者は修正の**正しさそのもの**をヘッジしている。

**コメント（あるいは仕様、AC）とコードの矛盾は、自動的には行1にならない。** コメントがAと主張しコードがBを
していることは、両者が食い違っていることを教えるのであって、Aが正しくBがバグであることを教えるのではない：
より完全で、より意図的に見える散文は、コードがすでに追い越した古びた計画でも同じようにありうる。どちらか
一方を実際に支持する証拠 — 記述された振る舞いにもはや呼び出し元がないことを示す grep、片方が古いという明示、
他の行1の修正が引くのと同じ証拠 — がない限り、これは行2である：二つの修正をフラットに並べ（「コメントの言う
通りにコードを引き上げるか、コードがやっていることを言うようにコメントを直すか」）、著者自身のスコープ判断に
選ばせよ。開示されたスコープ分割 — 後続チケット、「まだ繋いでいない」という注記、`TODO(#N)` — は最も明快な
ケースである：それは食い違いが意図的だと教えるが、どちらが誤りかは教えない。その不在もまた証拠ではないので、
誰も説明していないコメントは、何かが一方を支持するまで行2の既定値のままである。

強さは**重大度と直交する**：`critical` / `major` / `minor` / `nit` はその指摘がマージを止めるかどうかを
言い、強さは対処をどれだけ強く述べるかを言う。`major` に既知の修正がない（行3）こともあれば、`nit` に
ちょうど一つある（行1）こともある。

行3のために立てられる issue はそれ自体が決定のための issue である：何が決められねばならないか、何がそれを
決着させるかは、その issue 自身の本文 — このテンプレートではなく `write-nice-issue-description` で書かれる
— に着地し、指摘のほうは事実と、それを登録せよという指示と、修正を名指しできない理由を担う。「調査が必要」
だけでは行3ではない。それは作業が抜け落ちた行3である。

### 読み手がすでに使っている言語で書く

リポジトリの言語、レビュースレッドの言語、周囲のコメントの言語である。ここにあるすべてのルールは指摘の**形**
— Title / Summary / Details、予算、強さの行 — についてのものであり、どの言語で投稿しようと同じように適用
される。翻訳された指摘がつまずく場所は二つ：

- **予算は投稿する言語で数える。** ある言語では20行に収まり別の言語では収まらない Details は、後者では
  予算超過であり、対処はいつもと同じ：折り返しの問題ではなく、一つに二つの指示が入っている。
- **同じ指摘を二つの言語で二度投稿しない。** バイリンガルのコメントは読むコストを倍にし、実際にはいくつの
  別々の論点が述べられたのかを隠す。

## Common Rationalizations（よくある自己正当化）

| 自己正当化 | 実際のところ |
|---|---|
| 「すべての選択肢を挙げるのが誠実だ。」 | 却下した選択肢はあなたの文脈であって、読み手の文脈ではない。メニューは彼らに情報を与えず、判断をあなたより情報の少ない者に移すだけである。擁護できる修正を言い切れ。フラットなリストは本当に互換な選択肢のために取っておけ。 |
| 「修正を一つ言い切るのは押しつけがましい。」 | 強さは判断がどこに座るかについてのものであって、口調についてではない。擁護できる修正をヘッジすると、読み手はあなたの判断を代わりに背負うことになり、彼らのほうが下手にそれを背負う。丁寧さは言葉遣いに宿るのであって、曖昧さに宿るのではない。 |
| 「修正がないので、提案として軟化させておく。」 | 裏付けのない柔らかな提案は、あなたが一度も持っていなかった修正を読み手に探させに行かせる。登録せよ：issue を立て、コードからリンクする。 |
| 「20行では説明を担えない。」 | ほぼ常に一つに二つの指示が入っている — 分割せよ。兆候がもっと早くこれを捕まえる。本当に一つなら、超過分はリンク先の issue に属するのであって、Details ではない。 |
| 「箇条書きの summary より段落のほうが自然に読める。」 | それが自然に読めるのは**あなた**にとってである。どの節が指示なのかをすでに知っているから。読み手にとって散文は、依頼を従属節に隠させ、いくつの論点が述べられたのかを隠させる。箇条書きは両方を数えられるようにする — 書くときに窮屈に感じるのは、まさにそのためである。 |
| 「先に背景を置くほうが読み手に親切だ。」 | Title と Summary が事実と修正であり、なぜは Details に行く。summary の3つの記述の後で行動できない読み手は読むのをやめ、背景には決して到達しない。 |
| 「同じファイル／同じPRの話だから、一つの指摘だ。」 | 単位は**対処**であって、主題ではない。異なる編集 — あるいは片方を受け入れつつもう片方に異議を唱えうるもの — なら二つの適用であり、束ねると、あなたができたはずの分割を読み手にやり直させることになる。 |
| 「自分には問題なく読める。」 | あなたは読みながら、テキストに欠けている意図を自分で補っている。テキストだけを手にしている人間として判断せよ — それこそが失敗モードのすべてである。 |
| 「どんな依頼も否定すれば事実にできる。」 | 依頼を否定しても文法が変わるだけで、内容は変わらない — 「ライブラリ `A` が導入されていない」は「ライブラリ `A` を導入せよ」と同じ情報しか担っていない。事実は上流になければならない：その依頼が応答しているところの、コード内の振る舞いである。 |
| 「Title にファイル名を入れるほうが正確だ。」 | 誤った水準での正確さは、ルールではなく証拠として読まれる。読み手は問題の住所を必要とする前に、問題の形を認識する — ファイルは Summary の最初の箇条書きに置き、Title は swap test にかけよ。 |
| 「コメント／仕様は意図された振る舞いを記述しているのだから、コードをそれに合わせるのが修正だ。」 | より完全な側に読めることは、それが現在のほうだという証拠ではない。コメントのほうが古びた半分でありうる。コードを直すものとして言い切ることは、著者に属するスコープの問題まで決めてしまう。grep か明示がどちらか一方を支持しない限り、行2である。 |
| 「このスキルの実例が英語なので、指摘も英語にすべきだ。」 | 実例が英語なのはスキルが英語だからである。リポジトリのレビューがすでに使っている言語で投稿せよ — このスキルが固定するのは形であって、言語ではない。 |

## Red Flags（危険信号）

- Title が、破られた規則ではなく、その証拠であるパスや識別子を担っている。
- Title が、依頼に「〜でない」を差し込んだだけのものになっている。
- Title が依頼、評価、あるいはどう感じたかになっている。
- Summary が段落になっていて、指示が従属節の中に隠れている。
- 擁護できる修正があるのに、選択肢が並べられている。
- 修正が、たまたまサンプルしたファイルに縛り付けられている — 「これらを圧縮せよ」。
- Details の中に小見出しがある。
