# 予算に収める

下書きが長くなっているとき、その散文を圧縮する前にこれを読むこと。

3つの記述と20行は、散文を圧縮して達成できるものではない。読み手の行動を変えないものを取り除くことで達成
できる：

| 削るもの | なぜ |
|---|---|
| 前置きとメタ叙述（「このPRをレビューしました」「以下で詳細を説明します」） | 読み手は自分が何を開いたか知っている。事実から始めよ。 |
| 賞賛とクッション | 行動を担わず、その後に来る指摘を薄める。 |
| 引用して返されたコード、差分、issue のテキスト | 読み手はそれを持っている。代わりに `path:line` を指せ。 |
| 何を確認したかの棚卸し | 指示ではなくプロセスである。 |
| 同じ論点が summary と details と締めの一行に | 読み手が行動する場所で、一度だけ言え。 |
| 仕様の代わりに立つ曖昧な数量詞（「適宜」「必要に応じて」） | 完全であるかのように読め、何も規定していない。 |
| 同じ指摘を第二言語で言い直したもの | 一つの指摘、一つの言語。翻訳は二つ目のコピーであって、二つ目の論点ではない。 |

それでも Details が20行に収まらないなら、それはたいてい**一つに二つの指示**が入っている：さらに圧縮する
のではなく、兆候に戻って分割せよ。

**例外は、証拠がかさばるケース** — 測定の表、再現ログ。コードブロック内の証拠は予算の外に座るが、散文で
語られた証拠はそうならないので、ブロックの中に入れること。表そのもののサイズが Details を溢れさせる段階に
なったら、実際に投稿するテキストの中でその表自体をフェンスで囲め。
