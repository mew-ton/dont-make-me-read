# description を書く

スキルの `description` や frontmatter を書く／レビューするときに読むこと。`description` は、エージェントが
そのスキルを発火させるかどうかを決めるときにロードされる唯一のテキストなので、それ単体で判断可能でなければ
ならず、手順を漏らしてはならない。

どの description も満たすべきこと、どれも担ってはならないこと、そして違いを生む文体 — そのあとにサイズ
制限と、それが収まる frontmatter。

## 1. どの description も満たすべきこと

スキルによっては、どんな書き方をしても節3を綺麗には満たせない構成のものがある。以下はそれでも成り立ち、
それがエージェントの判断に使えるすべてである。

### 1.1 三人称で書く

description を読むのは、そのスキルをロードするかどうかを決めているエージェントであって、話しかけられて
いる誰かではない。スキル**について**書くこと — スキルとして書くのでもなく（「私はあなたの issue を検査
します」）、読み手に向かって書くのでもない（「あなたは〜の専門家です」）。言明は手元の作業に照らして判断
できるが、呼びかけはできない。

残る命令形は節 1.3 の `Use this skill when …` であり、それが残るのは、三人称なら落ちてしまう主語を
名指しするからである。

### 1.2 スキルが何をするかを書く

一節で。そして一節が予算でもある。エージェントが知る必要があるのは、自分が何を選ぼうとしているかであって、
その選択がどう遂行されるかではない。「呼ばれた側が、どの呼び出し元から呼ばれたかで分岐するのを防ぐ」は
問いを決着させる。そういう callee を見つけるためのテストは決着させないし、本文に属する。

### 1.3 スキルをいつ適用するものかを書く

機会を名指しする — 書かれつつある成果物か、進行中の活動か。

そしてそれをこのスキル自身の機会として名指しする：主語のない `Apply when …` ではなく
`Use this skill when …`。主語のない形は主語を推測に委ねるが、description が開いたままにできない唯一の
ものが、その文が作業を記述しているのか、それともそのスキルについて読み手に指示しているのか、である。
主語を名指しすることがそれを買う。

### 1.4 英語で書く

どの言語でプロンプトを打とうと description は英語で書く。英語の用語こそが、どんな場合でもプロンプトに
生き残るもの — ファイル名、ツール名、ライブラリ名 — であり、公開するスキルは利用者がどの言語で打つか
知り得ない。

ここで決着するのは description の言語だけで、他のどれでもない。**本文**は、一つのチームを越えて出荷する
スキルならこれも英語である。エージェントが読むので。**スキルが生み出す出力** — issue、指摘、ドキュメント —
は*その*読み手がすでに使っている言語に属し、それは各 writing スキルが自分で述べる。このファイルの英語を、
スキルがエージェントに何を書けと指示するかにまで持ち下ろさないこと。

## 2. description が決して担ってはならないもの

これもまた、スキルの構成が他を強いる場合でも：以下のどれも description には属さない。

### 2.1 手順

手順を追った指示を description に決して置かない。手順がそこにあると、エージェントは description からそのまま
行動できると信じて本文を決してロードせず、そのスキルが届けるために存在する指示が飛ばされる。*what* と
*when* を述べ、*how* は本文に留めよ。

**どのスキルがどのスキルへ引き渡すかもまた手順である。** 「より大きなレビューの一つの軸として、あるいは
`/x` コマンドから走らせる」は文脈のように読めるが、そうではない — それはこのスキルが**どう使われるか**を
エージェントに伝えており、まさに本文を任意のものに見せる類の行である。呼び出し元と引き渡しは本文で、
それらに依存する手順が住んでいる場所で名指しせよ。

### 2.2 そのスキルが適用する判定基準

そのスキルが何を検査するかを列挙する description —「決定可能な問題、検査可能な受け入れ条件、スコープ外の
境界」 — はエージェントに判定基準そのものを手渡しており、判定基準を握ったエージェントには、それを限定する
本文をロードする理由がない。そのスキルが何に対するパスであるかを述べ、何を通すかは本文に留めよ。

これは `Forces the X that Y.` の行が最も陥りやすい失敗である。担うのは姿勢であり、そこで止める：その姿勢が
どんな基準で適用されるかは本文のものである。

### 2.3 他所の名前

別のスキル、別のファイル、これを呼ぶ誰か。

**具体名はエージェントの推測を制限する。**
`DO NOT use for an architecture doc (that is write-nice-architecture-docs)` はルーティング表として読まれ、
それを手渡されたエージェントは、境界がそもそも存在する理由である問い — *この*成果物は自分のものか — を
問わなくなる。条件である成果物を名指しせよ。それを所有するスキルではなく。後者は棚についての事実である。

**サイズも食う。** どの名前も 1024 文字から文字数を使い、それを所有していたすべての description で、
改名された日にもう一度使わせる。リポジトリ自身の不変条件も同じである：スキルは自分の description によって
到達されるか、さもなくば到達されない。

残るのは到達節 —「also applies when another skill needs …」— であり、別のスキルが本当にこれに依存
しているときだけである。それはこのスキルが**いつ**該当するかを述べ、誰も名指ししない。

### 2.4 本文がすでに担っている素性

その規則の論拠も、破ったときの代償も、処方も。それらは役に立つように読めて、漏れた手順とまったく同じ失敗で
ある — 論拠と処方を持ったエージェントはすでにそのスキルを与えられており、本文をロードするとしても、すでに
信じていることを追認するために読む。

見分けのつく用語は残る。それはトリガーだからである：画面の名前がついた `variant` は作業がどう見えるかで
ある。それが読み手に何を払わせるかは本文が述べることであり、発火させるのは前者だけである。

## 3. 効果のある文体

### 3.1 what と when のどちらを先頭にするか決め、その行に強制力を持たせる

最初の1行はエージェントが最初に重みづけする行なので、*what* と *when* のうち、自力では得られないほうに
充てる。どちらかを決めるのは一つの問いである：**作業はその成果物を名指しするか。** — それは裏側から見れば、
そのスキルがその成果物とともに終わるのか、それとも自分をロードしたターンのあとも効いていなければならないのか、
という同じ問いである。

**名指しする → `when` を先頭に。** issue、README、`ARCHITECTURE.md`、`SKILL.md`、プルリクエスト：作業が
その語を口にし、その語がスキルを発火させ、そのあとスキルが何をするかは本文が説明する。機会を名指しして、
そこで止める。

```text
Use this skill when writing or revising a README, and when adding a section to
one that already exists. DO NOT use this skill when the artifact is an
architecture doc, reference documentation, a tutorial, or a changelog.
```

**名指ししない → そのスキルが何を強制するかを先頭に。** 誰かがコードを書いている、あるいはコメントを
書いているあいだ効いていなければならない規則は、まさに作業がそれを名指ししないときに最も必要とされる：
作業は依頼ではなく diff とファイルなので、共有すべき語が無く、その規則を求めるものが何も無い。そして誰も
名指ししない機会は、エージェントが diff の途中で忘れる機会である。だから名指しだけでは足りない。そのスキルが
課す姿勢を、`Forces the X that Y.` の形で述べる — 一節で、そのスキルが何をさせるかを述べてなお、読み手が
それを実行できないところに置く：

```text
Forces the fact restated at the point of use over the pointer that sends the
reader away to get it … Use this skill when writing a code comment, a docstring,
a PR description, or any text that points elsewhere to be understood. DO NOT use
this skill when the target does not exist …
```

`when` はそのあとに続き、その作業が行われる動詞で **活動** として名指しされる（"writing, revising,
reviewing, or designing code"）。そして節 3.2 の境界がここでは最も働く：活動は、`DO NOT` が止めるまで、
その内側にあるすべてに到達する。

これで一度は中に入る。その活動のあいだ中に留め続けるのは本文の仕事であり、本文はそう述べない限りそれが
できない — [`structuring-skills.md`](structuring-skills.md#staying-in-force) を参照。

自分がどちらを書いているか分からないなら、最初の1行より先にそれを決着させること。それは本文も
決めるからである。

### 3.2 発火しない条件を記載する

境界のない when はその近くにあるものすべてに発火するので、`DO NOT use this skill when …` と、それを除外する
条件で description を閉じる：このスキルと取り違えられる成果物、自分のもののように見えて違う場合。

これは description 自身の `when` を否定したものである — 文法が同じなので、対で読めばそれが使用条件の全体に
なる。別の形に流れた `DO NOT`（`DO NOT use for …`、素の列挙）は、トリガーのもう半分としては読まれなくなり、
雑学として読まれ始める。

`DO NOT` は、そのスキルが**生み出さないもの**も、それが取り違えの原因になっている場合には閉じる —
`DO NOT use this skill when what is wanted is a verdict on whether a dependency is worth keeping`。
それは出力の説明ではなく、依然として使用の条件である。

### 3.3 leading word を前に出す

スキルは、description の中の語が、エージェントが取り組んでいるものの中の語と合致したときに発火する。それが
プロンプトであることもある。そうでないことも多い：`/` メニューから隠されたスキル（`user-invocable: false`）は
作業の途中で発火し、利用できる語は作業そのものの中にあるもの — 編集中のファイル、書かれつつある成果物、
コードがすでに使っている用語 — だけである。したがって description に **leading word** — このスキルが必要と
されるときに現れる語、何がそれを生むにせよ — を仕込み、それが起動の仕事をする場所である先頭付近に置くこと。

`when` が先頭に来る場合、そこは同じ位置であり、一つの節が両方を担う：作業が供給する語こそが、そのスキルが
どの機会に該当するかを述べる語だからである。姿勢が先頭に来る場合は、共有すべき語がそもそも無かった —
それが姿勢を先頭に置かせた理由である — ので、leading word は一文あとの `when` を待つ。

- **形式**：自然な文の中にある leading word。スラッシュ区切りのタグ列（`Skill / SKILL.md / description —`）
  ではなく、キーワードとして飾り立てた依頼文でもない。
- **もっともらしい語ではなく、実在の語**：自分のプロンプト、ドキュメント、コードに実際に現れる用語を使う —
  キーワード*のように聞こえる*だけのでっち上げのラベルではない。
- **枝ごとにトリガー一つ**：別個の状況をそれぞれ一度ずつ名指しする。同じ枝を言い換えただけの同義語は重複で
  ある。
- **トリガーの言語**：description は英語なので、共有される語は、エージェントが読んでいるものが何語であれ
  そこに生き残る語でなければならない — ファイル名、ツール名、固有名詞、そのまま打ち込む専門用語
  （`SKILL.md`、`issue`、`PR`、`description`）。単一言語のチームから出ないスキルは、そのチームが実際に打つ
  フレーズを、英語の文の中の引用された例として*追加で*埋め込んでよい。公開するスキルはそうしてはならない：
  利用者がどの言語でプロンプトを打つか知り得ず、第二言語のキーワード列は description を膨らませ、同期が
  ずれていくだけである。このプラグインのどの description もそれを持たないのは、そのためである。

### 3.4 Bad → Good

**Bad** — 先頭にタグ列、でっち上げのキーワード、手順の漏れ：

```text
Skill authoring / SKILL.md / quality — first read the whole file, then rewrite
each section, then check the frontmatter, for great skills and better writing.
```

**Good** — when が先頭で leading word を担い、what は一節、境界あり、手順なし、他の誰も名指ししない：

```text
Use this skill when writing, editing, or reviewing a skill, a SKILL.md, or its
description and frontmatter — how to write a skill's description and body so it
fires reliably and stays lean. DO NOT use this skill when the documentation is
not a skill's.
```

## Size（サイズ）

`description` には **1024文字**の厳しい予算がある。what + when + トリガーが収まらないなら、そのスキルは
たいてい仕事を抱えすぎている — description を水増ししたり切り詰めたりするのではなく、分割せよ
（[`structuring-skills.md`](structuring-skills.md) を参照）。

## No comments in the frontmatter（frontmatter にコメントを書かない）

frontmatter は `SKILL.md` の中で唯一、読まれるのではなく**パースされる**部分であり、そのすべてが発火のたびに
ロードされる。`user-invocable: false` の末尾につけた `#` は、それがなければ混乱したはずの誰にも説明しておらず、
すべての読み手が永久にその代金を払う — 枝の詳細を一段下へ押し下げるのと同じサイズの議論を、一段上へ適用した
ものである。本当に説明を要するフィールドは、著者が反論できる散文での説明を要する：本文か、リポジトリ自身の
アーキテクチャドキュメントで。
