# 本文を書く

`SKILL.md` の本文を書く、あるいは書き直すときに読むこと。

## Principles（原則）

**DO**

- **そのスキルが何をするかで始めること。** この読み手は発火の判断を過ぎており、これから動かねばならない。
- **各規則は、それを所有するファイルで決着させること。** そして各節には、下に定めた形を与えること。
- **論は、それが変える規則のそばに置くこと。** 読み手が何をするかを変える論はそこで席に値し、変えない論は
  本文の外に属する。

**DON'T**

- **そのスキル自身の frontmatter がすでに設定していることを言い直すこと** — `context: fork`、
  `user-invocable: false`。そのスキルがすることを何も変えない。
- **そのスキルがどう発火するかを説明すること。** 本文が読まれるのは発火したあとであり、その機構はもう
  使い終わっている。この読み手が必要とするのは「いつ適用するか」である。
- **たまたまそれを起動するスキルを名指しすること** — 「レビュー中に
  `write-nice-instructions-as-comment` から呼ばれる」。そのスキルが改名された日に誤りになり、それを検査する
  ものは何もない。このスキルが起動するサブスキルを名指しするのは逆向きである：両方を自分が所有しており、
  親は自分が呼ぶものを名指しせざるを得ない。
- **no-op を書くこと。** それは丁寧さに見えて、何かを変える規則と同じ代金を読み手に払わせる。

## The body's shape（本文の形）

```text
## Overview
## When it applies                      — description が対象を決着させないとき
## How to work
## <規則そのもの、あるいはそこへの振り分け>
## Persistence                          — スキルが効き続けるとき
## Common Rationalizations
## Red Flags
## Verification
```

締めるのはガードである：スキルは、作業の前に言いくるめられ、作業の途中で削られ、作業のあとで「終わった」と
宣言される。それぞれに一つずつある。

## Overview（概要）

そのスキルが何をするか、そしてなぜそれが重要かを一〜二文で。`description` が言うことをここで言い直すのが
その仕事である — description は発火の判断のための材料であり、この読み手はそれを過ぎている。

二つ目の短い節 `## When it applies` を足すのは、description だけからは対象の内にいるかを判断しにくいとき
だけである：作業が決して名指ししない定常的な規則か、近い隣人を持つ成果物か。振り分けの条件それ自身がどの
ケースが対象かを名指ししているなら、それがすでに答えている。

## How to work（どう進めるか）

規則を適用するときの姿勢を、一項目ずつ。作業に取りかかる著者が何をするかである。各項目が適用する規則そのもの
は、それを所有するファイルに留まる。

## The rules（規則）

規則が本文に収まるスキルは、ここに規則を持つ。無視したときの代償を、それぞれのそばに置く。

## Routing（振り分け）

同梱ファイルを持つスキルは、各ファイルへ到達する条件または問いを持ち、規則はそちらに委ねる。

別のスキルを起動するスキルは、それも、起動するステップの上で名指しする。何も起動しないスキルはどのスキルも
名指ししない：近隣の一覧は、著者の次の一手を何も変えない。

## Persistence（効力の持続）

ある活動のあいだ効き続けねばならないスキルは、一度ロードされたあと、その後に到着するすべてのものと競合する。
まだ効力があると決して言わない本文は、すでに与えられた助言として読まれ、作業は元いた場所へ流れ戻る。

以下の部分に分けて述べること：それをロードしたレスポンスだけでなく毎レスポンス効力を持つこと。エージェントが
目の前のケースが該当するかどうか迷っているあいだも効力が残ること。解除は明示的な条件によって起きること —
作業がそのスキルの守備範囲外へ移るか、止めるよう言われるか。

早く落としすぎるほうが、効かせすぎるより高くつく — もう当てはまらない規則が一段落ぶん余るのに対して、規則
なしで書かれたレスポンス一本まるごとである。しかも判断は毎レスポンス取り直されるので、安く済む失敗のほうを、
ルールが効いたままになる側にすること。

## Common Rationalizations（よくある自己正当化）

`Rationalization` と `Reality` の表。手順が飛ばされる前の言い訳を捕まえる。埋めるのはエージェントが実際に
口にしたものから：反論する羽目になった言い訳を、その最初の一回で足すこと。

## Red Flags（危険信号）

箇条書き。それぞれが出力の中で目に見える一つのものを名指しする — 「手順の入った description」 — ので、
エージェントはそれを探せる。規則の言い直しは、新たに見るべきものを何も与えない。

## Verification（検証）

チェックリスト。成果物を見るか、それに対して検査を一つ走らせれば決着するもの。

**項目がその席に値するのは、それが捕まえるものがスキルを機能させなくするときである** — ロードされないか、
発火しないか、到達されたうえで読み流されるか — あるいはそれが予算であるときである。残りの規則は、それが
住んでいる場所で読まれることで満たされる。その全部を列挙したチェックリストは、規則そのものになってしまって
いる。

## A sub-skill's body（サブスキルの本文）

親がサブスキルへ到達するのは、どのスキルへ到達するのとも同じく — 名前で、`Skill` ツールを通して — であり、
指示書は一つのかたまりとして渡される。その指示書が着地すべきところに、サブスキルの本文で **`$ARGUMENTS`** を
置くこと。
