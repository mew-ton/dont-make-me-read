# 本文を書く

`SKILL.md` の本文を書く、あるいは書き直すときに読むこと。

## Contents（目次）

- The shape（本文の形）
- DO
- DON'T
- Overview（概要）
- When it applies（いつ適用されるか）
- How to work（どう進めるか）
- The rules, or the routing to them（規則そのもの、あるいはそこへの振り分け）
- Persistence（効力の持続）
- Common Rationalizations（よくある自己正当化）
- Red Flags（危険信号）
- Verification（検証）

## The shape（本文の形）

```md
## Overview
## How to work
## The rules, or the routing to them
## Common Rationalizations
## Red Flags
## Verification
```

条件付きの節が二つある。`## When it applies` は `## Overview` の次に置く — description だけからは
対象の内にいるかを判断しにくいときだけ。`## Persistence` はガードの前に置く — ロードしたレスポンスを
越えてスキルが効き続けねばならないときだけ。

最後の三つがガードである。スキルは、作業の前に言いくるめられ、作業の途中で削られ、作業のあとで「終わった」と
宣言される — それぞれに一つずつ。

## DO

- **そのスキルが何をするかで始めること。** この読み手は発火の判断を過ぎており、これから動かねばならない。
- **各規則は、それを所有する reference で決着させること。** そして各節には、下に定めた形を与えること。
- **論は、それが変える規則のそばに置くこと。** 読み手が何をするかを変える論はそこで席に値し、変えない論は
  本文の外に属する。

## DON'T

- **そのスキル自身の frontmatter がすでに設定していることを言い直すこと** — `context: fork`、
  `user-invocable: false`。そのスキルがすることを何も変えない。
- **そのスキルがどう発火するかを説明すること。** 本文が読まれるのは発火したあとであり、その機構はもう
  使い終わっている。この読み手が必要とするのは「いつ適用するか」であり、それは `## When it applies` が担う。
- **たまたまそれを起動するスキルを名指しすること** — 「これはモデル起動スキルであり、レビュー中に
  `write-nice-instructions-as-comment` から呼ばれる」。そのスキルが改名された日に誤りになり、それを検査する
  ものは何もない。
- **no-op を書くこと。** それは丁寧さに見えて、何かを変える規則と同じ代金を読み手に払わせる。

## Overview（概要）

そのスキルが何をするか、そしてなぜそれが重要かを一〜二文で。`description` が言うことをここで言い直すのが
その仕事である — description は発火の判断のための材料であり、この読み手はそれを過ぎている。

## When it applies（いつ適用されるか）

二つ目の短い節。置くのは、description だけからは対象の内にいるかを判断しにくいときだけである：作業が決して
名指ししない定常的な規則か、近い隣人を持つ成果物か。ただし、振り分けの条件それ自身がどのケースが対象かを
名指ししているなら、それがすでに答えており、独立した一節は読み手がそれ無しでも通り抜けられた一行である。

## How to work（どう進めるか）

規則を適用するときの姿勢を、一項目ずつ。作業に取りかかる著者が何をするかである。各項目が適用する規則そのもの
は、それを所有する reference に留まる。

## The rules, or the routing to them（規則そのもの、あるいはそこへの振り分け）

規則が本文に収まるスキルは、ここに規則を持つ。reference を持つスキルは、代わりに各ファイルへ到達する条件
または問いを持ち、規則はそちらに委ねる — `SKILL.md` だけで規則を決着させられる著者は、その元になったファイル
を開かない。

## Persistence（効力の持続）

ある活動のあいだ効き続けねばならないスキルは、一度ロードされたあと、その後に到着するすべてのものと競合する。
まだ効力があると決して言わない本文は、すでに与えられた助言として読まれ、作業は元いた場所へ流れ戻る。

三つの部分に分けて述べること：それをロードしたレスポンスだけでなく毎レスポンス効力を持つこと。エージェントが
目の前のケースが該当するかどうか迷っているあいだも効力が残ること。解除は明示的な条件によって起きること —
作業がそのスキルの守備範囲外へ移るか、止めるよう言われるか。

早く落としすぎるほうが、効かせすぎるより高くつく — もう当てはまらない規則が一段落ぶん余るのに対して、規則
なしで書かれたレスポンス一本まるごとである。しかも判断は毎レスポンス取り直されるので、安く済む失敗のほうを、
ルールが効いたままになる側にすること。

## Common Rationalizations（よくある自己正当化）

`Rationalization` と `Reality` の表。手順が飛ばされる前の言い訳を捕まえる。埋めるのはエージェントが実際に
口にしたものから：反論する羽目になった言い訳を、その最初の一回で足すこと。

## Red Flags（危険信号）

箇条書き。それぞれが出力の中で目に見える一つのものを名指しする — 「手順の入った description」 — ので、
エージェントはそれを探せる。規則の言い直しは、新たに見るべきものを何も与えない。

## Verification（検証）

チェックリスト。成果物を見るか、それに対して検査を一つ走らせれば決着するもの。

**項目がその席に値するのは、それが捕まえるものがスキルを機能させなくするときである** — ロードされないか、
発火しないか、到達されたうえで読み流されるか — あるいはそれが予算であるときである。Red Flag が同じものを
名指ししていてよい：一方は書いているあいだに読まれ、他方はそのあとに読まれる。残りの規則は、それが住んでいる
場所で読まれることで満たされる。その全部を列挙したチェックリストは、規則そのものになってしまっている。

三つのガードのうち `SKILL.md` の外へ出せるのは Verification だけである。どの条件で出すかは progressive
disclosure の判断であり、それを決着させる reference へは `SKILL.md` が振り分ける。
