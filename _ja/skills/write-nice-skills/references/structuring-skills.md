# スキルを構造化する／分割する

本文が育っているとき、`SKILL.md` に入れるか reference に入れるかを決めているとき、あるいは一つのスキルを
二つに分けるべきか迷っているときに読むこと。

## The body budget（本文の予算）

予算が属するのは**同時に立つスキルの集合**であって、一つのファイルではない。スキルは一度に一つずつ到着
するわけではない：ある活動のあいだ効き続けるルールは、手元の成果物のために別のスキルが発火しているあいだも
常駐しており、読み手は両方の代金を払う。自分の上限の内側にあるファイルでも、その活動を超過させうる。

| そのスキル | 予算 | 理由 |
|---|---|---|
| ある活動のあいだ効き続ける — 読み手が何をしていようと常駐する | **2000トークン** | すべての活動のすべてのターンがその代金を払う |
| 一つの成果物、一つの枝のために取りに行かれる | **5000トークン / 500行** | それを必要とする読み手だけが払う |

チェックすべき集合は、同時に立つことになるスキルのすべてである：この活動のあいだ効くものと、手元の
成果物のために取りに行かれるもの。その上限は、それぞれの上限の合計である。編集しているファイルでは
なく、集合を測ること。

- 本文が指すものは**一段の深さ**に座る。reference の中に reference をネストしない：二つ目のホップは、
  読み手が同意していないホップである。
- 補助ファイルは `SKILL.md` から参照されることで見つかる。だからその名前も、そもそもディレクトリに入れるか
  どうかも、あなたが決めてよい。`references/`、`rules/`、`scripts/`、`assets/` は例示のレイアウトから
  借りた慣習であって要件ではない — 合う隣人に合わせ、それ以上は考えないこと。

### その予算のトークン側を測る

行数は弱い代理指標である：5000トークンは英語の散文でおよそ250行を買うが、日本語や中国語のような非ラテン
文字ではおよそ150行しか買えない。だから本文が500行に収まっていながら、なお予算の数倍のコストになりうる。
見積もるのではなく測ること：

```bash
bash <this skill's directory>/scripts/count-tokens.sh path/to/SKILL.md
TARGET=2000 bash <this skill's directory>/scripts/count-tokens.sh <常時効く SKILL.md すべて>
```

二行目が常時効くスキルの予算である。報告された数値を合計して集合を確認すること。

「このスキルのディレクトリ」とは、このファイルがロードされた場所である — プラグインのインストールパス、
`~/.claude/skills/write-nice-skills/`、あるいはリポジトリの `.claude/skills/write-nice-skills/`。ハード
コードすべき絶対パスは一つも存在しないので、場所を仮定するのではなく、このファイルを読んだ場所から解決
すること。

これは、現時点で既定のモデルに対する2回の実行の入力側トークン数を差分するので、APIキーは不要で、モデル
世代に固定されるものも何もない。1ファイルにつき1往復のコストがかかり、予算超過で非ゼロ終了する。

無料の事前チェックには `wc -m` ではなく `wc -c` を使うこと。トークンあたりのバイト数は文字体系間でほとんど
動かないのに対し、トークンあたりの文字数はラテン文字と非ラテン文字とでほぼ倍になる。**今日は、およそ
15 KB が5000トークンの、6 KB が2000トークンの代用になる。** スクリプトの最終行はその数字をあなた自身の実行から再導出する。
既定のモデルが変わった後は、この数字を鵜呑みにせずそこで再計算すること — 低すぎる古い数字は、そもそも予算を
超えていなかったファイルを分割させに行かせる。

## Staying in force（効力を持ち続ける）

ある活動のあいだ効き続けねばならないスキルは、一度ロードされたあと、その後に到着するすべてのものと競合
する。まだ効力があると決して言わない本文は、すでに与えられた助言として読まれ、作業は元いた場所へ流れ
戻る。

本文で、三つの部分に分けて述べること：それをロードしたレスポンスだけでなく毎レスポンス効力を持つこと。
目の前のケースが該当するかどうか迷っているあいだも効力が残ること。解除は明示的な条件によってのみ起きる
こと — 作業がそのスキルの守備範囲外へ移るか、止めるよう言われるか。

デフォルトが非対称なのは意図的である。これはシステムの性質ではなく毎レスポンス取り直される判断なので、
安く済むほうの失敗が、ルールが効いたままになる側でなければならない。

## Progressive disclosure: 何をインラインにし、何を開示するか

- **インライン**にする（`SKILL.md` に）：**すべての経路が必要とするもの** — なぜそのスキルが存在するのか、
  どう進めるか、どの reference へ振り分けるかの条件、そして Common Rationalizations のガード。規則そのもの
  ではない — `SKILL.md` だけで規則を決着させられる著者は、その元になった reference を開かない。それは
  description が本文に対して行う漏洩を、一段上でやっているのと同じである。
- **開示**する（context pointer の後ろに）：**一部の枝しか到達しないもの** — 深い詳細、長い実例、枝ごとの
  手順。
- **スキルの外へ出す**：**どの枝も到達しないもの** — 設計上の論拠、およびエージェントではなく、そのスキルを
  インストールする人・保守する人のために書かれたもの。[What goes in a sibling README](#what-goes-in-a-sibling-readme)
  を参照。

context pointer は条件とファイルを名指しする：「For writing a description, see
`references/writing-descriptions.md`」。その枝が実際に取られたときにだけ reference がロードされる。

## What goes in a sibling README（姉妹 README に何を置くか）

三つ目の行き先があり、それは無料である。`SKILL.md` の隣にある `README.md` はそこから参照されないので、
何にもロードされず、エージェントの文脈を一切消費しない。

そのディレクトリを誰が開くかが、そこに何を置くかを決める。

**他人がインストールするスキル**は、そのファイルを読んで採用される。だからスキルそのものの説明をそこが担う：
何を強制するのか、いつ発火するのか、どう呼び出し設定するのか、そして残りがどこにあるか。それを統べるのは
`write-nice-readme` である — その読み手こそ、あのスキルが書かれている対象であり、あのスキルの境界が除外して
いるのは `SKILL.md` であって、その隣の README ではない。

**自分のリポジトリだけが使うスキル**には、その読み手が居ない。保守する人はそのスキルが何のためにあるかを
すでに知っているので、その詳細は無駄になり、設計上の論拠がファイルの全部になる：founding argument、なぜ
スタイルガイドではなく skill なのか、この形がどの設計判断から来たのか。公開するスキルでも同じ論拠は説明の
下に座り、すでに決断した人がそこへ到達する。

どちらでもテストは同じ — これは読み手が次にすることを変えるか。エージェントに対しては、変えない。そのディレクトリ
を開く人に対しては、変える。

規則の**実務側**は rationale ではなく、動かない。「あなたは読みながら、テキストに欠けている意図を自分で
補っている」は Common Rationalizations に属する。そこにあれば、その言い訳に手が伸びた瞬間に反駁する。README で
命題として述べれば、一度読まれて同意されるだけであり、それは適用されることとは違う。

## Add Common Rationalizations（Common Rationalizations を足す）

エージェントが手を抜きそうなスキルには、その言い訳を先回りして封じること：飛ばす理由としてエージェントが
見つけるものの表と、それぞれを反駁する実際のところ。これをインラインに置くのは、ポインタの後ろにあるガードは
他のすべてと一緒に飛ばされるからである。

## Leave out what the structure already settles（構造がすでに決着させていることは書かない）

スキルは自分の分類も、誰が呼ぶかも、どこに座っているかも述べる必要がない。frontmatter と呼び出し元がそれらを
すべて確立しており、それを述べる一文はそのスキルがすることを何も変えず、そして呼び出し元の名前が変わった日に
そのスキルを誤りにする。

## When to split（いつ分割するか）

その切断がコストに見合うときにだけ分割する。三つの切断がそれを正当化する。最初の二つは mattpocock の
`writing-great-skills` から：

1. **トリガー語による** — 別個の状況が、実際に打ち込む*固有の* leading word を持っている。その語で別の
   モデル起動スキルを起動できる（あるいは一つのスキルの中で、別の reference をゲートできる）。
2. **順序による** — その*完了後*の手順を隠すべき一連のステップ。その一連を固有の文脈に隔離すると後続が
   クリアされ、その後に来る作業を邪魔しない。
3. **委譲による** — *異なる実行環境*で走るべきフェーズ：固有のモデル、固有のツールセット、固有の文脈。この
   切断は読み手が何を打つかについてでも、何が後に来るかについてでもない。**誰がその作業をすべきか**に
   ついてである。詳細：下記の [By delegation](#by-delegation)。

どの切断も当てはまらないなら、インラインのままにする。分割のための分割は、文脈の負荷（エージェントが毎ターン
検討しなければならないスキルが増える）か認知の負荷（著者が抱えねばならないファイルが増える）のどちらかを
増やし、何も買わない。

## By delegation（委譲による）

`By sequence` は**一つのスキルが二つになるかどうか**を決める。`By delegation` は**一つのフェーズがこの実行
環境を離れるかどうか**を決める。委譲されたフェーズは依然としてこのスキルの作業である — ただ、より安く狭い
どこかで走り、それが導出された材料ではなく結論を返すというだけである。

### 何を委譲してよく、何をしてはならないか

**機械的で読み取り専用の収集、列挙、パースを委譲せよ** — 出力が結論へ畳み込まれるもの。PRのコメントの取得、
変更ファイルの列挙、パッケージレジストリの走査、設計をリポジトリに接地させること：親が必要とするのは答えで
あって、それを生んだトランスクリプトではない。

**根拠が一緒に戻ってこない作業は決して委譲しない** — 判定を返すレビュー、答えだけを返す呼び出し。レビューの
実質をサブエージェントに置くと、各 findings の根拠がメインスレッドに決して届かず、誰もそのレビューを
レビューできなくなる。そこで文脈が問題なら、判断ではなく**セッション**を分割せよ。

テストは「判断か収集か」ではない。**呼び出し元が、その作業を検証するのに必要なすべてを受け取るかどうか**で
ある。*成果物を書く*スキルはこれを通る：成果物は丸ごと戻ってきて、読み手はその物自体を判断するので、fork の
後ろで蒸留されて消えるものが何もない。

### Naming（命名）

`<parent-skill-name>-<role>`：親の名前、ハイフン**一つ**、子が演じる役割 — `-change-inventory`、
`-repo-grounding`、`-version-lookup`。

その形は、公開時の命名ルールが許すものである：小文字英数字とハイフンのみ、1〜64文字、先頭と末尾のハイフン
なし、**連続するハイフンなし**、そして frontmatter の `name` は親ディレクトリ名と一致しなければならない。
したがって境界を示すために `--` に手を伸ばさないこと。単一のハイフンが利用できる唯一の区切りである。

子を隠すのは名前ではない。ユーザーの `/` メニューから外しておくのは、下記の `user-invocable` の仕事である。

### The child's frontmatter（子の frontmatter）

```yaml
user-invocable: false
disable-model-invocation: false
context: fork
agent: Explore
model: haiku
background: false
```

`user-invocable: false` は子をユーザーの `/` メニューから隠す。`background: false` は結論を同じターンで
使うときに必須で、既定は `true` である。`agent` と `model` は任意：`agent` はツールセットを選び
（`Explore` と `Plan` は読み取り専用）、`model` はコストと能力を天秤にかける — 収集のみなら `haiku`、
収集に軽い正規化が加わるなら `sonnet`。

`agent` と `model` は、理由を言えない限り**外しておく**二つである。どちらも子を「情報収集の実行が必要と
するもの」まで狭めてしまい、成果物そのものを生み出す fork にとって狭めることは誤りである：読み取り専用の
ツールセットでは書けないし、ファイルを列挙できる最安のモデルは、人が行動することになるものを起草させたい
モデルではない。両方を省けば fork は継承し、それが下記の `Cleanliness` の動機にとって正しい既定である。

`disable-model-invocation: true` は、正しく見えて誤っているフィールドである。ここでの呼び出し元は**モデル**
なので、`true` は子への唯一の経路を断ち切る。人間から隠すのは `user-invocable: false` であり、要件はそれで
すべてである。

`context: fork` こそが、子を親のターンの延長ではなく実行環境にするものである。それがないと、`model` は現在の
ターンの残り — メインの会話 — に適用され、そのスキルが委譲する何にも適用されない。

### Passing input（入力の渡し方）

入力全体を **`$ARGUMENTS`** として渡す。添字付き引数や名前付き引数はシェル的なクォート解析を通るので、
複数行の自由形式のブリーフは単一の引数として生き残れない。

### 二つの動機と、それぞれの `model` の選び方

| 動機 | fork が買うもの | `model` | `background` |
|---|---|---|---|
| **Context** — 大量の収集をメインスレッドから外す | 生の材料が親の文脈に決して着地しない | それができる最安のモデル：純粋な収集と数え上げなら `haiku`、軽い正規化が絡むなら `sonnet` | `false`。親が同じターンで結論を使うため |
| **Independence** — 二人の作業者が互いの出力を見てはならない | `context: fork` は会話履歴を持ち込まないので、隔離が要請ではなく構造になる | `sonnet`：作業は設計品質なので、モデルを落とすのではなく `effort` で狭める | 作業者を並列に走らせるべきときは未設定のままにする |
| **Cleanliness** — ブリーフを生み出した会話が成果物に届いてはならない | 探索、中途半端な依頼、取得した材料が、成果物が書かれる文脈に決して入らない | 未設定のままにする。作業は成果物自身のものである | `false`。呼び出し元が同じターンで結果を見せるため |

後ろの二行が散文を置き換えている。「どちらのサブエージェントにも他方の出力を見せるな」は読み手が破りうる
禁止だが、`context: fork` が会話履歴を持ち込まないことは彼らが破れない**性質**である。同じ手が一軸隣にも
当てはまる：「この会話の参加者にしか再構成できないことを書くな」は `avoid-unverifiable-context` のルールで
書き手が破りうるが、会話を見たことのないスキルはそれができない。

だから、成果物を書くスキルは fork して一つのブリーフを受け取り、ルーティングや制約をするスキルはメイン
スレッドに留まる。どちらもこの性質を必要とするが、作業対象を失わずにそれを持てるのは前者だけである。

## This skill as the worked example（このスキル自身が実例）

`write-nice-skills` は「全部書くな。枝の詳細は一段下に押し出せ」を教えるので、自分自身の枝に沿って分割
している：

- 常に必要な中核は `SKILL.md` に留まる。
- 著者が実際にいる二つの枝 — *description を書く*と*スキルを構造化する* — がそれぞれ一つの reference を
  得る。
- 共有語彙は `GLOSSARY.md` に行く。

単一ファイル版は、それが教えるルールと矛盾することになる。それがテストである：構造についてのスキルは、
それが規定するとおりに構造化されているべきだ。
