# スキルを構造化する／分割する

本文が育っているとき、`SKILL.md` に入れるか reference に入れるかを決めているとき、どちらを何と呼ぶかを
決めているとき、ロードされたスキルをどう効かせ続けるかを決めているとき、あるいは一つのスキルを二つに
分けるべきか迷っているときに読むこと。

## What is free and what is not（何が無料で、何がそうでないか）

インストールされているスキルの `name` と `description` は、そのスキルが一度も使われなくても、毎ターン
事前ロードされる。同梱ファイルは読まれるまで一切かからない。

したがって、枝を reference へ移すのはその枝が取られるまで無料であり、同じ枝を二つ目のスキルへ移せば、
インストールしている全員に対して、毎ターン、永久に description の代金を払う。

## The body budget（本文の予算）

予算が属するのは**同時に立つスキルの集合**である。スキルは一度に一つずつ到着するわけではない：ある活動の
あいだ効き続けるルールは、手元の成果物のために別のスキルが発火しているあいだも常駐しており、読み手は両方の
代金を払う。自分の上限の内側にあるファイルでも、その活動を超過させうる。

| そのスキル | 予算 | 理由 |
|---|---|---|
| ある活動のあいだ常時オンである — 読み手が何をしていようと常駐する | **全部あわせて2000トークン** | すべての活動のすべてのターンがその代金を払う |
| 一つの成果物、一つの枝のために取りに行かれる | **一つあたり5000トークン** | それを必要とする読み手だけが払う |

だからチェックすべき集合は、同時に立つことになるスキルのすべてである：この活動のあいだ効くものを合計して
一つ目の数字と、手元の成果物のために取りに行かれるものを二つ目の数字と突き合わせる。編集しているファイル
ではなく、集合を測ること。

### その予算のトークン側を測る

行数は弱い代理指標である：5000トークンは英語の散文でおよそ250行を買うが、日本語や中国語のような非ラテン
文字体系ではおよそ150行しか買えない。だから本文は行数では短く見えていながら、なお予算の数倍のコストに
なりうる。測ること：

```bash
bash <this skill's directory>/scripts/count-tokens.sh path/to/SKILL.md
TARGET=2000 bash <this skill's directory>/scripts/count-tokens.sh <常時効く SKILL.md すべて>
```

二行目が常時効くスキルの予算である。報告された数値を合計して集合を確認すること。

「このスキルのディレクトリ」とは、このファイルがロードされた場所である — プラグインのインストールパス、
`~/.claude/skills/write-nice-skills/`、あるいはリポジトリの `.claude/skills/write-nice-skills/`。この
ファイルを読んだ場所から解決すること：ハードコードできる絶対パスは一つも存在しない。

これは、現時点で既定のモデルにそのファイルを送り、ファイル抜きの基準リクエストを差し引くので、得られる数字は
そのモデル自身の数え方であり、モデルが変わっても正しいままである。1ファイルにつき1往復のコストがかかり、
予算超過で非ゼロ終了する。

無料の事前チェックには `wc -c` でバイト数を数えること。トークンあたりのバイト数は文字体系間でほとんど
動かないのに対し、トークンあたりの文字数はラテン文字と非ラテン文字とでほぼ倍になる。**今日は、およそ
15 KB が5000トークンの、6 KB が2000トークンの代用になる。** スクリプトの最終行はその数字をあなた自身の実行
から再導出する。既定のモデルが変わった後はそこで再計算すること — 低すぎる古い数字は、そもそも予算を
超えていなかったファイルを分割させに行かせる。


## Staying in force（効力を持ち続ける）

ある活動のあいだ効き続けねばならないスキルは、一度ロードされたあと、その後に到着するすべてのものと競合
する。まだ効力があると決して言わない本文は、すでに与えられた助言として読まれ、作業は元いた場所へ流れ
戻る。

本文で、三つの部分に分けて述べること：それをロードしたレスポンスだけでなく毎レスポンス効力を持つこと。
目の前のケースが該当するかどうか迷っているあいだも効力が残ること。解除は明示的な条件によって起きること —
作業がそのスキルの守備範囲外へ移るか、止めるよう言われるか。

効かせすぎる失敗と早く落としすぎる失敗は等価ではなく、しかも判断は毎レスポンス取り直されるので、安く済む
ほうが、ルールが効いたままになる側でなければならない。


## Open with what it is, then when it applies（何であるかを先に、いつ適用されるかを次に）

まず `## Overview`：そのスキルが何をするか、そしてなぜそれが重要かを一〜二文で。次に、読み手がその中に
いるかどうか。規則も、手順も、ガードもそのあとに来る。

後半 — 読み手がその中にいるかどうか — が場所を得るのは、発火があいまいなときだけである：作業が決して
名指ししない定常的な規則か、近い隣人を持つ成果物か。次の節がすでに入力や振り分けであるスキルは、それに
答え終わっている。そこに description を繰り返す節を置けば、それは **no-op** である。

その二文に収まらなかった論は、実務的であれば — それが擁護する規則か Common Rationalizations の行に属し —
そうでなければ、スキルの外に属する。

## Guard it three ways（三方向から守る）

スキルは、作業の前に言いくるめられ、作業の途中で削られ、作業のあとで「終わった」と宣言される。それぞれに
ガードを一つずつ。

| セクション | 何を捕まえるか | 形 |
|---|---|---|
| **Common Rationalizations** | 手順が飛ばされる前の言い訳 | `Rationalization` と `Reality` の表 |
| **Red Flags** | 出力に現れたあとの症状 | 箇条書き：どう見えるか、そしてそれが実際には何であるか |
| **Verification** | その作業が終わっているかどうか | どのチェックボックスも、成果物を見るか、それに対して検査を一つ走らせれば決着するチェックリスト |

Common Rationalizations を埋めるのはエージェントが実際に口にしたものから — 反論する羽目になった言い訳を、
その最初の一回で足すこと。Red Flag は出力の中で観察できるものを名指しする — 「1メッセージに3問」 — ので、
エージェントはそれを探せる。規則の言い直しは、新たに見るべきものを何も与えない。

**三つのうち二つはインラインに留まる。** Common Rationalizations に到達するのは、エージェントが飛ばす理由を
探している状態のときであり、その状態のエージェントはファイルを開きに行かない。Red Flags は書いているあいだ
頭の中に無ければならず、それはどのレビューよりも前である。

**Verification は開示できる。**「成果物を完了と呼ぶ前」は、エージェントが認識できる条件であり、context
pointer に必要なのはそれだけだからである。走らせるのにリストを読む以上のことが要るようになったら — 決まった順序の手順、
一つ一つに突き合わせる期待出力 — 開示すること。どの項目も見るかコマンド一つで答えられるうちはインラインに
留める：それが3〜5項目なら、ポインタとそのあとに続くロードよりインラインのほうが安い。

動かすときの行き先は、**`SKILL.md` の隣の `VERIFICATION.md`** である：スキルの常置の役割であり、どのスキルの
検査も同じ固定名を共有する。

## Naming（命名）

スキル自身の名前：小文字英字・数字・ハイフンのみ。64文字以内。先頭・末尾・連続のハイフンなし。そして
frontmatter の `name` はディレクトリ名と一致すること。`anthropic` と `claude` は予約語であり、名前に
現れてはならない。

**二つのファイルがスキルの常置の役割を担い、その名前は固定である。** どのスキルでも同じパスにあり、集合
として grep できる：

| ファイル | 何を担うか |
|---|---|
| `GLOSSARY.md` | 規則が使う用語 |
| `VERIFICATION.md` | 検査。チェックリストではなく手続きになったとき |

どちらも必須ではない。名前が固定されるのは、それを持つスキルにとってである。

**エージェントがロードするそれ以外のものは枝の material であり、名前はあなたのものである。**
`references/`、`scripts/`、`workflows/`、`assets/`、あるいは `SKILL.md` の隣に置いた裸のファイル。合う隣人に
合わせ、それ以上は考えないこと。

**エージェントが決してロードしないファイルは、このすべての外側にある** — そもそも存在するかどうかも、
何という名前かも、それを書く人のものである。

## Progressive disclosure: 何をインラインにし、何を開示するか

- **インライン**にする（`SKILL.md` に）：**すべての経路が必要とするもの** — overview、どう進めるか、どの
  reference へ振り分けるかの条件、そして Common Rationalizations のガード。規則そのものは、それを所有する
  reference に委ねること — `SKILL.md` だけで規則を決着させられる著者は、その元になったファイルを開かない。
- **開示**する（context pointer の後ろに）：**一部の枝しか到達しないもの** — 深い詳細、長い実例、枝ごとの
  手順。
- **スキルの外へ出す**：**どの枝も到達しないもの** — `SKILL.md` の隣にあって何からも参照されないファイルは
  決してロードされず、エージェントの文脈を一切消費しない。設計上の論拠、人に向けたそのスキルの説明、規則が
  どこから来たか。

本文が指すものは**一段の深さ**に座る。別の reference から到達される reference は*部分的に*しか読まれない —
エージェントは全体を読む代わりに `head -100` のようなもので覗き見る — ので、その二つ目のホップの150行目に
ある規則は、誰も読まなかった規則である。補助ファイルはすべて `SKILL.md` から直接リンクし、そうやって
見つかる。何という名前にするかは [Naming](#naming) で決着する。**100行を超える reference は、自分の見出しの
一覧で始める**。理由は同じで、部分的に読まれても、そのファイルに何が入っているかは見えるからである。

context pointer が名指しするのは、そのファイルへ到達する**条件または問い**である：「APIが200以外を返したら
`references/api-errors.md` を読む」、あるいは「エラーコードが何を意味するか」。読み手がその場合に入ったときに
だけ reference がロードされる。

**まっとうな前提を裏切る事実**も、同じくインラインに残る。`/health` エンドポイントがデータベースの停止中
でも応答することを知らないエージェントは、それが書いてあるファイルをロードさせる条件を認識できない。

規則の**実務側**は、エージェントの文脈にどれほど余裕がなかろうと、インラインに留まる。「自分には良く読める」
という言い訳と、それへの答えである「あなたは読みながら、テキストに欠けている意図を自分で補っている」は
Common Rationalizations に属する。そこにあれば、その言い訳に手が伸びた瞬間に答えが届く。何にもロードされないファイルに置けば一度読まれて同意されるだけであり、それは
適用されることとは違う。

## Leave out what the structure already settles（構造がすでに決着させていることは書かない）

frontmatter と呼び出し元が、そのスキルの分類も、誰が呼ぶかも、どこに座っているかもすでに確立している。
それを繰り返す一文はそのスキルがすることを何も変えず、そして呼び出し元の名前が変わった日にそのスキルを
誤りにする。

**no-op** も同じく書かない — モデルが促されなくても既に従う指示のことである。それは丁寧さに見えて、何かを
変える規則と同じ代金を読み手に払わせる。

## When to split（いつ分割するか）

まずスコープ。スキルは、関数がそうであるように、まとまりのある一単位の作業を覆う。狭すぎれば一つの作業で
複数のスキルがロードされ、それぞれの指示を互いに突き合わせる羽目になる。広すぎれば、正確に起動できるものが
なくなる。データベースに問い合わせて結果を整形するのは一単位であり、そこにデータベース管理を足すと二単位に
なる。

そのうえで、切断がコストに見合うときにだけ分割する。三つの切断がそれを正当化する：

1. **leading word による** — 別個の状況が、実際に打ち込む*固有の* leading word を持っている。その語で別の
   モデル起動スキルを起動できる（あるいは一つのスキルの中で、別の reference をゲートできる）。
2. **順序による** — その*完了後*の手順を隠すべき一連のステップ。その一連を固有の文脈に隔離すると後続が
   クリアされ、その後に来る作業を邪魔しない。まず、どのステップにも、検査可能で網羅的な完了条件を与える
   こと：「バリデータが0で終了する」。固有のスキルを必要としているように見える一連のステップは、たいてい
   曖昧な条件を一つ抱えているだけであり、エージェントはそこで止まらずに通り過ぎる。
3. **委譲による** — *異なる実行環境*で走るべきフェーズ：固有のモデル、固有のツールセット、固有の文脈。この
   切断は**誰がその作業をすべきか**についてであり、最初の二つは読み手が何を打つかと、何が後に来るかに
   ついてである。これには固有の reference があり、`SKILL.md` がそこへ振り分ける。

どの切断も当てはまらないなら、インラインのままにする。分割のための分割は、文脈の負荷（毎ターン description が
一つ増える）か認知の負荷（著者が抱えねばならないファイルが増える）のどちらかを増やし、何も買わない。


## This skill as the worked example（このスキル自身が実例）

このスキルは、すべてのスキルに求めるとおり、自分自身の枝に沿って分割している：

- 常に必要な中核は `SKILL.md` に留まる。
- 著者が実際にいる枝 — *description を書く*、*スキルを構造化する*、*段階を委譲する* — がそれぞれ一つの
  reference を得て、Bad → Good の実例が四つ目を得る。description を書くことと、書いたものを実例に照らす
  ことは、到達する瞬間が違うからである。
- 共有語彙は `GLOSSARY.md` に行く。

それがテストである：構造についてのスキルは、それが規定するとおりに構造化されている。
