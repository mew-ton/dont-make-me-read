# スキルを構造化する／分割する

本文が育っているとき、`SKILL.md` に入れるか reference に入れるかを決めているとき、どちらを何と呼ぶかを
決めているとき、frontmatter が何を担ってよいかを決めているとき、ロードされたスキルをどう効かせ続けるかを
決めているとき、あるいは一つのスキルを二つに分けるべきか迷っているときに読むこと。

## What is free and what is not（何が無料で、何がそうでないか）

インストールされているスキルの `name` と `description` は、そのスキルが一度も使われなくても、毎ターン
事前ロードされる。同梱ファイルは読まれるまで一切かからない。

したがって、枝を reference へ移すのはその枝が取られるまで無料であり、同じ枝を二つ目のスキルへ移せば、
インストールしている全員に対して、毎ターン、永久に description の代金を払う。

## Staying in force（効力を持ち続ける）

ある活動のあいだ効き続けねばならないスキルは、一度ロードされたあと、その後に到着するすべてのものと競合
する。まだ効力があると決して言わない本文は、すでに与えられた助言として読まれ、作業は元いた場所へ流れ
戻る。

本文の `## Persistence` 節で、三つの部分に分けて述べること：それをロードしたレスポンスだけでなく毎レスポンス効力を持つこと。
エージェントが目の前のケースが該当するかどうか迷っているあいだも効力が残ること。解除は明示的な条件によって起きること —
作業がそのスキルの守備範囲外へ移るか、止めるよう言われるか。

早く落としすぎるほうが、効かせすぎるより高くつく — もう当てはまらない規則が一段落ぶん余るのに対して、
規則なしで書かれたレスポンス一本まるごとである。しかも判断は毎レスポンス取り直されるので、安く済む失敗の
ほうを、ルールが効いたままになる側にすること。


## The body budget（本文の予算）

予算が属するのは**同時に立つスキルの集合**である。スキルは一度に一つずつ到着するわけではない：ある活動の
あいだ効き続けるルールは、手元の成果物のために別のスキルが発火しているあいだも常駐しており、読み手は両方の
代金を払う。自分の上限の内側にあるファイルでも、その活動を超過させうる。

| そのスキル | 予算 | 理由 |
|---|---|---|
| ある活動のあいだ常時オンである — ロードしたレスポンスを越えて、本文がそれを効かせ続ける | **そうした `SKILL.md` を全部合計して2000トークン** | すべての活動のすべてのターンがその代金を払う |
| 一つの成果物、一つの枝のために取りに行かれる | **1ファイルあたり5000トークン** | それを必要とする読み手だけが払う |

だから、一緒に出荷する常時オンのスキル — 自分が測れるもの — を合計して一つ目の数字と突き合わせ、手元の
成果物のために取りに行かれるファイルを一つずつ二つ目の数字と突き合わせること。誰か他人の常時オンのスキルも
常駐しうる。だから一つ目の数字は、埋めるための枠ではなく、下回り続けるための天井である。どちらの数字も
このスキル自身のものであり、一つのターンが担える量に照らして定められている。

### 測る

行数はどちらの数字に対しても弱い代理指標である — 本文は行数では短く見えていながら、なお予算を大きく超える
コストになりうる — だからトークンを測ること：

```bash
# 成果物起動型のファイルを、それぞれ 5000 に照らして
bash <this skill's directory>/scripts/count-tokens.sh path/to/SKILL.md path/to/reference.md
# 常時オンの SKILL.md すべてを、2000 に照らして合計するため
bash <this skill's directory>/scripts/count-tokens.sh <常時オンの SKILL.md すべて>
```

スクリプトは各ファイルを、現時点で既定のモデルに送り、ファイル抜きの基準リクエストを差し引く。得られる数字は
そのモデル自身の数え方であり、モデルが変わっても正しいままである。
ファイルごとに数とトークンあたりのバイト比を印字し、どれか一つでも `TARGET` — 環境変数で、既定は5000 — を超えると
非ゼロ終了する — だから一つ目のコマンドは成果物起動型のファイルをそれだけで検査できる。常時オンの数字は合計なので、ファイル単位の終了コードでは
検査できない：二行目を走らせ、自分で数を足し合わせること。

「このスキルのディレクトリ」とは、このファイルがロードされた場所である — プラグインのインストールパス、
`~/.claude/skills/write-nice-skills/`、あるいはリポジトリの `.claude/skills/write-nice-skills/`。この
ファイルを読んだ場所から解決すること：ハードコードできる絶対パスは一つも存在しない。

無料の事前チェックには `wc -c` でバイト数を数えること。トークンあたりのバイト数が安定した比率であり、
だからこそバイト数がトークン予算の代用になる。**およそ
15 KB が5000トークンの、6 KB が2000トークンの代用になる。** どちらも、スクリプトがここで最後に報告した
比率を3バイト/トークンに丸めたものである。報告される比率がそこから
0.5バイト以上離れたら、そのつど計算し直すこと — 低すぎる古い数字は、そもそも予算を超えていなかったファイルを分割させに行かせる。


## The body's shape, and what opens it（本文の形と、その冒頭に来るもの）

まず `## Overview`：そのスキルが何をするか、そしてなぜそれが重要かを一〜二文で。description が言うことを
ここで言い直すのがその仕事である — description は発火の判断のための材料であり、この読み手はそれを過ぎて、
これから動かねばならない。

読み手が対象の内にいるかどうかを述べる二つ目の短い節 — `## When it applies` — を置くのは、それが
description だけからは判断しにくいときだけである：作業が決して名指ししない定常的な規則か、近い隣人を持つ
成果物か。ただし、振り分けの条件それ自身がどのケースが対象かを名指ししているなら、それがすでに答えており、
独立した一節は読み手がそれ無しでも通り抜けられた一行である。

その他はすべてそのあとに来る：どう進めるか、どの reference へ振り分けるかの条件、そのスキルが常時オンなら
`## Persistence` 節、そして後述の三つのガード。

## Naming（命名）

スキル自身の名前は、プラットフォーム自身がそれに課す制限の内側で：小文字英字・数字・ハイフンのみ。64文字以内。先頭・末尾・連続のハイフンなし。そして
frontmatter の `name` はディレクトリ名と一致すること。名前が `anthropic` でも `claude` でもないこと。他のスキルのフェーズとして起動されるスキルには、これに加えてもう一つの命名規則がある。
`SKILL.md` がそれを決着させる reference へ振り分ける。

**二つのファイルがスキルの常置の役割を担い、その名前は固定である** — どちらも `SKILL.md` の隣。どのスキル
でもそれぞれが同じパスにあり、grep 一回で全部が見つかる：

| ファイル | 何を担うか |
|---|---|
| `GLOSSARY.md` | 規則が使う用語 |
| `VERIFICATION.md` | 検査。開示されるようになったとき — 後述の *Progressive disclosure* を参照 |

名前が固定されるのは、それを持つスキルにとってである。

**エージェントがロードするそれ以外のものは枝の material であり、名前はあなたのものである。**
`references/`、`scripts/`、`workflows/`、`assets/`、あるいは `SKILL.md` の隣に置いた裸のファイル。そのスキルの
他のフォルダがすでに使っているものに合わせ、それ以上は考えないこと。

## Progressive disclosure: インライン、開示、あるいは未リンク

- **インライン**にする（`SKILL.md` に）：**すべての経路が必要とするもの** — overview、どう進めるか、どの
  reference へ振り分けるかの条件、description が対象を決着させないなら `## When it applies` 節、スキルが
  常時オンなら `## Persistence` 節、そして三つのガードすべて —
  Common Rationalizations、Red Flags、Verification。規則そのものは、それを所有する
  reference に委ねること — `SKILL.md` だけで規則を決着させられる著者は、その元になったファイルを開かない。
- **開示**する（そこへ到達する条件を名指すポインタの後ろに）：**一部の枝しか到達しないもの** — 深い詳細、長い実例、枝ごとの
  手順。
- **未リンクのままにする**：**どの枝も到達しないもの** — `SKILL.md` の隣にあって何からも参照されないファイルは
  決してロードされず、エージェントの文脈を一切消費しない。設計上の論拠、人に向けたそのスキルの説明、規則が
  どこから来たか。

文脈にどれほど余裕がなかろうとインラインに留まるものが二つある。**まっとうな前提を裏切る事実** — エージェント
は、そこに何が書いてあると予期する理由のないファイルへ自分を送る条件を認識できないからである。そして
**飛ばそうとするまさにその瞬間にエージェントが必要とする答え** — Common Rationalizations の行、Red Flag。
エージェントが決してロードしないファイルに置けば、その答えは誰も適用しない助言だからであり、Red Flag は
書いているあいだ、どのレビューよりも前に頭の中に無ければならないからである。

**動いてよいガードは Verification である。** 走らせるのにリストを読む以上のことが要るようになったら — 決まった
順序の手順、一つ一つに突き合わせる期待出力 — 開示すること。行き先は **`SKILL.md` の隣の `VERIFICATION.md`**
で、到達させるのは「成果物を完了と呼ぶ前」である。エージェントが認識できる条件であり、そのポインタに必要な
のはそれだけである。どの項目も見るかコマンド一つで答えられるうちはインラインに留め、成果物ごとにではなく
スキルごとに一度走らせる項目も、手順ごとインラインに留めること：読み手がそれに出会うのは一度である。

## How a reference is reached（reference へどう到達するか）

本文が指すものは**一段の深さ**に座る。別の reference から到達される reference は*部分的に*しか読まれない —
エージェントは全体を読む代わりに `head -100` のようなもので覗き見る — ので、その二つ目のホップの150行目に
ある規則は、誰も読まなかった規則である。エージェントがロードするファイルはすべて `SKILL.md` から直接リンクし、そうやって
見つかる。何という名前にするかは [Naming](#naming) で決着する。そうやって到達される reference は、それを必要
とした枝の上で丸ごと読まれる。だからその中のどこにある規則も、読まれた規則である。

ただし読み手は、長い reference の一つの節のために戻ってくる。その節を見つけるためにまた丸ごと読むのは、
このファイルが省くはずだった往復である。だから**100行を超える reference — このスキルの数字である — は、
自分の見出しの一覧で始める**。それより短いものが一覧を持っていてもよい。

context pointer が名指しするのは、そのファイルへ到達する**条件または問い**である：「APIが200以外を返したら
`references/api-errors.md` を読む」、あるいは「エラーコードが何を意味するか」。読み手がその場合に入ったときに
だけ reference がロードされる。

## Guard it three ways（三方向から守る）

スキルは、作業の前に言いくるめられ、作業の途中で削られ、作業のあとで「終わった」と宣言される。それぞれに
ガードを一つずつ。

| セクション | 何を捕まえるか | 形 |
|---|---|---|
| **Common Rationalizations** | 手順が飛ばされる前の言い訳 | `Rationalization` と `Reality` の表 |
| **Red Flags** | 出力に現れたあとの症状 | 箇条書き。それぞれが出力の中で目に見える一つのものを名指しする |
| **Verification** | その作業が終わっているかどうか | チェックリスト |

Common Rationalizations を埋めるのはエージェントが実際に口にしたものから — 反論する羽目になった言い訳を、
その最初の一回で足すこと。Red Flag は出力の中で観察できるものを名指しする — 「手順の入った description」 — ので、
エージェントはそれを探せる。規則の言い直しは、新たに見るべきものを何も与えない。

**項目がその席に値するのは、それが捕まえるものがスキルを機能させなくするときである** — ロードされないか、
発火しないか、到達されたうえで読み流されるか — あるいはそれが予算であるときである。Red Flag が同じものを
名指ししていてよい：一方は書いているあいだに読まれ、他方はそのあとに読まれる。残りの規則は、それが住んでいる場所で読まれることで満た
される。その全部を列挙したチェックリストは、規則そのものになってしまっている。

## The frontmatter（frontmatter）

`name` と `description` が必須であり、この二つがエージェントが事前ロードするものである。残りは任意で、
見つけられるかどうかではなく、どう走るかを決める：

| フィールド | 何を決めるか |
|---|---|
| `user-invocable`、`disable-model-invocation` | どちらの呼び出し元が到達できるか — 人の `/` メニュー、モデル、あるいは両方 |
| `context`、`background`、`model` | それ自身の実行環境として走るのか、そして何のもとで走るのか |
| `allowed-tools` | すでに手の届く範囲のうち、何がプロンプトなしで事前承認されるか |
| `disallowed-tools` | 何に手を伸ばしてはならないか — ツールを取り上げるのはこのフィールドである |

実行環境のフィールドは、別のスキルの一段階として起動されるスキルが立てるものであり、それを決着させる
reference へは `SKILL.md` が振り分ける。

そのすべてをコメントなしで書くこと。frontmatter はそのスキルが発火するたびにロードされる。その*選択*に議論が
要るフィールドが要するのは、著者が反論できる散文 — 本文 — であって、末尾の `#` ではない。設定をただ言い直す
一文は、後述の *Leave out what changes nothing* が扱う。

## Leave out what changes nothing（何も変えないものは書かない）

そのスキル自身の frontmatter がすでに設定していることを言い直す一文 — `context: fork`、
`user-invocable: false` — あるいは、たまたまそれを起動するスキルを名指しする一文は、本文に書かない —
「これはモデル起動スキルであり、レビュー中に `write-nice-instructions-as-comment` から呼ばれる」。どちらも
そのスキルがすることを変えず、後者はそのスキルが改名された日に誤りになる。

**no-op** も同じく書かない。それは丁寧さに見えて、何かを変える規則と同じ代金を読み手に払わせる。

そして、何も変えない論も書かない。読み手が何をするかを変える論は、それを変える規則のそばに属する。変えない
論は、本文の外に属する。

## When to split（いつ分割するか）

まずスコープ。スキルは、関数がそうであるように、まとまりのある一単位の作業を覆う。狭すぎれば一つの作業で
複数のスキルがロードされ、それぞれの指示を互いに突き合わせる羽目になる。広すぎれば、正確に起動できるものが
なくなる。データベースに問い合わせて結果を整形するのは一単位であり、そこにデータベース管理を足すと二単位に
なる。

そのうえで、切断がコストに見合うときにだけ分割する。そのコストはこのファイルの冒頭のものである：二つ目の
スキルは、それをインストールする全員に対して、毎ターン、永久に description の代金を払う。三つの切断が
それを正当化する：

1. **leading word による** — ある状況が*固有の* leading word を持ち、しかもこのスキルが先に発火していなくても
   到来する。そのスキルがすでにロードされたあとでしか現れない語は、その内側で reference をゲートするもので
   あり、毎ターンの description が二つになることで何も買わない。
2. **順序による** — 呼び出し元が一つの単位として到達できるべき一連のステップで、その途中の手順を後に来る
   ものが見る必要がないもの。固有のスキルを必要としているように見える一連のステップは、たいてい曖昧な完了
   条件を一つ抱えているだけであり、エージェントはそこで止まらずに通り過ぎる — だから各ステップの条件を、
   検査可能で、そのステップのどの部分も未計上のまま残さないところまで研ぐこと（「バリデータが0で終了する」）。
   そのうえで、切断がまだ必要かを見る。
3. **委譲による** — *異なる実行環境*で走るべきフェーズ：固有のモデル、固有のツールセット、固有の文脈。この
   切断はフェーズがどの実行環境で走るかを決めるのに対し、cut 2 はそのステップがどのスキルに属するかを決める。
   あるフェーズをそもそも委譲してよいかは別のテストであり、固有の reference にある。`SKILL.md` がそこへ
   振り分ける。

どの切断も当てはまらないなら、インラインのままにする。分割のための分割は、文脈の負荷（毎ターン description が
一つ増える）か認知の負荷（著者が抱えねばならないファイルが増える）のどちらかを増やし、何も買わない。
