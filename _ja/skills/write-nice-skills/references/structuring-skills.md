# スキルのサイズと分割

スキルが育っているときに読むこと：いくらまで許されるか、どう測るか、何を同梱ファイルへ出すか、そして一つの
スキルを二つに分けるべきか。

## What this settles（このファイルが決めること）

インストールされているスキルの `name` と `description` は、そのスキルが一度も使われなくても、毎ターン事前
ロードされる。同梱ファイルはそうではない：それを必要とする枝の上で読まれ、それ以外の誰も読まない。

だからサブスキルと同梱ファイルは、払うものが違う。サブスキルは、それをインストールした全員に対して、毎ターン、
永久に description の代金を払う。ファイルの代金を払うのは、それを開いた読み手だけである。育っているスキルが
どちらを勝ち取ったのかを、このファイルが決める。

## The decision（判断）

```text
測る。
├ 予算の内側                            → することは無い
└ 超えている →
    ├ 一部の枝しかその材料を必要としない → ファイル分離する
    ├ 切断がコストに見合う               → サブスキルに切り出す
    └ どちらでもない                     → スキルそのものを見直す
```

以下の章はこの順に並ぶ：まず測り方、そのあとは図が挙げた順に、各出口。

## Measuring it, and the figures（測り方と数字）

予算が属するのは**同時に立つスキルの集合**である。スキルは一度に一つずつ到着するわけではない：ある活動の
あいだ効き続けるルールは、手元の成果物のために別のスキルが発火しているあいだも常駐しており、読み手は両方の
代金を払う。自分の上限の内側にあるファイルでも、その活動を超過させうる。

| そのスキル | 予算 | 理由 |
|---|---|---|
| ある活動のあいだ常時オンである — ロードしたレスポンスを越えて、本文がそれを効かせ続ける | **そうした `SKILL.md` を全部合計して2000トークン** | すべての活動のすべてのターンがその代金を払う |
| 一つの成果物、一つの枝のために取りに行かれる | **1ファイルあたり5000トークン** | それを必要とする読み手だけが払う |

だから、一緒に出荷する常時オンのスキル — 自分が測れるもの — を合計して一つ目の数字と突き合わせ、手元の
成果物のために取りに行かれるファイルを一つずつ二つ目の数字と突き合わせること。**その合計が検査であり、2000
が落ちる線である。** 誰か他人の常時オンのスキルも自分のものと並んで常駐しうるが、それは出荷物のどれを測っても
出てこない。だから1999で通った合計でも、その活動を超過させうる。通ることは下限であって、目標ではない。
どちらの数字もこのスキル自身のものである。

行数はどちらの数字に対しても弱い代理指標である — 本文は行数では短く見えていながら、なお予算を大きく超える
コストになりうる — だからトークンを測ること：

```bash
# 一つの成果物または一つの枝のために取りに行かれるファイルを、それぞれ 5000 に照らして
bash <this skill's directory>/scripts/count-tokens.sh path/to/SKILL.md path/to/other-file.md
# 常時オンの SKILL.md すべてを、2000 に照らして合計するため
TARGET=2000 bash <this skill's directory>/scripts/count-tokens.sh <常時オンの SKILL.md すべて>
```

スクリプトは各ファイルを、現時点で既定のモデルに送り、ファイル抜きの基準リクエストを差し引く。得られる数字は
そのモデル自身の数え方であり、モデルが変わっても正しいままである。ファイルごとに数とトークンあたりのバイト比
を印字し、どれか一つでも `TARGET` — 環境変数で、既定は5000 — を超えると非ゼロ終了する。だから一つ目の
コマンドは成果物起動型のファイルをそれだけで検査できる。常時オンの数字は合計なので、ファイル単位の終了コード
では検査できない：二行目を走らせ、自分で数を足し合わせること。

無料の事前チェックには `wc -c` でバイト数を数えること。トークンあたりのバイト数が安定した比率であり、
だからこそバイト数がトークン予算の代用になる。**およそ 15 KB が5000トークンの、6 KB が2000トークンの代用に
なる。** ここにある数字はそれぞれ、スクリプトを一度走らせた結果を丸めたものである。スクリプトが印字する
バイト換算は一つだけで、いま測った対象のモデルと、そのとき効いていた `TARGET` に対するものである。だから上の
一つ目のコマンドが 15 KB の数字を、二つ目が 6 KB の数字を印字する。既定のモデルが変わったら、それぞれ新しい
実行から読み取ること — 低すぎる古い数字は、そもそも予算を超えていなかったファイルを分割させに行かせる。
二つ目のコマンドの終了コードは常時オンの検査ではない。その合計は依然として自分で足すものである。

## Splitting the files（ファイルへの分割と構成）

材料の一つ一つは、以下の置き場のどれかに行く。

- **インライン**にする（`SKILL.md` に）：**すべての経路が必要とするもの** — 本文が持つ節そのもの、そして
  ガードのうちエージェントが頭に入れておかねばならない二つ — Common Rationalizations と Red Flags。
- **外へ出す**（そこへ到達する条件を名指すポインタの後ろに）：**一部の枝しか到達しないもの** — 深い詳細、
  長い実例、枝ごとの手順。
- **未リンクのままにする**：**どの枝も到達しないもの** — `SKILL.md` の隣にあって何からも指されないファイルは
  決してロードされず、エージェントの文脈を一切消費しない。設計上の論拠、人に向けたそのスキルの説明、規則が
  どこから来たか。

スキルの常置の役割を担うファイルは、名前が固定である。置き場は `SKILL.md` の隣で、どのスキルでも同じパスに
あり、grep 一回で全部が見つかる。

- **`GLOSSARY.md`** — 規則が使う用語
- **`VERIFICATION.md`** — 外へ出されたあとの検査

どちらも必須ではなく、名前が固定されるのは、それを持つスキルにとってである。

**その他にエージェントがロードするものはすべて枝の材料であり、その名前はあなたのものである。**
`references/`、`scripts/`、`workflows/`、`assets/`、あるいは `SKILL.md` の隣の裸のファイル。そのスキルの
他のフォルダがすでに使っているものに合わせ、それ以上考えないこと。

## The principles of splitting a file（ファイル分割の原則）

**一段の深さ。** 別のファイルから到達されるファイルは、丸ごと読まれるとは限らない — エージェントはその上の
ほうを覗いて先に進むことがある — ので、その二つ目のホップの下のほうにある規則は、読まれたと当てにできない
規則である。エージェントがロードするファイルはすべて `SKILL.md` から直接指され、それを必要とした枝の上で
読まれる。

**ポインタは、そのファイルへ到達する条件または問いを名指しする**：「APIが200以外を返したら
`references/api-errors.md` を読む」、あるいは「エラーコードが何を意味するか」。読み手がその場合に入ったときに
だけファイルがロードされる。

**規則そのものは、それを所有するファイルに委ねる。** `SKILL.md` だけで規則を決着させられる著者は、その元に
なったファイルを開かない。

**以下は、文脈にどれほど余裕がなかろうとインラインに留まる。** まっとうな前提を裏切る事実 —
エージェントは、そこに何が書いてあると予期する理由のないファイルへ自分を送る条件を認識できないからである。
そして、飛ばそうとするまさにその瞬間にエージェントが必要とする答え — Common Rationalizations の行、
Red Flag — エージェントが決してロードしないファイルに置けば、その答えは誰も適用しない助言だからである。

**動いてよいガードは Verification である。** これはエージェントが頭に入れておく必要のない唯一のガードである：
他の二つは考えている最中に捕まえねばならないのに対し、これは最後に、仕上がった成果物に照らして読まれる。だから
満たすべき条件は無い — `SKILL.md` が重いなら、チェックリストを `VERIFICATION.md` へ出し、「成果物を完了と
呼ぶ前」で到達させること。

## Splitting into a second skill, and its principles（スキル分割と原則）

まずスコープ。スキルは、関数がそうであるように、まとまりのある一単位の作業を覆う。狭すぎれば一つの作業で
複数のスキルがロードされ、それぞれの指示を互いに突き合わせる羽目になる。広すぎれば、正確に起動できるものが
なくなる。データベースに問い合わせて結果を整形するのは一単位であり、そこにデータベース管理を足すと二単位に
なる。

そのうえで、切断がコストに見合うときにだけ分割する。そのコストはこのファイルの冒頭のものである：サブスキルは、
それをインストールする全員に対して、毎ターン、永久に description の代金を払う。分割のための分割は、文脈の
負荷（毎ターンの description が一つ増える）か認知の負荷（著者が抱えるファイルが増える）のどちらかを増やし、
何も買わない。それを勝ち取る切断は以下である。

### leading word による

ある状況が*固有の* leading word を持ち、しかもこのスキルが先に発火していなくても到来する。そのスキルが
すでにロードされたあとでしか現れない語は、その内側でファイルをゲートするものであり、毎ターンの description
が二つになることで何も買わない。

### 順序による

呼び出し元が一つの単位として到達できるべき一連のステップで、その途中の手順を後に来るものが見る必要がない
もの。固有のスキルを必要としているように見える一連のステップは、たいてい曖昧な完了条件を一つ抱えているだけ
であり、エージェントはそこで止まらずに通り過ぎる — だから各ステップの条件を、検査可能で、そのステップのどの
部分も未計上のまま残さないところまで研ぐこと（「バリデータが0で終了する」）。そのうえで、切断がまだ必要かを
見る。

### 委譲による

*異なる実行環境*で走るべきフェーズ：固有のモデル、固有のツールセット、固有の文脈。この切断はフェーズがどの
実行環境で走るかを決めるのに対し、順序による切断はそのステップがどのスキルに属するかを決める。

委譲されたフェーズも依然として親の作業である。より安く、より狭いところで走り、それを生んだ材料ではなく親が
必要とするものを返す。**テストは、呼び出し元がその作業を検査するのに必要なものを、すべて受け取るかどうか
である。**

**機械的で読み取りのみの収集・列挙・解析は委譲すること** — PRのコメントを取ってくる、変更ファイルを並べる、
パッケージレジストリを辿る、設計をリポジトリに接地させる。答えこそが親の欲しかったものの全部であり、その
答えが丸ごと返ってくるから、これは通る。

**成果物を生むフェーズは委譲すること。** 渡すのは書かれた一つの指示書である。成果物が丸ごと返ってきて、
読み手がその物自体を判断できるから、これは通る。

**産物が判定だけのフェーズは決して委譲しないこと。** レビューがその例である：その実質をサブスキルに置くと、
判定はそれぞれが何に立脚しているかを伴わずに返ってきて、誰もそのレビューをレビューできない。

サブスキルを固有の実行環境に置くのはこの切断だけであり、だから frontmatter が変わるのもこの切断だけである。
そのフィールドを定めるファイルと、サブスキルの本文がどこで指示書を受け取るかを述べるファイルへは、`SKILL.md`
が振り分ける。

### サブスキルとは何か

他と変わらない一つのスキルである：このスキルが持つ規則に則って書くこと。leading word による切断が残すのは、
自分の力で到達される兄弟である。順序または委譲による切断が残すのは、親が起動するフェーズである。

親のフェーズとしてしか走らないサブスキルは、名前を親から取る：`<parent-skill-name>-<role>`。この接頭辞が、
ディレクトリ一覧で二つを並べて保つ。改名が触るのは自分の持ち物だけである：両者のディレクトリと frontmatter
の `name`、そして親の本文のうちサブスキルを名前で呼び出している箇所。

## Looking at the skill itself（スキルそのものを見直す）

移すものが無く、切る先も無いということは、重さがインラインに留まるしかない章にあるということであり、その
大半はガードである。しかし Common Rationalizations と Red Flags は、実際に起きたことから埋められる：反論
する羽目になった言い訳ひとつにつき一行、出力の中で見つけた欠陥ひとつにつき一項目。厚い二つは、**このスキル
が何回言いくるめられたか、何回間違えたかの数**である。行を削ることは記録を消して原因を残すことなので、見る
べきはスキルそのものである。何を切り出し、何を削るかは、そのスキルが何を抱えているか次第である：表が告げる
のは、何かがおかしいということであって、何がおかしいかではない。

実例を一つ。プルリクエストをレビューするスキルがワークフローを走らせており、その走りのステップ一つ一つに、
それぞれサボる理由があった。だから表は、どのステップに対する行かを言う列を持たざるを得なくなった。その列
こそが発見だった：Rationalization 対 Reality に三つ目の軸の居場所は無く、それが要るということは、行が複数の
スキルに属しているということだった。答えは、ステップごとに一つのスキルにすること — 計測では見えなかった切断
であり、この枝はそのためにある。ステップの条件を研いでも届かなかった。どれ一つ曖昧ではなく、言い訳はそれぞれ
自分のステップについてのものだったからである。
