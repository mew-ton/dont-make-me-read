# 子スキルへ段階を委譲する

一つのスキルの一段階を別の場所で走らせるべきときに読むこと：自前のモデル、自前のツールセット、自前の文脈で。

## 何を委譲してよく、何をしてはならないか

委譲が決めるのは、**一つのフェーズがこの実行環境を離れるかどうか**である。委譲されたフェーズは依然として
親の作業であり、より安く狭いどこかで走り、それを
生んだ材料ではなく親が必要とするものを返す。

テストは、**呼び出し元が、その作業を検証するのに必要なすべてを受け取るかどうか**である。

**機械的で読み取り専用の収集、列挙、パースを委譲せよ** — PRのコメントの取得、変更ファイルの列挙、
パッケージレジストリの走査、設計をリポジトリに接地させること。これが通るのは、親が欲しかったのは答えだけで
あり、その答えは丸ごと戻ってくるからである。

**成果物を生み出すフェーズを委譲せよ。** 書かれたブリーフを一つ渡す。これが通るのは、成果物が丸ごと戻って
きて、読み手がその物自体を判断するからである。

**生み出すものが判定だけのフェーズは決して委譲しない。** レビューがその例である：その実質を子に置くと、
各判定が何に立脚しているかを欠いたまま戻ってきて、誰もそのレビューをレビューできなくなる。

## fork が何を買うのか、そして場合ごとにどの `model` を求めるか

以下の動機は fork が何を買うのかを述べるもので、上の委譲してよい二つのケースに当てはまる：収集はたいてい
`Context`、成果物を生み出すフェーズはたいてい `Cleanliness`、そして `Independence` はそのどちらかを二回委譲
する場合で、どちらの写しも他方の答えを見てはならない。

| 動機 | fork が買うもの | `model` |
|---|---|---|
| **Context** — 大量の収集をメインスレッドから外す | 生の材料が親の文脈に決して着地しない | それができる最安のモデル：純粋な収集と数え上げなら `haiku`、軽い正規化が絡むなら `sonnet` |
| **Independence** — 二つの子が互いの出力を見てはならない | 同じフェーズが二回走り、どちらの走りも他方が生み出したものに届かない | 元になっているケースのとおり。`Context` か `Cleanliness` |
| **Cleanliness** — ブリーフを生み出した会話が成果物に届いてはならない | 探索、中途半端な依頼、取得した材料が、成果物が書かれる文脈に決して入らない | 未設定のままにする。子は親のものを継承する |

## Naming（命名）

`<parent-skill-name>-<role>`：親の名前、ハイフン、そして子が演じる役割 —
`review-nice-issues-change-inventory`、`write-nice-architecture-docs-repo-grounding`。この接頭辞が、
ディレクトリ一覧で親子を隣に並べる。そして改名が触るのは自分が所有するファイルだけである：それぞれの半分の
ディレクトリと frontmatter の `name`、そして親の本文で子を名前で起動している箇所。

## Passing input（入力の渡し方）

親が子に到達する経路は、どのスキルに対しても同じ — 名前で、`Skill` ツール経由である。ブリーフが着地すべき
場所に、子の本文で **`$ARGUMENTS`** を置き、ブリーフは一塊で渡すこと。
