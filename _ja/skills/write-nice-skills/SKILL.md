## Scope（範囲）

このスキルは **`SKILL.md` をオーサリングすること**についてのものである — スキルの `description` と本文を、
(a) 発火すべきときに発火し、(b) ロードする価値があるほど軽く保たれるように書き、レビューすること。新しい
スキルを作るときにも、既存のものを編集するときにも適用される。

これは汎用のリポジトリレビューのパス**ではない** — PRに対してチェックリストを走らせるのは別の仕事である。
スキルがどの frontmatter フィールドを設定するかは決めない — コメントを入れないこと以外は。そしてスキル以外の
ドキュメントのためのものでもない。これは
目の前の `SKILL.md` によって取りに行かれ、そのファイルとともに終わる。だからこそ persistence の節を持たず、
自分自身の description も `when` を先頭に取る。

詳細は一段下にある（[References](#references) を参照）。このファイルは、どの枝にいようとすべての著者が
必要とするものを担う。

## Why the description carries the weight（なぜ description が重みを担うのか）

エージェントがスキルをロードするかどうかを決めるとき、それが読むテキストは `description` **だけ**である。
本文はまだ文脈になく、スキルが発火した**後で**ロードされる。したがって description は、二つの負荷のかかる
仕事を同時にこなす：

1. エージェントが *このスキルが該当するかどうか* を description だけから判断できなければならない。
2. 手順を漏らしては**ならない**。手順が description にあると、エージェントは本文をロードせずに行動できると
   信じ込み、そのスキルが届けるために存在するまさにその指示を飛ばす。

「Writing the description」以下のすべては、この一つの事実から導かれる。

## Principles（原則）

**Description**（詳細：
[`references/writing-descriptions.md`](references/writing-descriptions.md)）：

1. **満たすべき：命令形、意図、when、英語、簡潔。** `Use this skill when …` — 三人称を使うのは、主語を
   落とすとその文が作業の記述として読まれてしまう場合だけである。そのスキルの著者が何を強制したかったのかを
   一節で示し、機会を名指しし、全体を 1024 文字に収めること。
2. **満たしてはならない：手順、判定基準、他所の名前。** 手順はエージェントを本文なしで行動させ、そのスキルが
   適用する判定基準は同じことを一段上で起こす。兄弟スキルの名前、ファイル、これを呼ぶ誰か：具体名は
   ルーティング表として読まれ、*この*成果物は自分のものか、という問いをエージェントに問わせなくする。
   そして改名された日にもう一度支払わせる。成果物を名指しせよ。それを所有するスキルではなく。
3. **効果のある文体。** 最初の1行は、*what* と *when* のうちエージェントが推測できないほうを担い、それを
   決めるのは一つの問いである：作業はその成果物を名指しするか。名指しするなら（issue、README、`SKILL.md`）
   `when` を先頭に。名指ししないなら — コードやコメントを書いているあいだ効いている規則がそうである —
   姿勢を先頭に：`Forces the X that Y.`。誰も名指ししない機会は、エージェントが忘れる機会だからである。
   `DO NOT use this skill when …` で閉じる。同じ `when` を否定したものなので、対で一つの使用条件として
   読まれる。作業そのものが供給する語である leading word を前に出す。枝ごとにトリガー一つ、同義語の
   水増しはしない。
4. **本文の素性は本文に残す。** その規則の論拠も、破ったときの代償も、処方も置かない — それらを手渡された
   エージェントは、スキルそのものを手渡されている。見分けのつく用語は残す：発火させるのはそれである。

**Body**（詳細＋基準：
[`references/structuring-skills.md`](references/structuring-skills.md)）：

5. **全部書かない。** 本文をサイズ予算の中に保ち — 予算は同時に立つスキルの集合に属し、ある活動の
   あいだ効き続けるスキルに対して最も厳しい — 枝に固有の詳細は本文が指すファイルへ一段押し下げる。
   すべての経路が必要とするものをインラインにし、一部の枝しか到達しないものはポインタの後ろに置く。
6. **Common Rationalizations を足す。** エージェントが手を抜きそうなスキルには、その言い訳を先回りして
   封じる（下の表を参照）。
7. **効き続けねばならないなら、効き続けると述べる。** ある活動のあいだ効き続けるスキルは一度ロード
   されたあと、その後に来るすべてと競合する。まだ効力があると決して言わない本文は、すでに与えられた
   助言として読まれる。
8. **構造がすでに決着させていることは書かない。** スキルは自分の分類も、誰が呼ぶかも、どこに座って
   いるかも知る必要がない — frontmatter と呼び出し元がそれらをすべて確立しており、それを述べる一文は
   そのスキルがすることを何も変えない。呼び出し元の名前が変わった日に、そのスキルを誤りにもする。
   description も原則 2 によって同じ制約を受ける。
9. **frontmatter にコメントを書かない。** それは `SKILL.md` の中で読まれるのではなくパースされる部分であり、
   そのすべてが発火のたびにロードされる。本当に説明を要するフィールドは、著者が反論できる散文での説明を要する
   — 本文か、アーキテクチャドキュメントで — 将来のすべての読み手が代金を払う末尾の `#` ではない。

上で使った用語（leading word、trigger、branch、progressive disclosure、context pointer）は
[`GLOSSARY.md`](GLOSSARY.md) で定義されている。

## Common Rationalizations（よくある自己正当化）

エージェントはこのスキルを飛ばす理由を探す。それらを封じよ：

| 自己正当化 | 実際のところ |
|---|---|
| 「description は短いほうが確実に発火する。」 | 発火するのは*共有された語*によってであって、簡潔さによってではない。プロンプトが共有する leading word がなければ、決して結びつかない — 長さはレバーではない。 |
| 「自己説明的になるよう、手順を description に入れておく。」 | するとエージェントは description から行動し、本文を決してロードしない — あなたが書いた手順は飛ばされる。手順は本文に留めよ。 |
| 「なぜその規則が重要かを description が説明しないと、誰も本気で受け取らない。」 | 論拠と代償と処方こそがそのスキルである。本文がロードされる前に読まれる場所にそれらを置けば、エージェントはすでにスキルを与えられている — 要約に基づいて行動し、何も確認しない。作業が供給する語は残し、理屈は下へ動かせ。 |
| 「使わない場合を述べるのは否定的で、予算の無駄だ。」 | 境界のない `when` は隣接する成果物すべてに発火し、誤った発火は毎回、本文まるごとを支払わせる。`DO NOT` は条件の、安いほうの半分である。 |
| 「もう一方の成果物を所有する兄弟スキルを名指しすれば、エージェントの振り分けを助けられる。」 | それは*この*成果物が自分のものかという、境界がそもそも存在する理由である問いを、エージェントに問わせなくする。そしてそのスキルが改名された日にもう一度支払いが来る。除外する成果物のほうを名指しせよ。スキルは自分の description によって到達されるか、さもなくば到達されない。 |
| 「1ファイルのほうが分割より単純だ。」 | 肥大した `SKILL.md` は、そのスキルが発火する*たびに*全部ロードされ、文脈全体を引きずる。枝でしか使わない詳細はポインタの後ろへ押し出せ。 |
| 「今フルのガイドを書いて、後で削る。」 | 削らない。長すぎるスキルは長すぎるまま出荷される。書きながら予算まで削れ。 |
| 「この description は自分には良く読める。」 | あなたはトリガーではない。自分の要約に照らすのではなく、*ユーザー*が打つ語に照らして確認せよ。 |
